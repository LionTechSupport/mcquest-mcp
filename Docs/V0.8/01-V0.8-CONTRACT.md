# MCQuest MCP v0.8 — Contract

> STATUS: **V0.8 ACTIVE DEVELOPMENT SPECIFICATION (APPROVED 2026-09-20)**
>
> This contract defines the consolidated V0.8 extension-layer contract, incorporating ALL substantive proposals of the retired predecessor package per the 2026-09-20 user instruction (consolidated coverage record: `08-V0.8-CONSOLIDATED-COVERAGE.md`). It is normative for planning only. Nothing in this contract authorizes implementation on its own; implementation begins only after explicit Phase 3 authorization (DEC-021).

---

## 1. Binding Premises

P001 — V0.8 is an audit-layer extension, not a rewrite of the core repository intelligence model.

P002 — The MCP remains read-only by default.

P003 — All V0.8 tools must return structured evidence with file paths, line numbers, and an explicit evidence basis.

P004 — Output must stay bounded, deterministic, and suitable for AI client consumption.

P005 — The tool layer must preserve the project’s safety model: root confinement, read-only operation, and no repository mutation.

P006 — The V0.8 layer must remain a thin analytical layer over repo evidence; it does not replace the human decision-maker.

P007 — V0.8 must not reinterpret or bypass the V0.7 and earlier constraints unless a new decision explicitly authorizes them.

P008 — Scope creep is forbidden unless explicitly approved. The proposed tools are intentionally narrow and specialized.

P009 — V0.8 output must distinguish `evidence` (what was observed) from `issue` (what looks inconsistent or risky), `severity` (how urgent the issue appears), and `recommendation` (a suggested review step — never a forced action and never a fact claim).

P010 — Interoperability with Cline (or any MCP client) is a client-compatibility concern, not a claim that MCQuest implements Cline-native tools or presentation. `search_block` is an existing server-side MCQuest formatter (`src/mcquest_mcp/formatting.py`), not a Cline API.

P011 — Cross-call activity grouping and aggregation belong to the client. The server must not maintain session-level counters or emit client-side activity summaries.

P012 — Optional native-like compatibility wrappers are deferred until a concrete client need is demonstrated; if approved later, they must be read-only, preserve root confinement, and delegate to the existing implementations rather than duplicate logic.

P013 — V0.8 tools MUST expose stable summary metadata (`operation`, `query`/`pattern`, `path`/`scope`, `files_affected`, paging, completeness) when returning structured evidence, to support generic MCP-client presentation.

P014 — The V0.8 output budgets are binding: normal presentation ≤ 4000 chars, absolute ceiling ≤ 16000 chars, per-line clip ≤ 200 chars (first 199 chars + `…`), explicit pagination only, per-tool deterministic sorting, project-root confinement, and the V0.7 P004/P005 completeness semantics (`collection_complete=true` means the total is known, NOT that every item was delivered).

P015 — `mcquest_find_ui_text` is authorized as a lexical-only UI-candidate detector/classifier. Parser-grade and semantic UI classification remain RESERVED and NOT AUTHORIZED (Phase 3 lane). No V0.8 tool may cross into the reserved lane.

P016 — V0.8 tools compose existing primitives only (the shared walked/ignored-path/size-guarded source and markdown readers, the `search_block`-family renderers, and existing evidence tools). V0.8 introduces NO new search index, parser dependency, embedding surface, or broad-language expansion.

## 2. Proposed Tool Contracts

Canonical ownership (DEC-029): this contract is the single canonical normative location for V0.8 rule text — tool contracts, enums, lexical evidence rules, output fields, the severity/confidence model, input/path/error behavior, budgets, and completeness semantics. `04-V0.8-TEST-PLAN.md` holds the test assertions and fixtures and must reference the sections here rather than restate rule text. `05-V0.8-DECISIONS.md` records decisions and cross-references this contract. `00`, `02`, `03`, `06`, `07`, `08` are non-canonical references.

### 2.0 Input, path, and error behavior (all four tools)

Binding and deterministic (DEC-027). This mirrors existing project conventions verified in the codebase (`src/mcquest_mcp/security.py`, `src/mcquest_mcp/tools/component_inventory.py`, `src/mcquest_mcp/tools/docs.py`). No new error code and no new response field is introduced.

| Input case | Required behavior |
|---|---|
| `path` omitted, empty, or the project root | Scan the project root, subject to the tool's file-type boundary |
| in-root file path | Accepted if its extension is within the tool's file-type boundary; otherwise rejected |
| in-root directory path | Recursive scan, subject to the ignored-directory policy and the file-size guard |
| nonexistent path | Rejected: `FileNotFoundError` |
| unsupported file type | Rejected: `ValueError` (mirrors `docs.py` "Not a Markdown file" and `component_inventory`'s supported-set rejection) |
| path outside the project root | Rejected explicitly: `ValueError` (mirrors `security.resolve_project_path`); never silently confined, never an empty result |
| ignored directory (`is_ignored_path`) | Rejected: `ValueError` |
| unreadable file, or file exceeding `MAX_FILE_BYTES` | Rejected: `ValueError` ("Unreadable file" / "File exceeds N byte safety limit") |

- Invalid input MUST NOT be reported as an empty result set. A zero-row response means "no match in the scanned scope" and never "input rejected".
- `offset` must be >= 0; negative values are rejected (`ValueError`), matching existing tools.
- `max_results` is clamped to 1-500 (default 50), matching existing tools.

### 2.1 `mcquest_find_ui_text`

Purpose:

- find candidate user-facing text in TS/JS sources (`.js`, `.jsx`, `.ts`, `.tsx` only)
- apply lexical heuristics only; classification follows the DEC-032 rules below — `decorative` (letter-absence) and `unknown` (letter-bearing, while the brand/admin lists are unrecorded) are emittable; `localizable`, `brand`, and `admin-only` are not emittable until their evidence rules/lists are recorded
- return a bounded evidence list with file/line and classification

Binding scope (DEC-015): lexical-only UI-candidate detection and classification. Parser-grade and semantic UI classification are RESERVED and NOT AUTHORIZED. Results are candidates; a zero result never proves that no UI text exists (same honesty rule as `mcquest_find_strings`).

Eligible literal locations (DEC-026): quoted string literals and template-literal static segments, using the existing `mcquest_find_strings` lexical scanner (`src/mcquest_mcp/tools/strings.py`). That scanner is the approved primitive; V0.8 adds no extractor.

Explicit limitations (verified against the approved primitive — DEC-026):

- JSX text nodes are NOT extracted. The approved primitive scans only `'`, `"`, and backtick delimiters, so text written directly between JSX tags (for example `<Button>Save changes</Button>`) is not a candidate. JSX text nodes are therefore out of scope for V0.8 and MUST NOT be claimed as covered.
- Attribute string values (`title="Save"`) and other quoted/template literals ARE in scope and must be reported as distinct from JSX text nodes.
- Comments are NOT a candidate source; no comment extractor is added. The approved primitive has no comment awareness, so a quoted literal that physically appears on a comment line is not excluded by it. That is an incidental lexical limitation, not comment support, and it MUST NOT be described as comment filtering.
- A zero result never proves that no user-facing text exists.

Input concepts:

- `path` — project-relative root or file path (root confinement applies; see §2.0)
- `file_pattern` — optional basename glob filter
- `max_results` — bounded result count (clamped 1–500, default 50)
- `offset` — 0-based explicit pagination continuation
- `classify` — whether to return classification labels (default `true`; when `false`, rows carry only the location and snippet — DEC-032)

`include_brand` is REMOVED from the V0.8 input contract and the filter is deferred (DEC-026): no maintained brand-token list or owner exists in the project's authoritative documentation, so the contract must not promise brand filtering. This is a recorded deferral, not a documented no-op input.

`include_admin` is likewise REMOVED from the V0.8 input contract and the filter is deferred (DEC-031): with `admin-only` not emittable, the filter would be a documented no-op — the same condition that removed `include_brand` (DEC-026). If an admin/dev/debug marker list is later recorded and `admin-only` becomes emittable, the filter may be reconsidered by a separate decision.

Classification enum (fixed, DEC-018): `localizable` | `brand` | `admin-only` | `decorative` | `unknown`.

Classification rules (canonical — DEC-032), computed from the candidate literal's text only:

- A literal containing no ASCII letter matching `[A-Za-z]` is classified `decorative` (letter-absence branch; emittable). Confidence `high` (§4): determinate lexical evidence, no unresolved element.
- A literal containing one or more ASCII letters is classified `unknown` while the required brand-token list and admin-marker list remain unrecorded (§7b of `02-V0.8-PLAN.md`). Its `reason` MUST identify the missing brand-token list and admin-marker list as the unresolved evidence. Confidence `medium` (§4): the label reflects recorded state whose defining evidence is unresolved.
- `localizable`, `brand`, and `admin-only` are NOT EMITTABLE in the current V0.8 implementation until their required evidence rules/lists are formally recorded. `brand` has no maintained token list or owner (DEC-026) and `admin-only` no recorded marker list, so neither can satisfy DEC-017's evidence requirement; `localizable` has no recorded evidence rule and is NEVER inferred by elimination. All three remain in the fixed enum (DEC-018 unchanged) and MUST NOT be emitted.
- An enum value that cannot currently be emitted MUST NOT be treated as implementation-ready merely because it emits nothing.
- Filters suppress rows only: `classify` (plus `file_pattern`) control which rows and fields are emitted and never change a row's classification value. Classification is computed before filters are applied (DEC-026/DEC-031).

Completeness (DEC-016): full-scan two-pass model — this tool performs an honest counting pass over the in-scope candidate evidence, so `collection_complete=true` is always reported (`total` is the known count, not the delivered count) and pagination is explicit only (`offset`/`next_offset`/`has_more`).

Output:

- summary block with stable metadata (P013)
- `file:line` evidence rows
- text snippet
- classification / confidence / reason (confidence is a heuristic label and is never presented as fact — DEC-017); emitted when `classify=true` (the default). When `classify=false`, each row carries only the location and snippet and the summary is unchanged (DEC-032)

Safety:

- read-only
- no writes
- no project mutation
- no code execution
- no parser dependency, no new index (P016/DEC-019)

### 2.2 `mcquest_ui_contract_audit`

Purpose:

- analyze component contracts and cross-file usage consistency on lexical evidence (`.js`, `.jsx`, `.ts`, `.tsx` only; no parser — DEC-018)
- detect missing props, stale props, mismatched component usage, and likely drift
- report evidence without performing any fix

Input concepts:

- `path` — root or component directory (root confinement)
- `component_pattern` — optional file filters
- `include_callers` — optional boolean
- `max_results` — bounded result count (clamped 1–500, default 50)
- `offset` — 0-based explicit pagination continuation

Issue category enum (fixed, DEC-018): `missing_prop` | `stale_prop` | `mismatched_usage` | `signature_drift` | `unverifiable`.

Lexical evidence rules (canonical — DEC-022/DEC-023). All rules are exact-text and exact-token comparisons: no parser, no symbol resolution, no semantic inference.

- `missing_prop` — a prop key declared at an in-scope component definition is not passed at one or more in-scope call sites. Severity then depends on scan completeness and evaluability (§4):
  - `critical` ONLY when all relevant call sites are accounted for in a complete scan AND every such call site omits the prop AND every such call site is fully evaluable;
  - `warning` when only some relevant call sites omit the prop;
  - never `critical` when the scan is incomplete, a relevant call site is unevaluable, or coverage cannot support an all-sites claim.
- `stale_prop` — a prop key passed at the call sites of a fully available in-scope definition is demonstrably not declared by that definition.
  - A definition is "fully available" only when: exactly one in-scope definition site is found for the component name; its declared prop-key set is lexically enumerable (no spread/rest element among the declared props); and the definition file is readable within `MAX_FILE_BYTES` and not on an ignored path.
  - `warning` only. If the definition is unavailable, partial, ambiguous, or duplicated across definition sites, a verified `stale_prop` MUST NOT be asserted; report `unverifiable` instead.
- `mismatched_usage` — the same component name is referenced at two or more fully evaluable in-scope call sites whose prop-key sets differ, and no in-scope definition explains the difference. Severity `warning` (DEC-031).
- `signature_drift` — a definition line's declared prop-key list differs lexically (exact key tokens) from the prop keys passed at one or more fully evaluable in-scope call sites. Severity `warning` (DEC-031).
- `unverifiable` — the contract cannot be settled from lexical evidence alone: a non-literal or spread argument list, an unresolved component-name match, an unavailable/partial/ambiguous definition, or an unreadable target. Severity is always `info` and confidence always `low`; it is never asserted as a confirmed defect and is never `critical`.

Terminology used by these rules: a "relevant call site" is an in-scope lexical call/reference of the component name; a call site is "accounted for" when it was both enumerated and read; and it is "fully evaluable" when its argument list is lexically complete (no spread, no unresolved non-literal argument list).

Absence of lexical evidence is never proof of a defect (DEC-022). A merely unobserved call site is never reported as a verified missing-prop violation. Finding severity and scan completeness are separate dimensions and must not be conflated (DEC-022/DEC-028).

Completeness (DEC-016, corrected by DEC-022): full-scan two-pass model — this tool performs an honest counting pass over the in-scope definition/call-site evidence, so `collection_complete=true` is always reported (`total` is the known count, not the delivered count) and pagination is explicit only (`offset`/`next_offset`/`has_more`). Earlier text in this section stated a capped-scan model for this tool; that contradicted DEC-016, `00-V0.8-MASTER.md` section 7, `02-V0.8-PLAN.md` section 7 and `04-V0.8-TEST-PLAN.md` section 2.3, and is corrected here (not silently reconciled). The capped-scan model applies only to `mcquest_doc_gap_audit` and `mcquest_feature_impact_audit`.

Output:

- component name
- file / line
- caller usage
- issue category (enum above)
- severity (`info` | `warning` | `critical`; heuristic label — DEC-017; rules in section 4)
- confidence (`low` | `medium` | `high`; heuristic label — DEC-025)
- supporting evidence row, required for every emitted severity and confidence label
- `risk` is NOT emitted by this tool; risk semantics are deferred (section 4 / DEC-025)

Safety:

- read-only
- no automatic edits or code generation

### 2.3 `mcquest_doc_gap_audit`

Purpose:

- find misalignment between documentation and implementation
- detect stale references, missing docs, and mismatched feature status using lexical evidence rules (DEC-018)

Input concepts:

- `docs_path` — Markdown scope (`.md`, `.markdown`, `.mdown`, `.mkd`; root confinement)
- `code_path` — the existing supported code set (`.js`, `.jsx`, `.ts`, `.tsx`); no broader-language expansion (DEC-019)
- `feature_scope` — UNRESOLVED (DEC-030). The retired predecessor package listed this input but no authoritative project material defines a meaning for it. It MUST NOT be implemented until a definition is recorded (see `02-V0.8-PLAN.md` section 7b).
- `max_results` — bounded result count (clamped 1–500, default 50)
- `offset` — 0-based explicit pagination continuation

Issue type enum (fixed, DEC-018): `stale_reference` | `missing_doc` | `conflicting_reference` | `status_mismatch`.

Eligible documentation locations and token boundaries (canonical — DEC-026):

- Eligible location: a line of an in-scope Markdown file (`.md`, `.markdown`, `.mdown`, `.mkd`) that is OUTSIDE a fenced code block.
- Documentation tokens are recognized lexically only; no Markdown parser is used and none may be implied. **Eligible evidence carriers (canonical — DEC-033):** (a) the content of a backtick-delimited inline span, and (c) a path-like token containing `/` with a recognized source or doc extension. The identifier-token form `[A-Za-z_][A-Za-z0-9_]*` is a tokenizer/evidence-extraction rule applied WITHIN those eligible carriers; it is NOT a standalone carrier over arbitrary Markdown prose. Ordinary prose words (`the`, `tool`, `returns`, `This`, …) are therefore never code-reference candidates merely because they match the identifier shape (DEC-033; honesty boundary under DEC-022).
- Fenced code blocks are excluded by default. Fence recognition is a lexical line-state scan: a line whose first non-whitespace characters are three or more backticks or three or more tildes toggles the fenced state; a language tag on the opening fence is ignored. This is a lexical computation over lines from the existing markdown reader (`src/mcquest_mcp/tools/docs.py`), not a parser dependency and not a new index.
- Unterminated fence: if the document ends while a fence is open, every line after the opening fence is treated as fenced (excluded) and the condition is reported through the completeness NOTE (`collection_complete=false`), never as a finding.
- Tokens inside backticked inline spans are eligible; tokens inside fenced blocks are not.

Lexical evidence rules (canonical — DEC-026/DEC-030). Exact-text and exact-token comparisons only; no semantic inference.

- `stale_reference` — an eligible documentation carrier token (per the carrier rule above: inline backtick-span content, or a path-like token with a recognized source or doc extension) that names a code symbol or location is not found in the bounded code scan. Severity `warning`. Bare prose identifiers are NOT eligible carriers and never produce this finding; no semantic symbol resolution and no maintained symbol list are used (DEC-033). Absence of lexical evidence is not proof of a stale reference (DEC-022).
- `missing_doc` — NOT EMITTABLE in V0.8 (DEC-030): the source of explicit documentation obligations (what lexically creates an obligation for a code token to be documented) is not defined in the project's authoritative material. It remains in the fixed enum (DEC-018 unchanged) but MUST NOT be emitted until that source is recorded.
- `conflicting_reference` — NOT EMITTABLE in V0.8 (DEC-033). "Exact-text contradictory claims about the same token" has no recorded lexical contradiction evidence rule, and this contract forbids semantic inference, so the category has no lawful evidence path in V0.8. It remains in the fixed enum (DEC-018 unchanged) and MUST NOT be emitted by `mcquest_doc_gap_audit`. No contradiction vocabulary, marker list, semantic inference rule, or natural-language contradiction detector may be invented. Reconsideration condition: a future decision must define the lexical contradiction evidence rule and its severity/confidence mapping before the category becomes emittable.
- `status_mismatch` — a documentation status token differs lexically from the code-side signal it claims to describe. Emittable only once the status-token and code-side-signal lists are defined (see `02-V0.8-PLAN.md` section 7b); until then it MUST NOT be emitted.
- Absence from a partial scan is never proof of global absence, and absence of lexical evidence is never proof that a defect exists (DEC-022/DEC-028).

Consistent references (DEC-024): when a documentation token and its code-side counterpart match exactly, that is a CONSISTENCY finding, not a gap or discrepancy, and MUST NOT be described as drift. Supporting consistency rows requires a row type the current fixed enums cannot express; this is an unresolved contract change (below), not something V0.8 may invent.

Unresolved contract change under consideration (DEC-024 — requires separate user approval; NOT approved):

- An existing enum value that legitimately represents a consistency finding does not exist: `stale_reference`, `missing_doc`, `conflicting_reference`, `status_mismatch` are drift categories; the `mcquest_ui_contract_audit` categories describe prop/usage drift; the `mcquest_find_ui_text` enum is a classification, not a finding. No value is added here.
- Because the row-type field is named "issue type", informational consistency rows also require a schema/naming decision.
- Until approved: consistency rows are NOT emitted, and this capability MUST NOT be treated as implementation-ready merely because it emits nothing.
- If approved later, the mechanics are: row identity = one row per (feature token, documentation file) pair; deduplication = repeated occurrences of the same pair collapse to a single row; deterministic sort key = `(docs relative_path ASC, doc line ASC, code relative_path ASC)`; budget participation = consistency rows count toward the same `total`/`returned`/budget accounting as every other row (paged and clipped identically).

Completeness (DEC-016; bounded-scan parameters DEC-033): capped-scan model — `collection_complete=false` with an explanatory NOTE when the scan scope is capped. Bounded-scan limits (adopting the established `mcquest_component_inventory` convention; no new indexing mechanism): `MAX_ENUMERATE_FILES = 2000` and `MAX_FILES_ANALYZED = 500`. `total` counts findings produced within the bounded scan only; it does not claim to be a global repository-wide total when the scan was capped. When the enumeration or analysis cap prevents complete collection inspection, `collection_complete=false`, the approved incomplete-collection NOTE is emitted, and the documented continuation information (`next_offset`/`has_more`) is provided. When the bounded scan completes without hitting a cap, `collection_complete=true` and no incomplete-collection NOTE is emitted merely because the tool is conceptually bounded. No automatic page 2 is rendered. `collection_complete` (the bounded collection was fully examined) and `truncated` (output rendering hit the presentation/ceiling budget) remain separate signals and are never conflated (DEC-028). A capped scan may report a `critical` finding only when the evidence independently establishes that specific claim; any claim that logically depends on complete coverage requires complete coverage (DEC-022/DEC-028).

Output:

- doc file / code file
- issue type (enum above)
- severity (`info` | `warning` | `critical`; heuristic label — DEC-017; rules in section 4)
- confidence (`low` | `medium` | `high`; heuristic label — DEC-025)
- explanation
- evidence line references
- supporting evidence row, required for every emitted severity and confidence label
- `risk` is NOT emitted by this tool; risk semantics are deferred (section 4 / DEC-025)

Safety:

- read-only
- no auto-document change

## 3. Core Output Rules

All V0.8 tools must follow the same evidence contract (binding per P014):

- `[SUMMARY]` section
- `tool:` and `scope:` metadata
- `total`, `returned`, `max_results`, `offset`, `next_offset`, `has_more`, `truncated`, `collection_complete`, `budget` fields per P014 (V0.7 P004/P005 semantics: `collection_complete=true` means the total is known, NOT that every item was delivered)
- `[EVIDENCE]` section
- precise file/line references
- per-tool deterministic sort key (pinned in `04-V0.8-TEST-PLAN.md` §2.3)
- truthful completeness reporting
- a `severity` field (`info` | `warning` | `critical`) on the analytical-review tools `mcquest_ui_contract_audit` and `mcquest_doc_gap_audit` only, always labeled as a heuristic (DEC-017)
- a `confidence` field (`low` | `medium` | `high`) wherever a classification, issue category, or issue type is emitted, decided by evidence sufficiency and residual ambiguity and never by the number of repeated references (DEC-025)
- a `risk` field — DEFERRED; no V0.8 tool emits `risk` values (DEC-025)
- `mcquest_find_ui_text` emits `classification`, `confidence`, and `reason` when `classify=true` (the default; `classify=false` rows carry location and snippet only — DEC-032), and emits no `severity` and no `risk` (per its output list in section 2.1)
- stable summary metadata: `operation`, `query` or `pattern`, `path` or `scope`, `files_affected`, paging and completeness fields (P013)

Budget behavior at each limit (canonical — DEC-028):

- Per-line limit (<= 200 chars): every emitted line is clipped at 199 chars plus the `…` clip marker. The clip marker and the whole-output truncation marker are distinct and are asserted separately.
- Normal presentation budget (<= 4000 chars): a default call renders under the 4000-char presentation budget. Items are emitted atomically — an item that would cross the budget is dropped whole, never split mid-snippet.
- Absolute ceiling (<= 16000 chars): reached only through explicit expansion; the response never exceeds it.
- When the presentation budget or the ceiling omits content, the response sets `truncated=true` and appends `[OUTPUT TRUNCATED: N characters omitted]` with the exact omitted count.
- Continuation: the existing `search_block`-family architecture supports deterministic continuation, so an explicit `offset` is the only continuation mechanism. `next_offset` points past the last item actually delivered and `has_more` reports whether further items remain. No cursor token is promised and no automatic page 2 is rendered.
- Truncation and incomplete collection are separate signals: `truncated=true` means content was withheld by a budget; `collection_complete=false` means the underlying scan was not exhaustive. They are never conflated.

No tool may claim complete evidence when a response is partial, and no tool may present a partial collection as complete.

Evidence, analysis, and recommendation must be kept distinct (see §4 Severity and Risk Model). Recommendations are review checklists only and must never be presented as fact.

## 4. Severity and Risk Model

V0.8 distinguishes:

- `evidence` — what was observed (file/line references)
- `issue` — what looks inconsistent or risky
- `severity` — how urgent or important the issue appears
- `confidence` — how confident the classification is
- `recommendation` — a suggested next review step, not a forced action and not a fact claim

All severity and confidence labels are **heuristics** and must be explicitly labeled as such in every output; they are never presented as fact (DEC-017). No label may be emitted without its supporting evidence row. Severity, confidence, and risk are three separate dimensions and MUST NOT be derived from one another (DEC-025).

Label definitions (canonical; DEC-009 as refined by DEC-022/DEC-025; the mapping is asserted through fixtures in `04-V0.8-TEST-PLAN.md` section 2.7):

- severity `info` — informational observation; no immediate action implied
- severity `warning` — evidence shows a partial or likely inconsistency or drift; should be reviewed
- severity `critical` — a positively established, observable condition only, and always accompanied by its evidence row. `critical` is permitted ONLY when:
  - the specific claim is established by evidence that was actually read, AND
  - for any claim that logically depends on complete coverage (such as "all relevant call sites"), that complete coverage exists and every element of the claim is fully evaluable (DEC-022); a capped scan may report `critical` only when the evidence independently establishes that specific claim (DEC-022/DEC-028); AND
  - it is never inferred from vague high-impact judgement, and absence from a partial scan is never treated as proof of global absence (Df-13/DEC-022).
- confidence `high` — the rule's required references for the emitted label are all present, and no in-scope element of that row's evidence is non-literal, unresolved, or unreadable
- confidence `medium` — the rule for the emitted label is satisfied, but at least one in-scope element of the row's evidence is incomplete
- confidence `low` — the label holds only under a lexical assumption, or the row is `unverifiable`; requires human confirmation
- confidence MUST NOT be decided by the number of repeated or duplicated references (DEC-025). The former "supported by multiple exact references" wording is withdrawn.

Risk (DEC-025): risk is a PER-FINDING label, distinct from severity and confidence, and must never be read as confidence in the evidence. No defensible risk scale is defined in the accepted specification, so risk semantics are DEFERRED: no V0.8 tool may assign or emit a `risk` value until a separate decision defines the scale and its fixture expectations.

This distinction must be explicit in every V0.8 tool output schema, and every per-tool output list in section 2 must agree with section 3 and this section.

## 5. Client Interoperability Boundary

Cline-native `search` and `read_files` tools, and Cline's grouped activity summaries (e.g., a summary of multiple reads and searches), are client-side features generated from the client's own tool-call records. They are not MCP protocol features, and `search_block` is not a Cline API.

`search_block` is an existing server-side MCQuest formatter that standardizes bounded `[SUMMARY]` / `[EVIDENCE]` responses with totals, paging, truncation, and deterministic output. V0.8 must preserve it and must not attempt to reproduce client-side aggregation in the server.

V0.8 interoperability requirements are limited to:

- valid MCP tool registration and schemas
- structured, bounded result text
- explicit query/path/operation metadata where useful
- stable output for generic clients
- optional compatibility wrappers only after a demonstrated client need

V0.8 must not:

- claim that an MCQuest tool is a Cline-native tool
- depend on Cline-specific UI internals for correctness
- maintain cross-call activity counters in the MCP server
- replace `mcquest_search` or weaken its evidence contract merely to imitate native tool names

Compatibility wrappers (if ever approved) must remain read-only, preserve root confinement, and delegate to the existing implementation rather than duplicate search logic.

## 6. Scope Boundaries

The V0.8 audit layer is intentionally scoped to:

- UI text discovery
- UI contract drift
- doc drift review
- feature impact review

It is not a general-purpose replacement for all project management or agent orchestration.

The following remain out of scope unless a separate approval occurs:

- file editing
- document mutation
- semantic embeddings
- full feature lifecycle management
- full business-process bookkeeping
- any new search index, parser dependency, or broad-language expansion (DEC-019/P016)
- parser-grade re-authorization of previously rejected classes
- semantic or parser-grade UI classification (reserved Phase 3 lane; DEC-015)
- `mcquest_audit_summary` — deferred (DEC-011; confirmed 2026-09-20); not part of the V0.8 tool set (see `08-V0.8-CONSOLIDATED-COVERAGE.md` §4)
- AI-generated recommendations presented as fact without evidence
- any write-enabled or document-correction authority (all V0.8 tools are read-only)
- JSX text-node extraction (not covered by the approved primitive — DEC-026, section 2.1)
- brand filtering via `include_brand` (deferred — DEC-026, section 2.1)
- emitting the `localizable` or `brand` classification, the `missing_doc` or `conflicting_reference` issue type, or a `risk` value (no evidence rule, token list, obligation source, lexical contradiction rule, or risk scale is recorded — DEC-025/DEC-026/DEC-030/DEC-032/DEC-033)
- consistency rows (row type not approved — DEC-024)
- implementing the `feature_scope` input (undefined — DEC-030)
