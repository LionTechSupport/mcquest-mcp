# MCQuest MCP v0.8 — Plan

> STATUS: **V0.8 ACTIVE DEVELOPMENT SPECIFICATION (APPROVED 2026-09-20)**
>
> This document describes the consolidated V0.8 extension layer, incorporating ALL substantive proposals of the retired predecessor package per the 2026-09-20 user instruction (consolidated coverage record: `08-V0.8-CONSOLIDATED-COVERAGE.md`). It is a planning artifact only; implementation begins only after explicit Phase 3 authorization (DEC-021).

---

## 1. Planning Objective

V0.8 is intended to expand MCQuest MCP beyond raw repository evidence into a focused audit layer that helps with:

- app-facing text discovery
- UI contract drift detection
- doc-to-code inconsistencies
- feature-impact review

This work is intentionally incremental and not a broad rewrite of the MCP platform.

---

## 2. Proposed Order of Work

### Phase A — Specification only

- define exact scope of each new tool (four new standalone audit tools; reuse of shared internals per DEC-019)
- define output contract (completing the evidence contract with the severity/risk field, summary metadata, and P014 binding semantics)
- define severity/risk model and confidence labels (heuristic labels, definitions in `01-V0.8-CONTRACT.md` §4; fixture-based mapping rules in `04-V0.8-TEST-PLAN.md` §2.7)
- define safety and boundedness rules
- adopt numerical limits and budgets as binding (DEC-013: 4000/16000/200, explicit pagination only, deterministic ordering, root confinement, P004/P005 semantics)
- define file-type boundaries per tool (DEC-019)
- define per-tool completeness models, issue/classification enums, and sorted evidence ordering (DEC-016/DEC-018)
- define acceptance criteria
- define required tests (`04-V0.8-TEST-PLAN.md`)

### Phase B — Implementation authorization (only after approval)

- create tool implementations under the existing tool layout
- add registration and discoverability tests (expected registered tool count: 20 → 24; `tests/test_registration.py`'s `EXPECTED_TOOLS` is updated accordingly, DEC-020)
- update `src/mcquest_mcp/server.py` instructions to describe the four new audit tools and extend discoverability assertions per the `tests/test_discoverability.py` pattern (DEC-020)
- validate read-only behavior
- verify output budget compliance
- verify tool descriptions and naming consistency (no Cline-native claims)

### Phase C — Follow-up refinement

- tune heuristics for UI text detection
- tune contract-audit severity levels
- tune doc-gap detection logic
- tune impact review scope and output

Constraint (DEC-028/DEC-029 traceability): Phase C may adjust thresholds, ordering, and noise suppression only. It MUST NOT change an approved evidence→severity/confidence mapping (DEC-017) or an approved lexical evidence rule (DEC-018/DEC-022…DEC-026) without revised fixtures covering the affected mapping/rule and an explicit, recorded user decision. Such a change is a specification revision, not tuning.

### Phase D — Client interoperability validation

- verify that MCP clients discover the V0.8 tools through MCP
- verify that search results remain useful under generic MCP rendering
- verify that query, path, totals, and continuation metadata survive presentation
- explicitly document that grouped native activity summaries remain client-owned

## 3. Proposed Tool Set

### 3.1 `mcquest_find_ui_text`

Focus:

- quoted string and template-literal candidate detection in TS/TSX/JS/JSX (JSX text nodes are NOT covered — DEC-026)
- localization candidate generation
- classification per DEC-032: `decorative` (no ASCII letter) and `unknown` (letter-bearing, while the brand-token and admin-marker lists are unrecorded) are emittable; `localizable`, `brand`, and `admin-only` are not emittable until their evidence rules/lists are recorded (DEC-026/DEC-032)

### 3.2 `mcquest_ui_contract_audit`

Focus:

- detection of component drift and broken shared interfaces
- issue reporting with evidence paths and affected call sites

### 3.3 `mcquest_doc_gap_audit`

Focus:

- mismatch between docs and implementation
- stale references and missing feature documentation
- `stale_reference` evidence carriers are inline backtick-span content and path-like tokens with a recognized extension; prose identifiers are never candidates by identifier shape alone (DEC-033). `missing_doc`, `conflicting_reference` (no lexical contradiction evidence rule — DEC-033), and `status_mismatch` remain NOT EMITTABLE; bounded-scan limits and `total` semantics follow DEC-033 (`MAX_ENUMERATE_FILES = 2000`, `MAX_FILES_ANALYZED = 500`; `total` counts findings within the bounded scan only).

### 3.4 `mcquest_feature_impact_audit`

Focus:

- feature references across code/docs/locales
- review checklist for change impact
- `include_docs`/`include_locales` optional booleans defaulting to `true` (DEC-034); bounded-scan limits `MAX_ENUMERATE_FILES = 2000` / `MAX_FILES_ANALYZED = 500` (DEC-035)

## 4. Scope Guardrails

The following are explicitly not part of V0.8 unless separately approved:

- parser-grade re-authorization of a previously rejected analysis class
- feature lifecycle management beyond audit and review
- write-enabled project tools
- automatic commit/push workflows
- general-purpose project ops automation

## 7. Design Choices — Decided by the 2026-09-20 Fix Pass (D1–D7)

The previously open design questions were resolved by user decisions D1–D7 on 2026-09-20 (docs-only; recorded in `05-V0.8-DECISIONS.md` DEC-015…DEC-020):

- `mcquest_find_ui_text` — a separate, narrow tool; lexical-only UI-candidate detection and classification; parser-grade and semantic UI classification remain RESERVED (DEC-015).
- `mcquest_ui_contract_audit` — strictly lexical; parser-grade approaches require a separate later approval (DEC-018).
- `mcquest_doc_gap_audit` — one scan with the fixed issue-type enum `stale_reference` | `missing_doc` | `conflicting_reference` | `status_mismatch` and documented lexical evidence rules (DEC-018).
- `mcquest_feature_impact_audit` — single-scan only, composing existing primitives; comparison-mode deferred (DEC-019).
- Tool output — evidence-first; labeled summary/severity views; recommendations limited to review checklists; all labels are heuristics, never facts (DEC-017).
- Budgets — 4000/16000/200, explicit pagination only, deterministic ordering, root confinement, P004/P005 semantics adopted as binding (DEC-013).
- `mcquest_audit_summary` — deferred (out of scope; DEC-011; confirmed 2026-09-20).
- Cline compatibility wrappers — deferred pending demonstrated client need (DEC-012).

The consolidated specification was **approved by the user on 2026-09-20** (DEC-021); these decisions do not by themselves authorize implementation. Implementation begins only after Phase 1 coverage verification and Phase 2 predecessor-package removal (both complete) and explicit Phase 3 authorization.

## 7b. Readiness-Baseline Resolution and Open Items (2026-09-20, docs-only)

Resolved by the readiness-baseline and post-readiness revisions (canonical rule text in `01-V0.8-CONTRACT.md`; decision records in `05-V0.8-DECISIONS.md` DEC-022…DEC-031):

- Missing-required-prop findings: `critical` requires a complete, fully evaluable all-sites claim; partial omission is `warning`; incomplete/unevaluable coverage is never `critical` (DEC-022).
- `stale_prop`: `warning` only against a fully available definition; otherwise `unverifiable` (DEC-023).
- Consistent documentation references: informational finding; one row per (feature token, doc file) pair; requires a new row type that no existing fixed enum provides — this remains an unresolved contract change (DEC-024) and is NOT approved.
- Risk: per finding; scale is deferred, so no V0.8 tool emits `risk` (DEC-025).
- Confidence: evidence sufficiency and ambiguity, never reference counts (DEC-025).
- Text extraction: comments and JSX text nodes are out of scope (verified against the approved primitive); `include_brand` removed and deferred; `brand`/`missing_doc` not emittable; fenced doc token rules defined (DEC-026).
- Path/error behavior: deterministic rejection table, no empty-result masquerade (DEC-027).
- Budgets/continuation/truncation: preserved limits; budget-cut semantics; explicit `offset` only; `truncated` and `collection_complete` kept separate; `doc_gap_audit` sort key pinned (DEC-028).
- Canonical ownership: `01-V0.8-CONTRACT.md` is canonical for rule text (DEC-029).
- `feature_scope` and missing artifacts are recorded as blockers (DEC-030).
- Severity mappings: `mismatched_usage` and `signature_drift` are `warning`, with fixture phenotypes recorded in `04-V0.8-TEST-PLAN.md` §2.7 (DEC-031).
- `include_admin` is removed from the `mcquest_find_ui_text` input contract and deferred while `admin-only` is non-emittable (DEC-031).
- `mcquest_find_ui_text` completeness (full-scan two-pass) is stated in the canonical contract §2.1 (DEC-031/DEC-016).
- `mcquest_find_ui_text` classification rules and `classify` semantics are recorded (DEC-032): emittable labels are `decorative` (no ASCII letter) and `unknown` (letter-bearing; reason names the missing brand-token and admin-marker lists); `localizable`, `brand`, and `admin-only` stay NOT EMITTABLE and `localizable` is never inferred by elimination; `classify` defaults to `true`, and `classify=false` rows carry location and snippet only.
- `mcquest_doc_gap_audit` evidence and bounded-scan rules are recorded (DEC-033): `stale_reference` carriers are inline backtick-span content and path-like tokens with a recognized extension (identifier form is a tokenizer within carriers, never a standalone carrier over prose); `conflicting_reference` is NOT EMITTABLE until a lexical contradiction evidence rule and its severity/confidence mapping are recorded; bounded-scan limits are `MAX_ENUMERATE_FILES = 2000` / `MAX_FILES_ANALYZED = 500` (no new indexing), `total` counts findings within the bounded scan only, and `collection_complete`/`truncated` remain separate signals with the NOTE only when a cap is actually hit.
- `mcquest_feature_impact_audit` boolean defaults and bounded-scan limits are recorded (DEC-034/DEC-035): `include_docs`/`include_locales` default to `true` (no new output fields/enums/classifications), `MAX_ENUMERATE_FILES = 2000` / `MAX_FILES_ANALYZED = 500` under the DEC-016/DEC-028 capped-scan model, `total` counts findings within the bounded scan only, `collection_complete`/`truncated` stay separate, pagination stays explicit via `offset`, and the pinned `(relative_path ASC, line ASC)` ordering is unchanged (no separate code/document/locale caps and no change to any other V0.8 tool's bounded-scan model).
