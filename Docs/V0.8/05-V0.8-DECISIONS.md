## DEC-009 — Severity/risk and confidence model

Status: **approved** (2026-09-20 fix pass, decision D4; refined by DEC-017; risk and confidence semantics clarified by DEC-025)

Decision:

Adopt the evidence / issue / severity / recommendation distinction from the predecessor package, with labels: severity `info` / `warning` / `critical`; confidence `low` / `medium` / `high`. All labels are heuristics, explicitly labeled as such in every output, and are never presented as facts. Fixture-based evidence→label mapping rules are required before implementation (see `04-V0.8-TEST-PLAN.md` §2.7). Definitions are recorded in `01-V0.8-CONTRACT.md` §4.

Clarification (2026-09-20, DEC-025): this decision never defined a `risk` label scale — the values `low`/`medium`/`high` above belong to `confidence` only. No defensible risk scale exists in the accepted specification, so risk semantics are deferred (DEC-025), and confidence is decided by evidence sufficiency and ambiguity, never by reference counts (DEC-025).

## DEC-022 — Required-prop findings and scan completeness

Status: **approved** (2026-09-20 readiness-baseline revision, docs-only; user-approved direction)

Decision:

- `critical` is permitted for a missing-required-prop finding only when all relevant call sites are accounted for in a complete scan AND every such call site is missing the required prop AND every such call site is fully evaluable.
- If only some relevant call sites are missing the prop, the finding is `warning`.
- If the scan is incomplete, relevant call sites are unevaluable, or coverage cannot support an all-sites claim, no `critical` finding is emitted on the basis of that all-sites claim.
- Terminology is pinned in `01-V0.8-CONTRACT.md` §2.2: "relevant call site" (in-scope lexical call/reference of the component name), "accounted for" (enumerated and read), "fully evaluable" (lexically complete argument list).
- A merely unobserved call site is never treated as a verified missing-prop violation. Absence of lexical evidence is never proof of a defect.
- A capped scan may report `critical` only when the evidence independently establishes that specific claim; any claim that logically depends on complete coverage requires complete coverage. Finding severity and scan completeness are separate dimensions.
- Effect: refines DEC-018's `missing_prop` rule (recording, not history rewrite) and the severity `critical` definition in `01-V0.8-CONTRACT.md` §4.

## DEC-023 — `stale_prop` evidence requirement

Status: **approved** (2026-09-20 readiness-baseline revision, docs-only; user-approved direction)

Decision:

- `stale_prop` is reported with severity `warning` only when an in-scope component definition is fully available and the supplied prop is demonstrably not declared by that definition.
- "Fully available definition" requires all of: exactly one in-scope definition site for the component name; a lexically enumerable declared prop-key set (no spread/rest element); and a definition file readable within `MAX_FILE_BYTES` and not on an ignored path.
- If the definition is unavailable, partial, ambiguous, or duplicated across definition sites, a verified `stale_prop` must not be asserted; `unverifiable` is reported instead.
- Unresolved cases are never silently classified as verified stale props.
- Effect: defines the missing evidence rule for the DEC-018 `stale_prop` value in `01-V0.8-CONTRACT.md` §2.2.

## DEC-024 — Consistent documentation references

Status: **approved** (2026-09-20 readiness-baseline revision, docs-only; user-approved direction; the supporting row type is NOT approved and remains an unresolved contract change)

Decision:

- When a documentation token and its code-side counterpart match exactly, that is a consistency finding, not a gap or discrepancy, and must not be described as drift.
- Preference: one row per (feature token, documentation file) pair, not one row per repeated occurrence.
- No existing enum value legitimately represents a consistency finding (`stale_reference`, `missing_doc`, `conflicting_reference`, `status_mismatch` are drift categories; the `mcquest_ui_contract_audit` categories are prop/usage drift; the `mcquest_find_ui_text` enum is a classification). No value is invented here.
- Because the row-type field is named "issue type", consistency rows would also require a schema/naming decision.
- Required contract change (if ultimately approved): a new row type for consistency findings, row identity = one row per (feature token, documentation file) pair, deduplication to a single row per pair, deterministic sort key `(docs relative_path ASC, doc line ASC, code relative_path ASC)`, and budget participation identical to every other row.
- Until a separate user approval records that change, consistency rows are NOT emitted and must NOT be treated as implementation-ready merely because they emit nothing.

## DEC-025 — Risk and confidence semantics

Status: **approved** (2026-09-20 readiness-baseline revision, docs-only; user-approved direction)

Decision:

- Risk is per finding, not response-level.

- Effect: clarifies DEC-009's risk/confidence semantics without rewriting its history.

## DEC-026 — Text extraction boundaries

Status: **approved** (2026-09-20 readiness-baseline revision, docs-only; user-approved direction)

Decision:

Comments:

- No comment extractor is added.
- Comments are not a candidate source. The approved primitive (`src/mcquest_mcp/tools/strings.py`) has no comment awareness, so quoted literals appearing on comment lines may incidentally be returned; this is a documented lexical limitation, not comment support.

Documentation tokens (`mcquest_doc_gap_audit`):

- Eligible location: an in-scope Markdown line outside a fenced code block.
- Lexical token recognition only (word-boundary identifiers, backtick-delimited spans, path-like tokens with a recognized extension); no Markdown parser.
- Fenced code blocks are excluded by default; fence recognition is a lexical line-state scan (three or more backticks or tildes as first non-whitespace characters); language tags are ignored.
- Unterminated fence: all lines after the opening fence are excluded and the condition is reported through the completeness NOTE, never as a finding.
- These rules are testable through fixtures (`04-V0.8-TEST-PLAN.md` §2.7).

JSX text nodes:

- JSX text nodes are included only if the currently approved primitives demonstrably extract them. Verified: they do NOT (the scanner handles `'`, `"`, and backtick delimiters only). Therefore JSX text nodes are OUT OF SCOPE and must be documented as a limitation, distinct from attribute string values and quoted/template literals, which remain in scope.
- No new JSX extractor is added.

Brand filtering:

- `include_brand` is not retained as a documented no-op. It is REMOVED from the `mcquest_find_ui_text` input contract and the filter is DEFERRED.
- No brand-token list or owner is invented; a list may be established only from authoritative project documentation.
- The `brand` classification remains in the fixed enum (DEC-018) but is NOT EMITTABLE until a token list and owner are recorded; otherwise-brand literals are reported as `unknown` with a reason naming the missing token list.
- `admin-only` (classification) and `status_mismatch` (issue type) are likewise NOT EMITTABLE until their marker/status lists are recorded (see `02-V0.8-PLAN.md` §7b).
- Filters suppress rows only; they never change a row's classification value.

## DEC-028 — Budgets, truncation, ordering, and completeness

Status: **approved** (2026-09-20 readiness-baseline revision, docs-only; user-approved direction; preserves DEC-013/DEC-016)

Decision:

- The approved numeric limits are preserved unchanged: normal ≤ 4000 chars, ceiling ≤ 16000 chars, per-line clip ≤ 200 chars.
- Behavior at each limit is defined: per-line clip at 199 chars + the `…` marker (distinct from the whole-output `[OUTPUT TRUNCATED: N characters omitted]` marker); atomic item emission under the presentation budget (an item that would cross the budget is dropped whole); the ceiling is never exceeded; `truncated=true` and the exact omitted count are reported when content is omitted.
- Deterministic ordering is preserved; the `mcquest_doc_gap_audit` sort key is pinned as `(docs relative_path ASC, doc line ASC, code relative_path ASC)` to remove the ambiguity between doc line and code line.
- Continuation: the existing `search_block` architecture supports deterministic continuation, so an explicit `offset` is the only continuation mechanism; `next_offset` points past the last item actually delivered; no cursor and no automatic page 2 are promised.
- Truncation (`truncated=true` = content withheld by a budget) and incomplete collection (`collection_complete=false` = scan not exhaustive) are separate signals and are never conflated. A partial collection is never presented as complete.
- Canonical wording: `01-V0.8-CONTRACT.md` §3; asserted in `04-V0.8-TEST-PLAN.md` §2.3.

## DEC-032 — `mcquest_find_ui_text` classification rules and `classify` semantics

Status: **approved** (2026-09-20 revision; user-approved direction; resolves the two implementation blockers reported against `01-V0.8-CONTRACT.md` §2.1 — no recorded lexical rule for `localizable`, and unspecified `classify` default/false-mode)

Decision:

- Letter-absence rule: a candidate literal containing no ASCII letter matching `[A-Za-z]` is classified `decorative`. This branch is emittable.
- Unresolved-list rule: a candidate literal containing one or more ASCII letters is classified `unknown` while the required brand-token list and admin-marker list remain unrecorded (§7b of `02-V0.8-PLAN.md`). The `reason` for an `unknown` row MUST identify the missing brand-token list and admin-marker list as the unresolved evidence.
- Non-emittable labels: `localizable`, `brand`, and `admin-only` are NOT EMITTABLE in the current V0.8 implementation until their required evidence rules/lists are formally recorded. `brand` remains gated by DEC-026 (no token list or owner) and `admin-only` by its unrecorded marker list; `localizable` has no recorded evidence rule and is never inferred by elimination. All three remain in the fixed enum (DEC-018 unchanged) and MUST NOT be emitted.
- `classify` semantics: `classify` defaults to `true`. When `classify=false`, each result row contains only the location (`file:line`) and snippet; `classification`, `confidence`, and `reason` are omitted. The summary block is unchanged. The output schema is otherwise unchanged; no enum value is added or removed and no schema expansion is introduced.
- Confidence mapping (per `01-V0.8-CONTRACT.md` §4): `decorative` rows carry `high` (determinate lexical evidence; no unresolved element); `unknown` rows carry `medium` (the label reflects recorded state whose defining evidence — the two lists — is unresolved).
- Canonical rule text: `01-V0.8-CONTRACT.md` §2.1 (with §3 and §6 aligned); fixture phenotypes (documented expectations only; no fixture files created): `04-V0.8-TEST-PLAN.md` §2.4/§2.5/§2.7; plan alignment: `02-V0.8-PLAN.md` §3.1/§7b.

## DEC-033 — `mcquest_doc_gap_audit` evidence carriers, `conflicting_reference` gate, and bounded-scan parameters

Status: **approved** (2026-09-20 docs-only revision; user-approved direction; resolves the implementation blockers reported against `01-V0.8-CONTRACT.md` §2.3 — no lexical definition for the `stale_reference` predicate, no lawful evidence path for `conflicting_reference`, and undocumented capped-scan parameters)

Decision:

### A. `stale_reference` evidence carriers

- Eligible documentation evidence carriers are **exactly** (a) the content of a backtick-delimited inline Markdown span, and (b) a path-like token containing `/` with a recognized source or documentation extension.
- The identifier-token form `[A-Za-z_][A-Za-z0-9_]*` is a **tokenizer/evidence-extraction rule applied within those eligible carriers**. It is NOT a standalone carrier over arbitrary Markdown prose.
- Consequently ordinary prose words (`the`, `tool`, `returns`, `This`, …) are not treated as code-reference candidates merely because they match the identifier shape, and bare prose identifiers are not sufficient evidence for `stale_reference`.
- No semantic symbol resolution is attempted and no maintained symbol list is introduced.
- This is an honesty boundary under DEC-022: absence of lexical evidence is not proof of a stale reference.

### B. `conflicting_reference` is NOT EMITTABLE

- No contradiction vocabulary, marker list, semantic inference rule, or natural-language contradiction detector is invented.
- `conflicting_reference` is **NOT EMITTABLE** in V0.8 and no `conflicting_reference` row may be emitted by `mcquest_doc_gap_audit`.
- It remains in the fixed enum (DEC-018 unchanged); no enum value is added or removed, and the public schema is unchanged.
- **Reconsideration condition:** a future decision must define the lexical contradiction evidence rule (its marker/evidence vocabulary) and its severity/confidence mapping before the category becomes emittable. This follows the same evidence-discipline as the other V0.8 categories whose required evidence source is not currently recorded (`missing_doc` DEC-030; `status_mismatch` DEC-026).

### C. Capped-scan parameters and `total` semantics

- `mcquest_doc_gap_audit` adopts the established `mcquest_component_inventory` bounded-scan convention: `MAX_ENUMERATE_FILES = 2000` and `MAX_FILES_ANALYZED = 500`. No new indexing mechanism is created.
- `total` counts findings produced **within the bounded scan only**; it does not claim to be a global repository-wide total when the scan was capped.
- The existing V0.8 distinction between `collection_complete` (whether the bounded collection was fully examined) and `truncated` (whether output rendering hit the presentation/ceiling budget) is preserved; they are never conflated (DEC-028).
- When the enumeration or analysis cap prevents complete collection inspection: `collection_complete=false`, the approved incomplete-collection NOTE is emitted, and the documented continuation information (`next_offset`/`has_more`) is provided.
- When the bounded scan completes without hitting a cap: `collection_complete=true`, and no incomplete-collection NOTE is emitted merely because the tool is conceptually bounded.
- No automatic page-2 behavior is invented; explicit `offset` remains the only continuation mechanism (DEC-028).

### D. Fixture phenotypes

- Fixture phenotypes for `stale_reference` (eligible backtick/path-like documentation token absent from the bounded code scan) and the explicitly non-emitting status of `conflicting_reference` are recorded as documented expectations only in `04-V0.8-TEST-PLAN.md` §2.7; no fixture files are created by this decision. A prose-identifier phenotype demonstrates that arbitrary Markdown prose does not become a `stale_reference` candidate solely because it matches `[A-Za-z_][A-Za-z0-9_]*`.

### E. Canonical locations and scope

- Canonical rule text: `01-V0.8-CONTRACT.md` §2.3 (carriers, evidence rules, `conflicting_reference` gate, bounded-scan completeness/`total`); `04-V0.8-TEST-PLAN.md` §2.3/§2.4/§2.7 (assertions and fixture phenotypes); `02-V0.8-PLAN.md` §3.3/§7b; traceability in `00`, `03`, `06`, `07`, `08`.
- No enum value is added or removed; no schema/API expansion; the four-tool scope is unchanged.
- This decision authorizes **documentation only**. It does not authorize implementation of `mcquest_doc_gap_audit` (or `mcquest_feature_impact_audit`), test authoring or execution, commit, or push.
