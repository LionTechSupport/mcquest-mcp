## 1. Purpose and Scope

This plan defines the test scope for the consolidated V0.8 audit layer (four tools):

- `mcquest_find_ui_text`
- `mcquest_ui_contract_audit`
- `mcquest_doc_gap_audit`
- `mcquest_feature_impact_audit`

Tests follow the same discipline as earlier phases: registration and discoverability tests, behavioral evidence tests, read-only and invariant tests, and budget-compliance tests. The plan is written against the contracts in `01-V0.8-CONTRACT.md` and the plans in `02-V0.8-PLAN.md`.

## 2. Test Areas

### 2.1 Registration and discoverability

- Registration is additive: the expected registered tool count is **24** (20 existing + 4 new); `tests/test_registration.py`'s `EXPECTED_TOOLS` is updated accordingly (DEC-020).
- Each new tool is registered and exported from the existing tool layout (`src/mcquest_mcp/tools/`).
- Each tool has a name, description, and declared parameter schema consistent with the contract.
- Tool descriptions do not claim Cline-native status and do not reference client-specific internals.
- `src/mcquest_mcp/server.py` instructions are updated to describe the four audit tools, and discoverability assertions are extended (matching the `tests/test_discoverability.py` pattern) (DEC-020).

### 2.2 Read-only and invariant behavior (binding per P014/P016)

- Root confinement: inputs outside the project root are REJECTED (DEC-027), never silently confined, and never reported as an empty result.
- Error behavior per `01-V0.8-CONTRACT.md` section 2.0: nonexistent path (`FileNotFoundError`), unsupported file type / outside-root / ignored directory / unreadable / oversized (`ValueError`); a zero-row response means "no match in the scanned scope", never "input rejected". Asserted directly (new section 2.8).
- No writes: no tool call mutates the target repository.
- No code execution: no tool executes project code.
- No cross-call state: no tool maintains session-level activity counters.
- No `_meta`, no file-backed response artifacts, no `format=json`.
- No new index, parser dependency, embedding surface, or broad-language expansion (P016/DEC-019). Objective verification: each new tool module's imports are asserted against the recorded import allowlist (see section 2.8). NOTE: that allowlist artifact does not exist yet (DEC-030), so this test area is BLOCKED until the allowlist is recorded; the tools themselves are not blocked.

### 2.3 Budgets, truncation, ordering, and completeness (binding — DEC-013/P014)

- normal presentation budget ≤ 4000 characters
- absolute response ceiling ≤ 16000 characters
- per-line clip ≤ 200 characters (first 199 chars + `…`) — the per-line ellipsis is the clip marker; the whole-output truncation marker is `[OUTPUT TRUNCATED: N characters omitted]`; the two are asserted separately
- explicit pagination only (no automatic page 2)
- per-tool deterministic sort keys (DEC-018):
  - `mcquest_find_ui_text`: `(relative_path ASC, line ASC, col ASC)`
  - `mcquest_ui_contract_audit`: `(relative_path ASC, line ASC)`
  - `mcquest_doc_gap_audit`: `(docs relative_path ASC, doc line ASC, code relative_path ASC)` (pinned by DEC-028; "line" is the DOC line, then the code path)
  - `mcquest_feature_impact_audit`: `(relative_path ASC, line ASC)`
- V0.7 P004/P005 completeness semantics apply: `collection_complete=true` means the total is known (two-pass honest count), NOT that every item was delivered; `has_more=true` / `next_offset` are continuation signals
- per-tool completeness models (DEC-016):
  - `mcquest_find_ui_text`, `mcquest_ui_contract_audit`: full-scan two-pass, `collection_complete=true` always
  - `mcquest_doc_gap_audit`, `mcquest_feature_impact_audit`: capped-scan, `collection_complete=false` + explanatory NOTE when the scan scope is capped (mirrors `mcquest_component_inventory`)
- `mcquest_doc_gap_audit` bounded-scan parameters and `total` semantics (DEC-033): `MAX_ENUMERATE_FILES = 2000` and `MAX_FILES_ANALYZED = 500` (no new indexing mechanism); `total` counts findings produced within the bounded scan only and is never presented as a global repository-wide total when the scan was capped; `collection_complete=true` with no incomplete-collection NOTE when the bounded scan completes without hitting a cap; `collection_complete` and `truncated` remain separate signals (DEC-028); explicit `offset` remains the only continuation mechanism (no automatic page 2)
- `total`, `returned`, `max_results`, `offset`, `next_offset`, `has_more`, `truncated`, `budget` fields are present and truthful; `budget` follows the existing `"{presentation}/{ceiling}"` representation (e.g. `4000/16000`)
- cut behavior: when the presentation budget or the ceiling omits content, the response sets `truncated=true`, appends `[OUTPUT TRUNCATED: N characters omitted]` with the exact omitted count, and `next_offset` points past the last item actually delivered; `truncated` (budget cut) and `collection_complete=false` (non-exhaustive scan) are asserted as separate signals and are never conflated (DEC-028)

### 2.4 Per-tool behavioral tests

- `mcquest_find_ui_text`: returns candidate user-facing text in TS/TSX/JS/JSX only; candidates are quoted string literals and template-literal static segments (JSX text nodes and comments are NOT covered — DEC-026); filtering is `classify` (plus `file_pattern`) only; `include_admin` and `include_brand` are removed and deferred (DEC-026/DEC-031); every evidence row has file/line + a value from the fixed enum `localizable` | `brand` | `admin-only` | `decorative` | `unknown` (+ confidence/reason when classifying — `classify` defaults to `true`, DEC-032); classification follows the canonical DEC-032 rules: no ASCII letter (`[A-Za-z]`) → `decorative` (`high`), one or more ASCII letters → `unknown` (`medium`, reason naming the missing brand-token and admin-marker lists); `localizable`, `brand`, and `admin-only` are asserted as ABSENT from all output while their evidence rules/lists are unrecorded (DEC-032); fixtures prove the classification is lexical-only and never parser-assisted (D2/DEC-015).
- `mcquest_ui_contract_audit`: reports component evidence with caller usage, an issue category from `missing_prop` | `stale_prop` | `mismatched_usage` | `signature_drift` | `unverifiable`, severity, confidence, and supporting evidence; category and severity assignments are checked against the canonical rules in `01-V0.8-CONTRACT.md` section 2.2 (DEC-022/DEC-023/DEC-031); `unverifiable` is required for non-literal/spread call sites and for unavailable/partial/ambiguous definitions and is never `critical`; the tool reports `collection_complete=true` (full-scan two-pass — DEC-016/DEC-022); performs no edits.
- `mcquest_doc_gap_audit`: reports doc/code file pairs with an issue type from the fixed enum `stale_reference` | `missing_doc` | `conflicting_reference` | `status_mismatch`, plus severity, confidence, explanation, and evidence line references; the only currently EMITTABLE issue type is `stale_reference` (DEC-033), and each type is verified against the canonical rules in `01-V0.8-CONTRACT.md` section 2.3 (carrier rule, token boundary, and fence rules per DEC-026/DEC-033); `missing_doc` is asserted ABSENT until its obligation source is recorded (DEC-030); `conflicting_reference` is asserted ABSENT — no lexical contradiction evidence rule is recorded, so the category is deferred/non-emitting, not silently omitted (DEC-033); `status_mismatch` is asserted ABSENT until its status/marker lists are recorded (DEC-026); `stale_reference` evidence carriers are inline backtick-span content and path-like tokens with a recognized extension, and prose identifiers are asserted NOT to produce findings merely by matching `[A-Za-z_][A-Za-z0-9_]*` (DEC-033); fenced-block exclusion and unterminated-fence NOTE behavior are fixture-asserted; consistency rows are NOT emitted (DEC-024); performs no document changes.
- `mcquest_feature_impact_audit`: given a target, returns impacted files, affected docs, locale keys/references, reason, and a review checklist; no `severity` and no `risk` field appears in output (DEC-025); fixtures prove it composes existing primitives only (no new indexing); makes no changes.
- All tools: when the response is partial, they do not claim complete evidence.

### 2.5 Severity/risk and metadata

- `severity` (`info`/`warning`/`critical`) appears on `mcquest_ui_contract_audit` and `mcquest_doc_gap_audit` only, each explicitly labeled as a heuristic (DEC-017), and only with its supporting evidence row; severity assignments are checked against the canonical rules in `01-V0.8-CONTRACT.md` section 4 (DEC-022).
- `confidence` (`low`/`medium`/`high`) appears wherever a classification or issue/issue-type is emitted; fixtures assert the confidence is decided by evidence sufficiency and ambiguity, never by the number of repeated references (DEC-025).
- No V0.8 tool output contains a `risk` field (risk scale deferred — DEC-025).
- `mcquest_find_ui_text` output contains no `severity` and no `risk` field (per its output list in `01-V0.8-CONTRACT.md` section 2.1).
- `mcquest_find_ui_text` classification output carries `confidence` (`low`/`medium`/`high`) and `reason` when classifying (Df-7); `classify` defaults to `true`, and `classify=false` rows carry only the location and snippet with the summary unchanged (DEC-032).
- Summaries MUST expose stable metadata: `operation`, `query`/`pattern`, `path`/`scope`, `files_affected`, paging and completeness fields (P013).
- Recommendations appear only as review checklists and are not presented as facts.

### 2.6 Client presentation (Phase D) — manual/integration verification

The following are manual or integration-level verifications, NOT automated unit tests (Df-8):

- Verify generic MCP clients can discover the tools and render result text with useful labels.
- Verify query/path/totals/continuation metadata survive generic presentation.
- Verify grouped activity summaries are not produced by the server (in unit tests, this is asserted only as the absence of such fields).

Automated unit tests instead verify: valid MCP registration/schemas, structured bounded text, the stable metadata fields above, and that no Cline-native claims appear in descriptions.

### 2.7 Severity/confidence mapping fixtures (required before implementation — DEC-017)

- Before implementation, define fixture sets that map concrete evidence to each label value per tool, using the canonical rules in `01-V0.8-CONTRACT.md` sections 2.2/2.3/4 as the mapping authority (e.g., a two-line component fixture where every fully-evaluable call site omits a required prop → `missing_prop`, `critical`, confidence per DEC-025; one call site omitting while another supplies it → `warning`; a spread argument list → `unverifiable`).
- Represent fixture sets per phenotype: never-`critical` (partial omission), `unverifiable` (non-literal/spread), `stale_prop` (fully available definition), `mismatched_usage` (differing prop-key sets across fully evaluable call sites, no explaining definition → `warning`, DEC-031), `signature_drift` (definition prop-key list differs lexically from call-site prop keys → `warning`, DEC-031), fenced vs unfenced doc tokens, unterminated fence, brand-like literal (indistinguishable from any letter-bearing literal while the brand/admin lists are unrecorded; → `unknown` with reason — DEC-032), no-ASCII-letter literal (→ `decorative`, `high`, letter-absence reason — DEC-032), letter-bearing literal (→ `unknown`, `medium`, reason naming the missing brand-token and admin-marker lists — DEC-032), `classify=false` rows (location + snippet only; no `classification`/`confidence`/`reason` fields; summary unchanged — DEC-032), comment-line incidental literal, `stale_reference` (an eligible carrier token — inline backtick-span content or a path-like token with a recognized extension — whose referenced code symbol/location is absent from the bounded code scan → `stale_reference`, `warning`, confidence per DEC-025; DEC-033), ordinary-prose identifier (a bare Markdown prose word such as `returns` that matches `[A-Za-z_][A-Za-z0-9_]*` but is NOT inside an eligible carrier → NO `stale_reference` finding; prose alone is not evidence — DEC-033), and `conflicting_reference` (NON-EMITTABLE/deferred in V0.8 — no fixture may imply that it is currently emitted; DEC-033). Fixture files are not created by documentation; these are documented expectations only.
- Tests assert the fixture mapping is stable and that every `severity`/`confidence` emitted in any tool output is accompanied by the evidence row that supports it.
- No label may be emitted without its supporting evidence row.
- Non-emittable values (`localizable`, `brand`, `admin-only`, `missing_doc`, `conflicting_reference`, `status_mismatch`, `risk`, consistency rows) are asserted ABSENT from output until their item-specific decisions are recorded (DEC-032/DEC-033 included), and MUST NOT be considered implementation-ready merely because the fixtures assert their absence.

### 2.8 Input, path, and error behavior (binding — DEC-027)

Per the canonical table in `01-V0.8-CONTRACT.md` section 2.0, fixtures/assertions for each of the four tools:

- omitted/empty path and explicit project root → scan proceeds (respecting the tool's file-type boundary);
- in-root file path within the file-type boundary → accepted; unsupported file type → `ValueError`;
- in-root directory path → recursive scan;
- nonexistent path → `FileNotFoundError`;
- path outside the project root → `ValueError` (explicit rejection; never a silent empty result);
- ignored directory → `ValueError`; unreadable/oversized file → `ValueError`;
- invalid input is never reported as an empty result set: a zero-row response means "no match in the scanned scope";
- negative `offset` → `ValueError`; `max_results` clamped to 1–500.

Primitive-composition test area (P016/DEC-019): assert each new tool module imports only from the recorded import allowlist. BLOCKER for this test area only: the import-allowlist artifact does not exist yet (DEC-030); it must be created and recorded before this assertion can be written. Do not fabricate the allowlist.

## 3. File-Type Boundaries (binding — DEC-019)

- `mcquest_find_ui_text`, `mcquest_ui_contract_audit`: `.js`, `.jsx`, `.ts`, `.tsx` only.
- `mcquest_doc_gap_audit`: docs side = Markdown (`.md`, `.markdown`, `.mdown`, `.mkd`); code side = the existing supported code set (`.js`, `.jsx`, `.ts`, `.tsx`). No broader-language expansion.
- `mcquest_feature_impact_audit`: union of the above plus locale `.json` files for key lookups, composing existing primitives only (no new indexing).
- Tests must assert that out-of-scope extensions are not scanned (root-bounded behavior).
