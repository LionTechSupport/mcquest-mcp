# MCQuest MCP v0.9 — Architecture

> STATUS: **P0 — APPROVED IMPLEMENTATION DESIGN (NOT BUILT)**
>
> Implementation status: **NOT STARTED**. No directory, module, class, or tool described here exists
> in the repository. This document is the design the future phases must implement.

---

## 1. Design principles

1. **Observe once, remember explicitly, validate before execution, invalidate when necessary, never
   repeat work without a reason.**
2. Analysis is separate from execution: Cline remains the execution authority.
3. Small modules, explicit state, deterministic behavior, testable pure functions.
4. No hidden global state; the only shared state is the in-memory store, keyed by
   `(session, process)` and scope.
5. Heuristics are labeled as heuristics; nothing is asserted beyond the analyzer's capability.
6. The server's own process facts are never presented as the client's terminal facts.

```text
facts.py                     (no internal deps)
  ▲
  ├── store.py               (facts)
  │     ▲
  │     └── invalidate.py    (store, facts)
  │
  ├── environment.py         (facts, store)
  ├── terminal.py            (facts, store)
  ├── capabilities.py        (facts only)
  ├── cost.py                (facts only)
  ├── operations.py          (facts only)
  ├── dialect.py             (facts only; pure text analysis)
  ├── native.py              (facts only; pure text analysis)
  ├── parse.py               (facts only; pure text analysis)
  ├── encoding.py            (facts only; pure text analysis)
  ├── hazards.py             (facts, parse)
  ├── hygiene.py             (facts, dialect)
  ├── redundancy.py          (facts, store, dialect)
  ├── failures.py            (facts, store)
  └── validate.py            (all analyzers + store + invalidate + capabilities + cost)
        ▲
        └── tools/shell_env.py   (thin adapters; formatting.py for output)
```

Rules:

- `facts.py` depends on nothing internal and is the shared vocabulary.
- Analyzers are pure functions over text + facts; they never touch the filesystem or a subprocess.
- Only `environment.py` may invoke the approved probes (§15 of the contract), through the existing
  safe-probe template.
- `validate.py` is the only orchestrator; tools stay thin.
- No module may call into V0.8 tool implementations except through the already-public helpers listed
  in `02-V0.9-IMPLEMENTATION-AUDIT.md` §4.

## 4. Three state categories (never conflated)

| Category | Meaning | Examples | May be presented as the client's terminal state? |
| --- | --- | --- | --- |
| **server-observed** | the MCP server established it itself | project root, OS, Python, git facts for the root, executable availability, probe baselines | **No** — probe baselines are machine capabilities, not the client's shell |
| **client-declared** | the client told V0.9 | client CWD, session id, client process id, client shell version, client env vars | Yes, with `source: CLIENT_DECLARED` and its trust label shown |
| **unknown** | nobody established it | un-declared CWD, unknown shell version, unknown console code page | No — must be printed as `unknown` |

**Hard rule:** server-owned process state (the server's own CWD, PID, console code page, shell) is
recorded only under a labeled `mcp_server` subject and must **never** be emitted as Cline's terminal
state (decisions A2, S2).

## 5. Component specifications (1 of 3)

### 5.1 `facts.py`

Shared vocabulary. No internal dependencies.

- `Source` — `SERVER_OBSERVED | CLIENT_DECLARED | UNKNOWN` (frozen; no additions).
- `Trust` — `trusted | corroborated | untrusted | unknown` (frozen; no additions).
- `Scope` — `REPOSITORY | WORKTREE | FILE | SESSION | PROCESS | EPHEMERAL`.
  `FILE` applies only to tool-derived, path-anchored evidence (decision A14); the proposal's §10 set
  is otherwise preserved.
- `Freshness` — `STATIC | SESSION | WORKTREE | PROCESS | EPHEMERAL`.
- `Fact` record — `{name, value, source, trust, scope, freshness, subject, observed_at, evidence}`.
  `observed_at` is UTC ISO-8601 **provenance only**; it never triggers expiry (decision A5).
- `Observation` record — a `Fact` plus `observation_id`, `operation`, and origin (`tool` or
  `terminal_session`).
- All enums are stable strings so outputs remain byte-deterministic.

### 5.2 `store.py`

The single piece of shared state. In-memory only (decision A4). No filesystem access, ever.

- `ObservationStore` — keyed by scope + subject + name; supports `record`, `lookup`, `reuse_check`,
  `invalidate_scope`, `snapshot`, and `reset`.
- `CommandHistory` — ordered records `{command_id, text, normalized[], cost, mutation, operation,
  session, process, verdict}`; supports normalized-duplicate lookup and bounded paging.
- `reset()` exists explicitly so tests cannot leak state across cases.
- Lifetime is the server process. Nothing survives restart; restarts must be reported as `unknown`
  rather than assumed.

### 5.3 `invalidate.py`

Event → scope invalidation, with monotonic per-scope revisions.

| Event | Invalidates |
| --- | --- |
| file modified | `FILE` (matching path), `WORKTREE` content/search-dependent facts |
| file created/deleted | path existence, inventories |
| `Set-Location` / CWD change | `PROCESS` CWD facts for that session/process |
| git checkout / reset / pull / branch switch | `WORKTREE` git facts |
| dependency installation | `SESSION` executable/package facts |
| configuration change | corresponding observed facts |
| console code page change | encoding observations |
| new PowerShell process | that process's `PROCESS` facts |
| terminal restart | that session's `SESSION`/`PROCESS` facts |
| server restart | all `SESSION`/`PROCESS` facts (reported as unknown) |

- Each invalidation bumps a per-scope, per-subject `revision` counter.
- Reuse rule: an observation is reusable iff its scope matches, its `(session, process)` identity
  matches for `PROCESS`/`SESSION`/`EPHEMERAL` scopes, and no invalidation event has touched that
  scope/subject since it was recorded.
- **Invalidate rather than guess** (proposal §11).

### 5.4 `environment.py`

Assembles the Environment Contract (`01-V0.9-CONTRACT.md` §5) from store entries plus the approved
probes, labeling every field with source + trust. Degraded mode is a first-class output: when nothing
is declared it emits `CWD: unknown / source: UNKNOWN / trust: untrusted` plus the explicit-path
directive (decision S1).

### 5.5 `terminal.py`

Terminal/session/process identity without privileged access:

```text
session<id>  -> processes[]  -> {shell, version, cwd, console_codepage}
```

- Only client-declared values populate the client tree; server facts live under `mcp_server`.
- No fact promotion between session ids or process ids (decision A2 rule 2).
- Unknown fields render as `unknown`, never as a server value.

## 6. Component specifications (2 of 3)

### 6.1 `operations.py` — semantic operation classification

Intent is classified **before** any command is considered. Approved taxonomy (proposal §12):

```text
READ_FILE      READ_JSON       SEARCH_LITERAL   SEARCH_REGEX   ENUMERATE_FILES
CHECK_PATH     CHECK_GIT_STATE  CHECK_CONFIG     MEASURE_EOL    RUN_NODE
RUN_PYTHON     RUN_TEST         BUILD            INSTALL        EDIT
```

The classifier must distinguish structured data from plain text, filesystem state from Git state,
environment state, execution, and mutation. Example: inspecting `quiz.loading` in `en/si/ta` JSON
files is `READ_JSON`, not a text search.

### 6.2 `dialect.py` — shell dialect intelligence

Understands at least: PowerShell, CMD, native Windows executables, Node.js, Python, nested shells.

Rule table entries are tagged by baseline (decision A8):

| Construct | Tag | Verdict |
| --- | --- | --- |
| `>nul` / `>NUL` | both | CMD-style redirection in PowerShell → WARNING |
| `&&` / `||` chaining | `ps5.1` (unsupported) | WARNING under 5.1, PASS under 7 |
| ternary `? :` | `ps5.1` (unsupported) | WARNING under 5.1 |
| `??`, `??=` | `ps5.1` (unsupported) | WARNING under 5.1 |
| `-Parallel` | `ps5.1` (unsupported) | WARNING under 5.1 |

When the effective baseline is unknown, baseline-dependent rules emit **INFO, never WARNING**
(decision S6).

### 6.3 `native.py` — native command boundary analysis

Identifies where PowerShell hands control to a native executable with its own argument grammar,
quoting rules, wildcard behavior, redirection, and output encoding.

Example: `findstr /n /c:"loading" file.json` is not a purely PowerShell operation; PowerShell invokes
`findstr.exe`, whose own parser governs `/n`, `/c:`, quoting, and output. The analyzer flags the
boundary and its risks (quoting, escaping, wildcards, redirection, pipes, argument grammar, encoding,
error propagation) without pretending the two parsers are equivalent.

### 6.4 `parse.py` — bounded parse-completeness scanner

Deterministic lexical scanner with three frozen verdicts (decisions A6, S4):

```text
INCOMPLETE (DETECTED, heuristic)
NO INCOMPLETENESS DETECTED (heuristic — NOT proof of completeness)
UNDETERMINED (construct outside scanner capability)
```

The words *valid*, *complete*, and *proven* must never be emitted as a verdict.

**Can recognise:** unclosed `'…'`; unclosed `"…"` (accounting for the `` `" `` escape); unterminated
here-string (`@'`/`@"` without a line-initial `'@`/`"@`); unbalanced `(` `[` `{` outside strings and
comments; trailing binary operator with no right operand (`|`, `||`, `&&`, `;`); leading binary
operator with no left operand; trailing line-continuation backtick; unterminated `$(`; dangling
redirection (`>`/`>>` with no target); the literal `>>` continuation marker.

**Cannot recognise (must never be implied):** grammar-level invalidity (`if` without `(`, malformed
`foreach`/`switch`), parameter/argument correctness, cmdlet existence, module/type resolution,
splatting, member/method correctness, and every semantic property.

A PowerShell continuation prompt (`>>`) is classified as **COMMAND INCOMPLETE / PARSER CONTINUATION**,
never as an ordinary execution failure.

## 7. Component specifications (3 of 3)

### 7.1 `encoding.py` — encoding / rendering intelligence

Models encoding as a pipeline and keeps its stages distinct:

```text
file encoding → native executable I/O → process output encoding →
console code page → terminal rendering → model interpretation
```

- `SOURCE EVIDENCE` (what a structured reader returns) ≠ `TERMINAL RENDERING EVIDENCE` (what the
  console showed).
- Mojibake in terminal output is never proof that the source file is corrupted.
- For structured files such as JSON, structured readers are preferred over visual terminal inspection.
- Distinguishes console-encoding (`chcp`) changes from file-encoding facts.

### 7.2 `hazards.py` — exception / stale-variable safety

Detects the dangerous pattern: an operation that can fail leaves a variable holding a previous value,
which a later operation consumes and presents as current evidence.

Example: `$bytes = [IO.File]::ReadAllBytes($p)` — if the read throws and later code continues,
PowerShell state may still hold an older value.

Rule enforced: **a measurement derived from failed input must never be emitted as authoritative
evidence.** The analyzer surfaces the dependency chain and the required guard (fail fast, clear the
variable, or re-derive) as a recommendation only.

### 7.3 `hygiene.py` — terminal hygiene and mutation minimization

| Pattern | Verdict |
| --- | --- |
| unnecessary `chcp` | WARNING (mutation + no demonstrated need) |
| repeated `Set-Location` | WARNING (redundant mutation) |
| repeated environment initialization | WARNING |
| unnecessary `$env:NAME = …` | WARNING (mutation) |
| `Set-ExecutionPolicy` | WARNING (machine/state mutation) |
| `Set-Item` on state | WARNING (mutation) |
| spawning an unnecessary PowerShell process | WARNING |

Preference enforced: **local explicitness over global shell-state changes.**

### 7.4 `cost.py` — qualitative cost model

| Class | Examples |
| --- | --- |
| `TRIVIAL` | observation lookup, `Get-Location`, `Test-Path` |
| `LOW` | targeted file read, structured JSON read, single-file literal search, `git status` |
| `MEDIUM` | bounded enumeration, multiple targeted reads |
| `HIGH` | recursive scans, broad `Select-String`, custom Python crawlers |
| `VERY HIGH` | repeated full scans, overlapping crawlers |

A separate **mutation cost** is added for state-changing operations. The objective is not fewer
commands for its own sake but less unnecessary work, less failure, less ambiguity, fewer repeated
discoveries, and more trustworthy evidence.

The cost table is a deterministic classification function: same command → same class.

### 7.5 `redundancy.py` — duplicate detection

The deterministic **n0–n3** ladder (decision A9):

| Level | Normalization |
| --- | --- |
| `n0` | raw (outer whitespace trimmed only) |
| `n1` | internal whitespace runs collapsed, tabs → space, ASCII case folded |
| `n2` | `n1` + `"…"`↔`'…'` unification **only** when the span has no backtick, no `$` interpolation, no doubled-quote escape, and no embedded quote of the other kind |
| `n3` | `n2` + `\`↔`/` inside path-like tokens, collapsed duplicate separators, drive-letter case normalized, and removal of a single leading environment-establishing prefix **only** when its target equals the known/declared repository root |

Explicitly **not** normalized (and required to be printed in the method line): alias equivalence
(`ls`↔`Get-ChildItem`), abbreviated parameters, parameter reordering, `-ErrorAction` differences,
here-string vs quoted string, `%` vs `ForEach-Object`, pipeline regrouping, and any similarity metric.

Output is `duplicate (level nN) of <command-id>` with reasons, or
`no duplicate found (levels n0–n3 checked)`.

Repetition is justified only when something relevant changed: file, worktree, terminal, process, CWD,
configuration, prior staleness, prior failure, or scope.

### 7.6 `failures.py` — failure classification and differentiated recovery

| Category | Examples |
| --- | --- |
| syntax failure | PowerShell rejects the command outright |
| parse incompleteness | continuation state, unterminated construct |
| wrong CWD | relative path resolved against the wrong root |
| missing file | path does not exist |
| permission failure | access denied |
| encoding / rendering issue | mojibake, mismatched decode |
| native-command argument issue | `findstr` quoting/grammar misuse |
| PowerShell semantic issue | valid syntax, wrong semantics |
| repository-state issue | operation invalid for current git state |
| tool availability issue | executable/module absent |

Recovery must be **differentiated**: a retry occurs only when at least one meaningful condition
changed (state, scope, command, path, encoding handling, dialect, CWD, plausible transient cause).
Otherwise the next action must differ from the previous one.

### 7.7 `capabilities.py` — capability registry and routing

- The registered tool set is the **authority**; the registry contributes intent tags only
  (decisions A12, S5).
- Registry rows: `{name, purpose, intent_tags[], scope, mutation_cost}` with a frozen tag vocabulary
  and deterministic ordering.
- Drift protection: registry ↔ pinned expected-tool list (both directions) and registry ↔ live
  `list_tools()` output.
- Routing answers "can an existing capability do this?" before any shell plan is produced.

### 7.8 `validate.py` — orchestrator

Composes every analyzer into one deterministic report. Composition order is fixed and matches the
contract's frozen section order (`01-V0.9-CONTRACT.md` §16).

- Inputs: command text, declared client context, store lookups.
- Outputs: leading `[SUMMARY]` (machine-readable) + fixed sections + recommendation.
- Never executes the command; never mutates state; never lowers a verdict to make a command pass.
- `lint` is a mode of this single analyzer, not a separate tool (decision A11).

## 8. Tool adapters

`tools/shell_env.py` holds ten thin functions. Each adapter:

1. validates and normalizes its declared inputs;
2. calls the corresponding `shell/` component;
3. renders through `formatting.py` (budgets: 4000 default / 16000 max / 200-char line clip);
4. carries an `Annotated[..., Field(description=...)]` parameter contract and a `"READ ONLY."`
   docstring, matching the existing tool convention;
5. performs no I/O beyond the approved probes and no mutation of any kind.

Registration happens in phases (decision A11), never as a single 10-tool release.
