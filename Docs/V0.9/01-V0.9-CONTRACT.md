# MCQuest MCP v0.9 — Contract

> STATUS: **P0 — APPROVED BEHAVIORAL CONTRACT**
>
> This document defines what V0.9 **must be**. It is a contract, not a description of built
> functionality. Implementation status: **NOT STARTED**.
>
> Where this contract and the original proposal differ in detail, the difference is an approved
> decision recorded in `07-V0.9-DECISIONS.md`; the proposal remains the source specification.

---

## 1. Purpose

V0.9 exists to make Cline's interaction with the environment **state-aware, process-aware,
shell-dialect-aware, operation-aware, failure-aware, encoding-aware, redundancy-aware,
mutation-aware, repository-aware, and MCQuest-aware**.

The contract therefore governs five things and nothing else:

1. what V0.9 may **know** (facts, sources, trust, scope, freshness);
2. what V0.9 may **remember** (observations, history, invalidation);
3. what V0.9 may **analyse** (operations, dialect, boundaries, parsing, encoding, hazards, cost,
   redundancy, failures, capabilities);
4. what V0.9 may **say** (verdicts, provenance, recommendations, output shape);
5. what V0.9 may **never do** (execution, mutation, enforcement, fabrication).

## 3. Non-goals

The following are contractually **out of scope** (proposal §34, confirmed by authorization):

- autonomous shell execution;
- automatic repository modification;
- vector database or embedding surface;
- broad cross-platform abstraction (Bash, CMD-only, Linux, macOS) in the MVP;
- replacing, weakening, or duplicating V0.8 audit tools;
- interpreting V0.9 as a generic shell utility.

Also explicitly out of scope for the MVP: policy enforcement/denial, sandboxing, controlled
autonomy, PowerShell AST parsing (deferred to a later phase), and any similarity-based command
equivalence.

## 4. V0.8 / V0.9 boundary

```text
MCQuest V0.8   Repository Intelligence                  "What is true?"
MCQuest V0.9   Environment + Terminal + Command Intel.   "How should I interact with it?"
Cline          Task Intelligence                         "What should I accomplish?"
```

Contractual rules:

1. V0.9 answers interaction questions; V0.8 answers repository-truth questions.
2. When an intent is satisfiable by an existing MCQuest capability, V0.9 **routes to that
   capability** rather than planning a shell equivalent (§19).
3. V0.9 does not extend, refactor, or repair V0.8 code.
4. V0.9's read-only stance is at least as strict as V0.8's.

## 5. Environment Contract

V0.9 must be able to represent at least the following facts:

| Fact | Typical source | Scope | Notes |
| --- | --- | --- | --- |
| OS family / version | server-observed | STATIC | never inferred from a client shell |
| Shell (family) | client-declared, else unknown | PROCESS | the *client's* shell is a client fact |
| Shell version | client-declared, else machine baseline probe, else unknown | PROCESS / SESSION | drives baseline-tagged dialect rules (A8) |
| Repository (root) | server-observed (`--project`, `MCQUEST_PROJECT_ROOT`) | STATIC | the only trusted root anchor |
| CWD | client-declared, else unknown | PROCESS | **untrusted unless declared and corroborated** |
| CWD trust | derived | PROCESS | one of `trusted/corroborated/untrusted/unknown` |
| Terminal session | client-declared, else unknown | SESSION | no cross-session reuse |
| Process identity | client-declared, else unknown | PROCESS | no cross-process reuse |
| Git configuration relevant to execution | server-observed for the root | SESSION | e.g. `core.autocrlf` |
| Git state (branch, status) | server-observed for the root | WORKTREE | invalidated by worktree events |
| Known MCQuest capabilities | server-observed | SESSION | matches the registered surface |
| Relevant environment rules | contract / policy constants | STATIC | e.g. "use `-SimpleMatch` for literal searches" |

Canonical representation (proposal §7, annotated with the required source/trust labeling):

```text
SHELL CONTEXT

OS: Windows                        source=SERVER_OBSERVED  trust=trusted
Shell: PowerShell <version|unknown> source=<CLIENT_DECLARED|UNKNOWN>
Repo: D:\DeveloperTools\mcquest-mcp source=SERVER_OBSERVED  trust=trusted
CWD: <path|unknown>                source=<CLIENT_DECLARED|UNKNOWN>  trust=<...>

Terminal:
  session = <declared|unknown>
  process = <declared|unknown>

Git:
  core.autocrlf = true             source=SERVER_OBSERVED  trust=trusted

Known capabilities:
  mcquest_doc_gap_audit
  mcquest_component_inventory
  mcquest_diagnostics
  ...

Rules:
  prefer targeted operations
  prefer structured reads for structured data
  use explicit repository paths when CWD is uncertain
  use -SimpleMatch for literal searches
  avoid unnecessary chcp
  fail fast on dependent reads
  do not emit measurements after failed input
  do not repeat fresh observations
  do not trust observations from another terminal process
```

Every fact the system reports must be classifiable as **observed**, **declared**, or **unknown**, and
each report must state the source and trust label alongside the value.

## 6. Fact sources

Exactly three sources exist. No others may be introduced.

| Source | Meaning | Trust it can reach | Examples |
| --- | --- | --- | --- |
| `SERVER_OBSERVED` | the MCP server established the fact itself | `trusted` | project root, OS, Python version, git facts for the root, executable availability, probe baselines |
| `CLIENT_DECLARED` | the client supplied the fact (it cannot be verified directly) | `untrusted` → `corroborated` | client CWD, session id, client process id, client shell version, client env vars, client console code page |
| `UNKNOWN` | nobody established the fact | `untrusted` / `unknown` | anything not observed and not declared |

Declaration channel (decision A2). Client context enters V0.9 only through explicit optional inputs:

| Input | Purpose |
| --- | --- |
| `client_session` | terminal/session identity |
| `client_process_id` | process identity |
| `client_cwd` | the client's working directory |
| `client_shell` | shell family/version of the client |
| `client_command`, `client_exit_code`, `client_output` | evidence about a command the client executed (recorded via `mcquest_shell_observe`) |

`mcquest_shell_observe` is the canonical recording path for all client-declared context.

Rules:

1. A server-observed fact is **never** relabeled as a client fact, and vice versa.
2. Values of the server's own process (CWD, PID, console code page, shell) are recorded only under a
   labeled `mcp_server` subject and may never be emitted as the client's terminal state.
3. `UNKNOWN` is a valid, reportable answer. It is never replaced by a guess.
4. When nothing is declared, V0.9 operates in degraded mode (decision S1): it reports
   `CWD: unknown / source: UNKNOWN / trust: untrusted` and instructs the caller to use explicit
   repository paths. It does not fail loudly.

## 7. Trust model

Exactly four trust values exist. No additional authority levels may be invented.

| Trust | Meaning | Typical origin |
| --- | --- | --- |
| `trusted` | established by the server itself | `SERVER_OBSERVED` facts |
| `corroborated` | client-declared and independently checked by the server without running the client's command | declared CWD that resolves to an existing directory inside the known root; declared probe result consistent with server-observed facts |
| `untrusted` | declared but not checked, or unknown | freshly declared CWD, unknown CWD |
| `unknown` | no basis for any judgement | un-declared facts |

Rules:

1. Corroboration upgrades **trust** only; it never changes **source**. A declared fact stays
   `source=CLIENT_DECLARED` and its provenance text remains "declared by client; not verified".
2. Facts are keyed by `(session, process)`. A fact declared for session A is never served for
   session B; session B receives `unknown`.
3. Server restart or client restart discards SESSION/PROCESS facts (decision S3). No carry-over.
4. No numeric "confidence score" may be invented for facts. Confidence is expressed only through
   source + trust + freshness.

## 8. Terminal and process identity

Terminal processes are distinct execution contexts. A variable, environment value, CWD, or process
state from one PowerShell process must never be assumed to exist in another.

V0.9 must distinguish:

```text
terminal session   ≠   process   ≠   shell   ≠   repository   ≠   CWD
```

Example (proposal §8):

```text
Terminal A
  process = 18240
  CWD = D:\DeveloperTools\mcquest-mcp

Terminal B
  process = 19310
  CWD = D:\DeveloperTools
```

Contractual rules:

1. An observation from Terminal A is never treated as current state in Terminal B.
2. A new PowerShell process receives a **new** identity; PROCESS-scoped facts of the previous process
   do not transfer.
3. Session/process identity is client-declared; if it is not declared, V0.9 cannot distinguish
   terminals and must say so rather than assume.
4. The MCP server's own process identity is a separate `mcp_server` subject and is never used as a
   substitute for a client identity.

## 9. Observation model

An observation must carry enough provenance to decide whether it can still be reused.

```json
{
  "observation": "git.autocrlf",
  "value": true,
  "scope": "REPOSITORY",
  "repository": "D:\\DeveloperTools\\mcquest-mcp",
  "observed_at": "<UTC ISO-8601>",
  "source": "SERVER_OBSERVED",
  "trust": "trusted",
  "freshness": "SESSION",
  "evidence": "git config core.autocrlf"
}
```

```json
{
  "observation": "locale.quiz.loading.si",
  "value": "Quiz පූරණය වෙමින්...",
  "scope": "FILE",
  "file": "frontend/src/locales/si.json",
  "operation": "READ_JSON",
  "terminal_session": "<declared session id>",
  "source": "CLIENT_DECLARED",
  "trust": "untrusted",
  "freshness": "WORKTREE"
}
```

Required fields: `observation`, `value`, `scope`, `observed_at`, `source`, `trust`, `freshness`,
`evidence`. Optional: `repository`, `file`, `operation`, `terminal_session`, `process_id`.

> No numeric `confidence` field exists in the approved model (decision A14). Precision must not be
> invented; reliability is expressed through `source` + `trust` + `freshness`.

## 10. Observation scopes

| Scope | Meaning | Reuse across sessions/processes |
| --- | --- | --- |
| `REPOSITORY` | repository identity and root-level facts | allowed (STATIC-backed) |
| `WORKTREE` | git state, file inventories, diagnostics | allowed while no worktree event invalidated it |
| `FILE` | a specific path's content/derived evidence (approved extension, A14) | allowed while that file is unmodified |
| `SESSION` | discovered tool versions/config for a session | never across sessions |
| `PROCESS` | CWD, shell variables, process-local state | never across processes |
| `EPHEMERAL` | command output and temporary state | never across commands |

## 11. Freshness

| Class | Examples |
| --- | --- |
| `STATIC` | repository root, repository identity |
| `SESSION` | discovered tool versions, configuration |
| `WORKTREE` | git status, file inventories, diagnostics |
| `PROCESS` | CWD, shell variables, process-local state |
| `EPHEMERAL` | command output, temporary state |

Rules:

1. Freshness is semantic, not time-based. **No wall-clock TTL exists in the MVP** (decision A5):
   nothing expires merely because time passed.
2. `observed_at` is provenance for the reader; it never triggers automatic expiry.
3. Validity = freshness class + explicit invalidation events + the per-scope revision counter.

## 12. Invalidation

Every event with a known effect invalidates the affected scopes; nothing is retained merely because it
was once true.

| Event | Potentially stale |
| --- | --- |
| File modified | content, searches, diagnostics |
| File created/deleted | inventories, path existence |
| Git checkout / reset / pull | worktree observations |
| Branch switch | Git state |
| CWD change (`Set-Location`, `cd`) | process CWD |
| New PowerShell process | process state |
| Dependency installation | executable/package facts |
| Configuration change | corresponding observations |
| Console code-page change | encoding observations |
| Terminal restart | session/process facts |
| Server restart | session/process facts (reported as unknown) |

Principle:

> **Invalidate rather than guess.**

## 13. Semantic operations

V0.9 classifies the intended operation **before** selecting a command; it never treats every request
as a command-generation problem.

```text
READ_FILE      READ_JSON       SEARCH_LITERAL   SEARCH_REGEX   ENUMERATE_FILES
CHECK_PATH     CHECK_GIT_STATE  CHECK_CONFIG     MEASURE_EOL    RUN_NODE
RUN_PYTHON     RUN_TEST         BUILD            INSTALL        EDIT
```

Classification must distinguish: structured data vs plain text; filesystem state vs Git state;
environment state; execution; mutation.

Preferred execution ladder (contractual preference order):

```text
existing evidence
  → existing MCQuest capability
    → structured tool operation
      → targeted shell operation
        → broader scan only if necessary
```

Example (proposal §12): *"Check `quiz.loading` in en/si/ta JSON files"* is `READ_JSON` — parse and
inspect the key. Repeated `findstr` searches are a contract violation of the preference ladder.

## 14. Recommend-only boundary

V0.9 **analyses, observes, plans, validates, and recommends**. It does not execute, mutate, or enforce.

| V0.9 may | V0.9 must not |
| --- | --- |
| analyse a command and report verdicts | execute the analysed command |
| recommend an operation or an existing capability | run, block, or deny anything |
| emit a prepared command **as text** | apply a correction automatically |
| record declared evidence and observations | modify the repository, files, or shell state |

Additional rules:

1. No V0.9 output may state or imply that a command was executed or verified by V0.9.
2. A prepared command must be labeled as prepared and **not executed**.
3. Policy enforcement, sandboxing, and controlled autonomy are out of scope.
4. Cline remains the execution authority; V0.9 never becomes a second execution path.

## 15. Probe boundary

Permitted server-side probes are **bounded, fixed-argv, read-only**. The distinction is explicit:
*arbitrary command execution* is forbidden; *bounded read-only environment probes* are permitted and
enumerated below.

| # | Probe | Invocation | Yields | Source |
| --- | --- | --- | --- | --- |
| 1 | project root | `--project` / `MCQUEST_PROJECT_ROOT` (no process) | repository identity | `SERVER_OBSERVED` |
| 2 | OS / platform | `platform`, `os`, `sys` stdlib | OS family/version, Python version | `SERVER_OBSERVED` |
| 3 | presence | `shutil.which(name)` | node/git/python/pwsh/powershell on PATH | `SERVER_OBSERVED` |
| 4 | git facts | `git --no-pager config --get core.autocrlf`, `rev-parse --show-toplevel`, `rev-parse --abbrev-ref HEAD`, `status --porcelain` | config, branch, status | `SERVER_OBSERVED` |
| 5 | node version | `node --version` | runtime version | `SERVER_OBSERVED` |
| 6 | machine shell baselines | `pwsh -NoProfile -NonInteractive -Command $PSVersionTable.PSVersion.ToString()` (same for `powershell`) | shell baselines available on the machine | `SERVER_OBSERVED` — **machine capability, explicitly not the client's shell** |

Probe rules:

1. Literal argv only. Client-supplied text is never interpolated into a probe.
2. No shell: no `shell=True`, no pipes, no redirection.
3. Explicit `encoding="utf-8", errors="replace"`; per-probe timeout ≤ 10s; `cwd` = project root.
4. `check=False` — a non-zero exit yields `UNKNOWN`, never a fabricated value.
5. Results are cached with SESSION freshness and invalidated on the mapped events.

Forbidden without exception: probes assembled from client command text; install/build/test/run
invocations; network access; state-mutating calls (`chcp`, `Set-Location`, `$env:` assignments); and
anything whose effect outlives the call.

## 16. Output conventions

1. Every V0.9 tool renders through the existing formatting layer so the established budget contract
   applies:
   - default output ≤ **4000** characters;
   - maximum ≤ **16000** characters;
   - line clip ≤ **200** characters.
2. Validation-style output begins with a machine-readable `[SUMMARY]` block, followed by fixed-order
   sections.
3. Section order (frozen): Syntax, Parse completeness, Shell dialect, Native boundary, CWD,
   Path safety, Redundancy, Operation, Mutation, Encoding, Failure propagation, Stale-variable
   hazard, Cost, Capability duplication, Recommendation.
4. Verdict tokens are exactly `ERROR`, `WARNING`, `INFO`, `PASS`, with a summary line
   `verdict: <ERROR|WARNINGS|PASS> (n ERROR, n WARNING, n PASS)`.
5. Warnings are not converted into hard errors. Severity must be proportional to evidence.
6. Output is deterministic: the same input yields byte-identical output. No clock-dependent,
   ordering-dependent, or randomness-dependent content.
7. Every heuristic is labeled as heuristic; findings carry their construct/location, not just a verdict.

## 17. Provenance

1. Every fact, observation, and recommendation carries: where it came from, when it was observed,
   which scope and freshness class it has, and how it was labelled (source + trust).
2. Declared evidence retains the text "declared by client; not verified" for its whole lifetime.
3. History records retain the originating command text, its normalization levels, its cost class, its
   operation classification, and the session/process it belongs to.
4. Provenance is immutable: later events add invalidation, they never rewrite how a fact was obtained.
5. Tool-derived evidence ingested from other MCQuest tools keeps its originating tool as the source.

## 18. No-false-evidence rule

> **A measurement derived from failed input must never be emitted as authoritative evidence.**

Contractual consequences:

1. If an operation can fail and a later operation consumes its result, the consumer must be flagged
   rather than trusted (stale-variable hazard).
2. Terminal rendering is never presented as source-file evidence; mojibake is not proof of corruption.
3. A heuristic negative (for example "no incompleteness detected") must be reported as a bounded
   heuristic result, never as proof.
4. `UNKNOWN` is preferred over any inferred value.
5. No output may describe a command as executed, verified, or successful unless that execution was
   performed and evidenced outside V0.9's analysis role.
6. Severity labels describe V0.9's analysis, not measured runtime facts.

## 19. MCQuest capability routing

1. Intent is checked against existing capabilities **before** a shell interaction is planned.
2. The registered tool set is the single authority for what exists; the intent-metadata registry adds
   only routing tags.
3. Drift protection is mandatory:
   - exact set equality between the registry and the pinned expected-tool list, in both directions;
   - equality between the registry and the tools actually exposed by the running server;
   - a frozen tag vocabulary and a deterministic registry order.
4. A routed recommendation names the capability and why it fits; it is a recommendation, never an
   invocation.
5. V0.9 must not recreate an existing capability through PowerShell (for example a recursive file walk
   plus literal search instead of the existing search/audit tools).

## 20. Redundancy policy

1. Recent relevant work is remembered so the same observation, search, Git check, file read,
   capability discovery, or environment discovery is not repeated unnecessarily.
2. A repeat is justified only when something relevant changed (file, worktree, terminal, process,
   CWD, configuration, prior staleness, prior failure, or required scope).
3. Duplicate detection uses the deterministic n0–n3 ladder only; no similarity measure is permitted.
4. A negative duplicate result must state the levels checked, so novelty is not implied.

## 21. Cost model

Classes: `TRIVIAL`, `LOW`, `MEDIUM`, `HIGH`, `VERY HIGH`, plus a separate mutation cost for
state-changing operations.

The objective is not merely fewer commands but less unnecessary work, less failure, less ambiguity,
fewer repeated discoveries, and more trustworthy evidence.

## 22. Failure classification and recovery

Failure categories (at minimum): syntax failure, parse incompleteness, wrong CWD, missing file,
permission failure, encoding/rendering issue, native-command argument issue, PowerShell semantic
issue, repository-state issue, tool-availability issue.

No-blind-retry policy:

1. A retry requires at least one meaningful change (state, scope, command, path, encoding handling,
   shell dialect, CWD, or a plausible transient cause).
2. An unchanged condition yields a **differentiated** next action, not a repetition.
3. Parse incompleteness is never reported as an execution failure.

## 23. Contract conformance

A V0.9 component conforms only if it:

1. labels every fact with source, trust, scope, freshness;
2. never promotes facts across sessions or processes;
3. preserves `UNKNOWN` rather than guessing;
4. performs no execution beyond the approved probes and no mutation at all;
5. produces deterministic, budget-compliant, summary-first output;
6. distinguishes heuristics from proofs;
7. recommends rather than enforces;
8. retains provenance for everything it reports.

Where this contract is silent, the proposal governs. Where the proposal is silent, the component must
ask rather than invent behavior.
