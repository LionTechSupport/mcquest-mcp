### 6.3 Implementation interpretations recorded (no approved decision was changed)

Mapping/detail ambiguities were resolved in code and are disclosed here rather than silently
resolved; none of these alters an approved decision, and none was recorded in `07`:

1. **`ENVIRONMENT_CHANGE` mapping** — this event is mandated by the P1 authorization but appears
   in neither contract §12 nor architecture §5.3. Mapped to `PROCESS` refined by variable name
   plus `EPHEMERAL` wholesale (env vars are "shell variables, process-local state", §10).
2. **`CONFIGURATION_CHANGE` mapping** — "corresponding observed facts" (§12) mapped to
   `REPOSITORY` + `FILE` + `SESSION`, subject-refined by config key, wholesale when no key is
   supplied; `WORKTREE` intentionally excluded.
3. **`REPOSITORY_WORKTREE_CHANGE` mapping** — mandated by P1, absent from both tables; mapped to
   `REPOSITORY` + `WORKTREE` wholesale; `FILE` changes arrive through the file events.
4. **Revision granularity** — counters are per `(scope, subject)` exactly as architecture §5.3
   states. Events described as "that session's facts" therefore conservatively over-invalidate
   sibling subjects in the same scope; over-invalidation is the safe direction ("invalidate
   rather than guess"), and a stale fact stays retrievable for audit while never reusable.
5. **Mutation cost** — contract §21 defines one class vocabulary "plus a separate mutation cost";
   implemented as the separate `CommandRecord.mutation` field using the same `CostClass` values
   instead of inventing a second scale.
6. **`Confidence` not implemented** — architecture §2's one-line layout mentions a `Confidence`
   type, but §5.1 does not specify it, contract §7 rule 4 forbids numeric confidence, and no enum
   values are approved anywhere. No values were invented; the type is deferred until an approved
   vocabulary exists.
7. **`record_command` invalidates `EPHEMERAL`** — contract §10 says EPHEMERAL facts are "never
   across commands"; the store enforces this on every command record so no caller can omit it.
8. **Field naming** — contract §9's `observation` / `observed_at` / `terminal_session` names were
   used verbatim (the contract is authoritative for behavior over §5.1's abbreviated sketch).

### 7.6 Implementation interpretations recorded (no approved decision was changed)

1. **PowerShell probe split (hybrid)** — `pwsh -Version` for PowerShell 7+; the single fixed
   `-Command` literal for Windows PowerShell 5.1, which has no print-and-exit version flag.
   Both are fixed argv with no user text; no generic PowerShell execution facility exists.
2. **Environment client-section subset** — the environment tool renders the five contract §5
   client fields (session, process, shell, shell version, CWD); the console code page is rendered
   by `mcquest_shell_terminal` only, because contract §5's environment table has no code-page row.
3. **`client_shell_version` declared input** — added as a fifth optional input because contract §5
   requires shell version to be client-declarable; decision A2's four-input list plus command
   evidence is otherwise unchanged, and no client input ever reaches a probe.
4. **Probe failures are cached** — a failed probe's `UNKNOWN` result is recorded like any other
   observation (contract §15 rule 5 caches results with SESSION freshness and invalidates on the
   mapped events), so a missing tool is not re-probed on every call.
5. **`environment.py` imports `terminal.py`** — contract §5's Environment Contract includes the
   terminal/identity rows, so the assembly module reads terminal state (architecture §3's
   dependency sketch lists only `facts`/`store` for this module; the extra edge is deliberate and
   one-directional — `terminal.py` never imports `environment.py`).
6. **Registry `scope`/`mutation_cost` fields** — A12's row schema names `scope` and
   `mutation_cost`; `scope` is a frozen six-value vocabulary and `mutation_cost` is always `None`
   because every row is read-only (a mutation cost would imply a mutation).
7. **Registry paging cap (10 rows)** — three-line rows at 10 per page keep one page inside the
   4000-character default budget while `total`/`implemented`/`planned` disclose the full registry
   on every page.
8. **Output carries no clock** — contract §16 rule 6 forbids clock-dependent output, so
   `observed_at` stays provenance inside the store and is never rendered; repeated calls are
   byte-identical by construction (verified).
9. **Worktree facts not probed** — `git status` was not implemented (minimum probes); the context
   tool reports `worktree: unknown` explicitly rather than implying absence.

### 8.3 P3 interpretation notes

1. The operation classifier is lexical and deterministic. It classifies the
   frozen contract §13 vocabulary only; it does not plan, route, or select a
   command. `UNKNOWN` remains the result for unrecognised input.
2. Parse analysis is explicitly heuristic. Its negative verdict is worded as
   `NO INCOMPLETENESS DETECTED (heuristic — NOT proof of completeness)`; it
   never claims validity, completeness, or proof.
3. Encoding and hygiene accept existing P1 `Fact` provenance where applicable.
   `UNKNOWN` evidence and server-owned `mcp_server` observations are not
   promoted to client evidence or client terminal state.
4. Redundancy uses the existing `ObservationStore`/`CommandHistory` and the
   A9 n0–n3 ladder only. Aliases, abbreviated parameters, parameter reordering,
   semantic equivalence, and similarity are not normalized.
5. P3 deliberately does not implement `planner.py`, `validate.py`, the shared
   validation report, capability routing, or any MCP adapter/registration.

### 9.4 P4 destructive-command rule (recorded, not a P3 change)

The post-P3 smoke test showed `Remove-Item -Recurse -Force ./build` classified as
`BUILD` with `is_mutation_bearing(BUILD) is False`, because the frozen contract
§13 vocabulary has no `DELETE` member. P3 is frozen and was **not** modified.

P4 therefore treats `is_mutation_bearing(...) is False` as *not* proof of safety.
`validate.py` carries its own bounded, lexical destructive-pattern evidence
(`_destructive_findings`) reported in the Mutation section, independently of the
operation classification. The smoke-test command now reports
`DESTRUCTIVE_REMOVAL` (WARNING) + `RECURSIVE_FORCED_REMOVAL` (ERROR) and an
overall `ERROR` verdict. `operations.py` and the frozen vocabulary are untouched;
`DELETE` was **not** added.

P4 also surfaces state mutations `hygiene.py` does not report
(`SET_CONTENT_WRITE`, `NEW_ITEM_CREATE`, `GIT_DESTRUCTIVE`, `GIT_FORCE_PUSH`, …)
as P4 evidence. This is recorded here as a P3 coverage gap **observed, not
repaired**; P3 remains frozen.

### 9.5 P4 interpretation notes

1. **Section order is asserted, not assumed.** `validate_command` raises
   `AssertionError` if the composed order ever differs from the contract §16
   rule 3 frozen order.
2. **`lint` is a mode, not a tool** (decision A11, test-plan RT8). `mode="lint"`
   runs the identical composition; no separate lint tool is registered.
3. **Encoding severity is preserved, never escalated.**
   `FILE_ENCODING_UNDECLARED` stays `INFO`, so `Get-Content -LiteralPath README.md`
   reports `PASS` with 0 ERRORs — the second post-P3 smoke finding is therefore
   *not* an error, and was deliberately not escalated.
4. **Redundancy is explicitly partial without a root.** When no
   `repository_root` is supplied, the Redundancy section emits an `INFO`
   `REDUNDANCY_PARTIAL` finding rather than implying a full n0–n3 evaluation.
5. **`observed_at` is stored but never rendered** (decision A5), so
   `mcquest_shell_validate` output is byte-identical across repeated calls.
6. **`observe.py` reuses P1/P2 only** — it imports `Fact`/`Observation`/
   `ObservationStore` from `facts.py`/`store.py`, `apply_invalidation` from
   `invalidate.py`, and `observed_now` from `environment.py`. It defines no
   second Fact model, store, or clock.
