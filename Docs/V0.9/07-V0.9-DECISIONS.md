## 2. Approved working decisions A1–A14

### A1 — Tool naming

- **Status:** APPROVED
- **Decision:** the ten V0.9 tools are named `mcquest_shell_environment`,
  `mcquest_shell_terminal`, `mcquest_shell_context`, `mcquest_shell_plan`,
  `mcquest_shell_prepare`, `mcquest_shell_validate`, `mcquest_shell_observe`,
  `mcquest_shell_next`, `mcquest_shell_history`, `mcquest_shell_capabilities`.
  The surface, count and responsibilities of proposal §27 are preserved 1:1; only the namespace
  prefix is added.
- **Rationale:** all 24 shipped tools use the `mcquest_*` namespace; a single family maximizes
  discoverability, avoids collisions with generic `shell_*` tools from other servers, and matches the
  server name. Renaming later is more expensive than prefixing now.
- **Alternatives considered:** (a) the literal bare `shell_*` names from §27 — a second family, higher
  collision risk, ambiguous ownership; (b) a full generic rename — satisfies an older generic-naming
  rule but breaks the existing 24-tool API, tests, and documentation.
- **Consequences:** the registration test grows by ten names; documentation records a single tool
  family; the older generic-naming directive remains unmet and is not silently overridden.

### A2 — Fact sources

- **Status:** APPROVED
- **Decision:** exactly three fact sources — `SERVER_OBSERVED`, `CLIENT_DECLARED`, `UNKNOWN`. Every
  fact carries `source`, `trust`, `scope`, `freshness`, `observed_at`, `evidence`. Client context
  enters only through explicit declared inputs (`client_session`, `client_process_id`, `client_cwd`,
  `client_shell`, and command evidence via `mcquest_shell_observe`). Default:
  `CWD → value: unknown, source: UNKNOWN, trust: untrusted`. Corroboration upgrades trust only, never
  source. Facts are keyed by `(session, process)` and never promoted across sessions or processes.
  The server's own process values are recorded under a labeled `mcp_server` subject and are never
  emitted as the client's terminal state.
- **Rationale:** the MCP server is a separate process and cannot observe Cline's terminal; the
  alternative is fabrication, which the no-false-evidence rule forbids.
- **Alternatives considered:** (a) `SERVER_OBSERVED` only — honest, but CWD stays permanently unknown
  and the wrong-CWD and multi-terminal scenarios cannot be addressed; (b) trusting a declared CWD by
  default — reintroduces the wrong-CWD failure; (c) corroborating by executing in the client shell —
  moves V0.9 toward execution authority, contrary to A13.
- **Consequences:** `unknown` becomes a first-class output; degraded mode is normal (S1); every fact
  line shows source and trust; cross-terminal inference is impossible by construction.

### A3 — Execution / probe boundary

- **Status:** APPROVED
- **Decision:** V0.9 may perform only **bounded fixed-argv read-only server probes**, from a closed
  allowlist: project root (`--project`/env), OS/Python facts (stdlib), executable presence
  (`shutil.which`), git facts (`git --no-pager config|rev-parse|status`), `node --version`, and
  machine shell baselines (`pwsh`/`powershell` version query). Probes use literal argv, no shell, no
  pipes or redirection, explicit UTF-8 decoding with replacement, ≤ 10s timeout, `cwd` = project root,
  and `check=False`; failure yields `UNKNOWN`. Arbitrary command execution remains forbidden.
- **Rationale:** the no-shell-execution principle and the need for live environment facts appear to
  conflict; enumerating a closed read-only allowlist resolves the conflict without granting execution
  authority. It also keeps V0.9 no broader than V0.8, which already spawns `git`/`node` with fixed
  argv.
- **Alternatives considered:** (a) file-read-only (no subprocess) — git facts become partially
  hand-parsed, shell baselines become unknown, and V0.9 becomes stricter than the shipped V0.8;
  (b) client-probe-only — zero new subprocesses but more round-trips and everything arrives declared;
  (c) deny all probes — not viable while `git`/`node` subprocesses already exist and must be labeled.
- **Consequences:** probe results are always `SERVER_OBSERVED`; shell baselines are explicitly labeled
  as machine capability (S2); the allowlist must be extended by decision, never by convenience.

### A4 — Observation persistence

- **Status:** APPROVED
- **Decision:** the observation and command history store is **in-memory only**, scoped to the MCP
  server process, with an explicit `reset()` hook for tests. No file, cache directory, or external
  store is created. Restart discards SESSION/PROCESS facts and they are reported as `unknown`.
- **Rationale:** the existing read-only invariant is enforced textually across `src/mcquest_mcp`
  (no write/delete/exec primitives), and creating files is outside the read-only design. Persistence
  would require relaxing that invariant for no MVP benefit.
- **Alternatives considered:** (a) a cache outside the project root — requires rewriting the
  no-write-primitive test and a separate decision authorizing file creation; (b) no store at all —
  makes redundancy detection, history, blind-retry prevention, and several acceptance criteria
  impossible; (c) client-held history — workable fallback, but every call must carry history and
  duplicate detection depends on complete client reporting.
- **Consequences:** memory is bounded by process lifetime; the store must be small, deterministic, and
  explicitly resettable; no stale state can survive a restart, which is the desired safety property.

### A5 — Freshness / TTL semantics

- **Status:** APPROVED
- **Decision:** **no wall-clock TTL in the MVP.** Freshness is a semantic class
  (`STATIC | SESSION | WORKTREE | PROCESS | EPHEMERAL`); validity derives from the class, explicit
  invalidation events, and a monotonic per-scope/subject `revision` counter. `observed_at` (UTC
  ISO-8601) is retained as provenance only and never triggers automatic expiry.
- **Rationale:** the proposal requires "how long it remains valid" to be explicit but supplies no
  numbers; inventing numeric TTLs would contradict the project's rule that approved limits are exact
  and must not be invented. Evidence-based invalidation is also deterministic and testable, whereas
  clock-based expiry makes tests time-dependent.
- **Alternatives considered:** (a) per-class numeric TTLs — requires invented numbers plus an
  injectable clock; (b) client-supplied TTL per observation — new input surface, determinism depends
  on client values; (c) TTL for EPHEMERAL only — smaller surface but still invents a number.
- **Consequences:** no expiry-by-age behavior exists; invalidation must be explicit and mapped; reuse
  decisions are deterministic; a future decision may introduce TTLs without changing the fact model.

### A6 — Parse-completeness heuristic boundary

- **Status:** APPROVED
- **Decision:** a **bounded heuristic lexical scanner** with three frozen verdicts:
  `INCOMPLETE (DETECTED, heuristic)`, `NO INCOMPLETENESS DETECTED (heuristic — NOT proof of
  completeness)`, `UNDETERMINED (construct outside scanner capability)`. The scanner's recognizable
  construct list and its cannot-recognize list are both published (`03-V0.9-ARCHITECTURE.md` §6.4).
  The words *valid*, *complete*, and *proven* are forbidden as verdicts. PowerShell AST parsing
  remains a later-phase upgrade.
- **Rationale:** the MVP must detect incomplete commands, but the only apparatus able to prove
  completeness (the parser/AST) is explicitly deferred. A heuristic must therefore never masquerade as
  a parser, and its negative result must be reported as bounded.
- **Alternatives considered:** (a) a PowerShell 7 AST probe for true diagnostics — requires widening
  the probe boundary to run `pwsh` against arbitrary analyzed text, plus JSON marshalling and
  availability handling, and overrides a proposal phase deferral; (b) deferring detection entirely —
  fails DEC-046 and an acceptance criterion; (c) the approved scanner now with the AST as a documented
  later upgrade (chosen path).
- **Consequences:** false-negative risk is disclosed rather than implied away; `UNDETERMINED` must be
  emitted for out-of-capability constructs; a continuation state is classified as parse incompleteness,
  never as an execution failure.

### A7 — Validation output shape

- **Status:** APPROVED
- **Decision:** validation output uses the **shared summary-first convention**: a leading
  machine-readable `[SUMMARY]` block (tool, command size, per-analysis verdicts, mutation, verdict
  line) followed by fixed-order sections — Syntax, Parse completeness, Shell dialect, Native boundary,
  CWD, Path safety, Redundancy, Operation, Mutation, Encoding, Failure propagation, Stale-variable
  hazard, Cost, Capability duplication, Recommendation. Verdict tokens are exactly
  `ERROR | WARNING | INFO | PASS`. Output is rendered through the existing formatting layer and obeys
  the 4000/16000/200 budget contract.
- **Rationale:** the proposal's example output is human prose, but every existing tool in this
  repository renders summary-first structured output through one shared module; consistency, budget
  compliance, and testability all depend on following it. Warnings are kept proportional to evidence
  rather than escalating to errors.
- **Alternatives considered:** (a) prose-only output as illustrated in the proposal — requires a new
  renderer, breaks pagination/budget conventions, and is hard to assert; (b) JSON-only output —
  inconsistent with every other tool and bypasses shared budget logic; (c) summary-only — loses the
  per-analysis evidence the proposal's example exists to show.
- **Consequences:** the section order and token set are frozen; any added analysis must fit an existing
  section or be added by decision; determinism is mandatory (byte-identical repeat output).

### A8 — PowerShell 5.1 vs 7 baseline

- **Status:** APPROVED
- **Decision:** **dual baseline support.** Every dialect rule is tagged `ps5.1`, `ps7`, or `both`. The
  effective baseline comes from a client-declared shell version if present, otherwise from the
  server's machine shell-baseline probe, otherwise `unknown`. Only incompatibilities with the
  effective baseline are flagged; when the baseline is unknown, baseline-dependent rules emit **INFO,
  never WARNING** (S6). Explicitly detected 5.1-impossible constructs: `&&`/`||` chaining, ternary
  `? :`, `??`/`??=`, and `-Parallel`.
- **Rationale:** the proposal targets PowerShell 7, but the audit measured a Windows PowerShell 5.1
  host. A 7-only rule set cannot express the single most valuable finding on that host ("this requires
  7 but the baseline is 5.1"), and an unqualified warning would be noise.
- **Alternatives considered:** (a) PowerShell 7 only — most commands on a 5.1 host would raise
  baseline warnings; (b) client-declared baseline only — no machine view, everything degrades to INFO
  until the client declares; (c) a single "unknown" baseline — loses the highest-value warning class.
- **Consequences:** machine shell baselines are labeled as machine capability, never as the client's
  shell (S2); the baseline must accompany every dialect verdict; the rule table needs a baseline tag on
  every entry.

### A9 — Normalized duplicate definition

- **Status:** APPROVED
- **Decision:** a **deterministic four-level ladder** with no similarity measure:

  | Level | Normalization |
  | --- | --- |
  | `n0` | raw (outer whitespace trimmed only) |
  | `n1` | internal whitespace runs collapsed, tabs → space, ASCII case folded (narrow: documented as aggressive; non-ASCII untouched) |
  | `n2` | `n1` + single/double quote normalization **only** when the span contains no backtick, no `$` interpolation, no doubled-quote escape, and no embedded quote of the other kind |
  | `n3` | `n2` + `\`↔`/` inside path-like tokens, collapsed duplicate separators, drive-letter case normalization, and removal of one leading environment-establishing prefix when its target equals the known/declared repository root |

  Output is `duplicate (level nN) of <command-id>` plus reasons, or
  `no duplicate found (levels n0–n3 checked)`.

  Explicitly **not** normalized: alias equivalence (`ls` ↔ `Get-ChildItem`, `cat` ↔ `Get-Content`),
  abbreviated parameters (`-Recurse` vs `-r`), parameter reordering, `-ErrorAction` differences,
  here-string vs quoted string, `%` vs `ForEach-Object`, pipeline regrouping, and any similarity or
  distance metric.
- **Rationale:** "normalized duplicate" was undefined; fuzzy matching is untestable and risks
  suppressing necessary work with a false duplicate claim. A fixed ladder is deterministic, testable,
  and states its own limits.
- **Alternatives considered:** (a) exact-match only — misses genuine repeats and weakens redundancy
  value; (b) adding alias/parameter canonicalization — needs a maintained alias table (a second source
  of truth requiring drift protection) and raises false-positive risk; (c) AST/semantic equivalence —
  a later-phase capability requiring a new authority and a richer level vocabulary.
- **Consequences:** normalization is narrow and disclosed; a negative result must name the levels
  checked; the non-normalized list is part of the contract and must appear in the method line.

### A10 — Documentation package

- **Status:** APPROVED
- **Decision:** the V0.9 documentation package is the **ten-file** package (`00`–`09`, plus the
  unchanged proposal), which treats the implementation audit and the architecture as first-class
  artifacts. The proposal's own §41 nine-file list is recorded as superseded for package layout only.
  The original proposal remains in place and authoritative for content. No consolidated-coverage file
  is created, because no predecessor package is being retired.
- **Rationale:** the executing instruction (newer than proposal §41) explicitly requires an
  implementation audit and an architecture document in the package, and the audit is the required
  first deliverable rather than a section of the plan.
- **Alternatives considered:** (a) the proposal's nine-file list — folds the audit into the plan and
  drops a separate architecture document, removing two first-class artifacts the authorization
  requires; (b) a single consolidated document — loses the per-document traceability maintained since
  V0.5.
- **Consequences:** the package contains ten new documents plus the proposal; the numbering difference
  from proposal §41 is recorded in `00` §1; the proposal is not renamed to `00-V0.9-MASTER.md`, since it
  must remain unchanged.

### A11 — Phased tool registration

- **Status:** APPROVED
- **Decision:** register the ten tools in **phases with an explicit checkpoint each**, never as a
  single release: P2 registers `environment`, `terminal`, `context`, `capabilities` (24 → 28);
  P4 registers `validate`, `observe` (→ 30); P5 registers `plan`, `prepare`, `history`, `next`
  (→ 34); P6 only verifies. `lint` stays a `mcquest_shell_validate` mode; no separate lint tool.
- **Rationale:** V0.8 shipped with per-tool authorization discipline, the executing instruction
  requires small independently testable increments, and a ten-tool release has a large blast radius
  for registration, schema, and documentation changes.
- **Alternatives considered:** (a) a single 10-tool release — one authorization, larger blast radius,
  harder to bisect or revert; (b) analyzers with no tools — no client-visible surface, leaving the
  approved surface unrealized; (c) only the first three tools, deferring the rest indefinitely — the
  declared decision surface would be only partially realized and routing/recovery criteria unproven.
- **Consequences:** the registration-count test changes in three separate phases; documentation must
  describe the phase of each tool; no tool may be registered ahead of its phase.

### A12 — Capability registry authority

- **Status:** APPROVED
- **Decision:** the registered tool set (`EXPECTED_TOOLS`) remains the **single authority** for which
  capabilities exist. The V0.9 registry adds only intent metadata (`{name, purpose, intent_tags[],
  scope, mutation_cost}`) and is protected by three drift tests:

  1. **exact set equality, both directions** between the registry and `EXPECTED_TOOLS` — an orphan
     registry row and an unregistered tool both fail;
  2. **live-server equality** — registry == the tools actually exposed by the running server
     (`list_tools()`);
  3. **field/tag discipline** — every intent tag comes from a frozen enum (the operation taxonomy plus
     capability classes), every purpose is non-empty, and registry order is deterministic.

  The registry may never become a second hand-maintained name list.
- **Rationale:** capability facts already exist as registrations plus a pinned test list; a separate
  registry would silently drift. Keeping the pinned list authoritative while the registry adds only
  routing tags preserves a single source of truth and makes routing testable.
- **Alternatives considered:** (a) runtime introspection only — zero drift, but no intent tags, so
  routing would keyword-match today's multi-sentence descriptions with much weaker quality;
  (b) making the registry authoritative and deriving `EXPECTED_TOOLS` from it — fewer lists but it
  rewrites an existing pinned test's contract and inverts authority; (c) hardcoding routing inside the
  planner — untestable and drifts silently.
- **Consequences:** registry rows must be updated in the same phase as any tool addition; routing
  quality depends on tag quality; drift failures are hard errors, not warnings.

### A13 — Recommendation vs execution boundary

- **Status:** APPROVED
- **Decision:** V0.9 is **recommend-only**: it never executes a client command, never mutates the
  repository or shell state, and never enforces a policy (no blocking or denying). `shell_prepare` may
  emit a complete corrected command **as text**, explicitly labeled as not executed. The approved
  read-only probes (A3) are the only server-side execution and are always labeled as server-side
  machine facts.
- **Rationale:** the proposal keeps Cline as the execution authority and lists autonomous execution,
  automatic repository modification, and sandboxing as non-goals or later phases. Removing an
  execution path entirely also removes a whole class of risk from the MVP.
- **Alternatives considered:** (a) allowing arbitrary execution — violates the non-goals and the
  read-only design; (b) allowing denial/enforcement — needs a policy source of truth and a blocking
  contract, and turns V0.9 into an authority rather than an advisor; (c) auto-applying "safe"
  corrections — grants mutation authority, which no current authorization permits.
- **Consequences:** no execution, mutation, or policy code path may exist in the codebase (test I3–I5);
  recommendations must be phrased as suggestions; the read-only source-level invariant continues to
  hold across the new package.

### A14 — Observation ingestion from other MCQuest tools

- **Status:** APPROVED
- **Decision:** observation ingestion happens through an **explicit ingest shape** on
  `mcquest_shell_observe`:

  ```text
  kind: observation | command
  name: <namespace>.<fact>            e.g. mcquest_search.total, locale.quiz.loading.si
  value: <string>
  scope: REPOSITORY | WORKTREE | FILE | SESSION | PROCESS | EPHEMERAL
  subject: <path | capability | query>            (optional)
  source: <tool or command that produced it>
  recorded_at_source: SERVER | CLIENT             (provenance, immutable)
  client_session / client_process_id              (required for SESSION/PROCESS/EPHEMERAL)
  ```

  Rules: tool-derived evidence (search totals, locale rows, diagnostics summaries) is ingested as
  `SERVER_OBSERVED` and may take only `REPOSITORY`/`WORKTREE`/`FILE` scopes; `SESSION`/`PROCESS`/
  `EPHEMERAL` ingestion requires a declared client identity and is always `CLIENT_DECLARED`; **no
  numeric confidence field exists**; the call returns the stored observation id, scope, freshness
  class, and the invalidation set it replaced. No other tool's output is intercepted or wrapped.
- **Rationale:** without an ingest path, V0.9 cannot know that a question was already answered by an
  existing capability, so redundancy detection, routing, and the "unnecessary duplicating scan" metric
  would be unmeasurable. An explicit shape keeps provenance honest and avoids touching V0.8 code.
- **Alternatives considered:** (a) no ingestion — redundancy detection limited to V0.9-initiated work;
  (b) automatic interception/wrapping of other tools' output — requires modifying every existing tool
  (forbidden by the additive rule) and hides provenance; (c) a free-form client evidence blob —
  unverifiable and breaks the observation schema.
- **Consequences:** `FILE` scope becomes part of the scope vocabulary for tool-derived evidence only;
  ingestion is read/write to the in-memory store only; process-scoped ingestion without a declared
  identity must be rejected rather than guessed.

## 3. Cross-cutting approved sub-decisions S1–S6

### S1 — Cold-start behavior

- **Status:** APPROVED
- **Decision:** with nothing declared, V0.9 runs in **degraded mode**: it reports
  `CWD: unknown / source: UNKNOWN / trust: untrusted` plus the directive to establish repository
  context or use an explicit path. It does **not** fail loudly.
- **Rationale:** the proposal's own multi-terminal example prescribes exactly this directive, and a
  hard failure would make every first call unusable.
- **Alternatives considered:** fail-loud when CWD is unknown; guessing the server's CWD.
- **Consequences:** degraded mode must be a first-class, well-tested output path (test E1); no command
  validation may claim CWD-dependent safety while the CWD is unknown.

### S2 — Server-owned process facts

- **Status:** APPROVED
- **Decision:** the server's own CWD, PID, console code page, and shell are recorded only under a
  labeled `mcp_server` subject and are never emitted as the client's terminal facts.
- **Rationale:** the server process is a different execution context; presenting its values as the
  client's would be a false fact.
- **Alternatives considered:** treating the server's CWD as a fallback for the client's CWD.
- **Consequences:** every output line requires an explicit subject; tests E6 and T3 enforce it.

### S3 — Restart semantics

- **Status:** APPROVED
- **Decision:** server restart and client/terminal restart discard SESSION and PROCESS facts, which
  then report `unknown`. Nothing carries over.
- **Rationale:** identity-keyed facts cannot survive the loss of the identity they were keyed to.
- **Alternatives considered:** carrying facts forward as "likely still true".
- **Consequences:** no cross-restart reuse; tests S5–S7 enforce it.

### S4 — Parse verdict vocabulary

- **Status:** APPROVED
- **Decision:** the parse verdict vocabulary is frozen to the three A6 values; the words *valid*,
  *complete*, and *proven* are forbidden as verdicts.
- **Rationale:** a heuristic cannot prove completeness; vocabulary must not imply it can.
- **Alternatives considered:** a two-value vocabulary (incomplete/complete) — implies a proof the
  scanner cannot deliver.
- **Consequences:** test P10 enforces the vocabulary; `UNDETERMINED` is mandatory for out-of-capability
  input.

### S5 — Registry authority

- **Status:** APPROVED
- **Decision:** the registered tool set is authoritative; the V0.9 registry contributes intent metadata
  only, enforced by the A12 drift tests.
- **Rationale:** one source of truth prevents silent divergence between capability facts and routing.
- **Alternatives considered:** a registry that itself defines the surface.
- **Consequences:** any tool addition requires a registry update in the same phase; drift is a hard
  failure.

### S6 — Unknown baseline

- **Status:** APPROVED
- **Decision:** when the effective shell baseline is unknown, baseline-dependent dialect rules emit
  **INFO**, never WARNING.
- **Rationale:** a warning must be proportional to evidence; an unverifiable baseline cannot support a
  warning.
- **Alternatives considered:** emitting WARNING anyway (noise) or suppressing findings entirely (lost
  signal).
- **Consequences:** test D6 enforces INFO; the reported verdict states that the baseline is unknown.
