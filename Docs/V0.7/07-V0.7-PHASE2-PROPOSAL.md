## 1. Observed problem

Coding agents answering repository-evidence questions like "list the
hardcoded user-visible strings in `TeacherDashboard.tsx`" have **no
precise deterministic MCQuest operation** and must instead:

1. construct an ad-hoc regex (e.g. `"[^"]+"|'[^']+`) via
   `mcquest_search`, which also matches imports, comments, syntax;
2. acquire unnecessarily broad evidence (one snippet per matching
   line, plus context lines, across many files at directory scope);
3. repeat follow-up `mcquest_read_file` calls per hit to recover the
   exact literal, quote style, column;
4. filter client-side with non-deterministic, unbounded ad-hoc logic.

`TeacherDashboard.tsx` is a **hypothesis/example** of this workflow
class (literal-inventory), not a predetermined solution and not a
claim that file exists here (it does not — §2.3).

## 6. Recommended primary target

**Phase 2 — Literal Evidence: new read-only tool
`mcquest_find_strings`** — a bounded, deterministic inventory of
string literals in supported JS/TS/JSX/TSX source.

This is a **lexical literal-inventory primitive, not a
hardcoded-UI-string detector**. It finds quoted JS/TS string
literals. It does NOT classify UI semantics, does NOT extract JSX
text nodes, and does NOT claim to find "all hardcoded UI strings"
(see §7 scope clarifications and §8A Phase 3 reservation).

One-sentence contract: *given a project-relative file or directory,
return every quoted string literal as structured
`path:line:col: "value"` evidence, summary-first, explicitly paged,
deterministically ordered, under 4000/16000/200.*

Why smallest useful change: reuses 100% of existing machinery
(walk, `resolve_project_path` + `is_ignored_path` +
`MAX_FILE_BYTES`, two-pass honest counting, `heapq.nsmallest`
paging, `search_block` rendering, 200-char clip). One additive tool;
no existing-tool changes, no index, no parser dep, no embeddings, no
execution, no generated-artifact access, no broad-language expansion.
Converts the worst workaround (ad-hoc regex + N reads + client

filter) into **one paged call chain** with literal-grade precision.

## 7. Exact contract (pre-implementation; normative on approval)

**Phase 2 scope clarification (binding).** `mcquest_find_strings`:

- finds **quoted JS/TS string literals** (lexical primitive);
- supported source extensions: **`.js`, `.jsx`, `.ts`, `.tsx`** only;
- **JSX text nodes are OUT OF SCOPE for Phase 2** (bare text between
  JSX tags is never emitted);
- **UI semantics are OUT OF SCOPE for Phase 2** (no user-facing /
  hardcoded-UI classification);
- results are **literal inventory, not UI classification**;
- a **zero-result response MUST NOT be interpreted as proof that no
  hardcoded user-facing UI text exists** (JSX text, unquoted,
  concatenated, or excluded-scope text may exist);
- **Phase 3** (`mcquest_find_ui_strings`, tentative, RESERVED ONLY —
  §8A) is the future place for UI-aware candidate detection.

### 7.1 Inputs

| Param | Type | Default | Bounds/validation |
|---|---|---|---|
| `path` | `str`, project-relative file OR directory | `frontend/src` | non-empty; `resolve_project_path`; nonexistent → `FileNotFoundError(path)`; traversal → `ValueError` |
| `file_pattern` | `str` basename glob (directory mode only) | `*` | `fnmatch` on basename, same as `search` |
| `min_length` | `int` minimum literal length (suppresses `""` noise) | `1` | `0..100`, else `ValueError` |
| `max_results` | `int` page size | `50` (`SEARCH_DEFAULT_RESULTS`) | clamped `1..500` (`MAX_SEARCH_RESULTS`) |
| `offset` | `int` 0-based continuation | `0` | `>= 0` else `ValueError`; `offset > total` → empty page, truthful summary |

No `case_sensitive` (literals returned verbatim; no predicate).

Literal definition (v1, lexical — NOT an AST): a maximal
single-line run of `'...'`, `"..."`, or `` `...` `` content scanned
left-to-right per line with backslash escapes honored (`\'`, `\"`,
`` \` ``, `\\`) so escaped delimiters never terminate the literal.
Reconciliation note: this wording supersedes any earlier looser
"no-unescaped-newline" phrasing — semantics are unchanged (single-line
lexical scan, escapes honored), now stated exactly. Template literals
(Phase 2 exact behavior):
- **static literal segments are candidates** — each maximal static run
  between backtick boundaries or `${` / `}` delimiters is emitted as
  its own literal item;
- **`${...}` expressions are not themselves treated as literal text**
  — the `${`, expression contents, and matching `}` contribute no
  literal characters (the scanner resumes the static run after `}`);
- **nested quoted literals inside `${...}` remain independently
  discoverable where applicable** — e.g. `` `a${"b"}c` `` yields
  static segments `a`, `c` plus the nested `"b"` literal at its own
  `(line,col)`, all ordered by `(path,line,col)`;
- **empty segments are not emitted** — zero-length static runs
  (e.g. adjacent `` `${x}` `` boundaries, empty `""` unless admitted
  by `min_length=0`) produce no item;
- **escaped delimiters are handled correctly** — `\`` inside a
  template (and `\'` / `\"` in their quote kinds, `\\` generally)
  never open/close/terminate a literal;
- **reported columns remain deterministic** — `col` is the 1-based
  column of the segment's opening delimiter (backtick for template
  head-segments, `}` for post-expression static segments); ordering
  stays `(relative_path ASC, line ASC, col ASC)`.

**Comments (explicit).** Phase 2 is lexical rather than AST-based.
No comment parser or AST dependency is added to exclude comments.
Consequence (binding): **quoted literals inside comments (line or
block) may be returned** as literal items; callers MUST NOT treat
results as code-only. Docstring/code distinction is a non-goal (§8).

### 7.2 Outputs

Summary-first via existing `search_block`: `[SUMMARY]` with
`tool=mcquest_find_strings`, `PATH`, `total`, `files_affected`,
`returned`, `max_results` (echoed effective page size),
`offset`, `next_offset`, `has_more`, `truncated`,
`collection_complete=true` (two-pass honest count), `budget`
(4000/16000 + `expanded` when `offset>0 or max_results>50`).
Unambiguous field semantics (V0.6 preserved):
- `total` = total **matching literals** within the requested bounded
  repository scope, **independent of page size**;
- `returned` = literals on this page (bounded by ceiling);
- `max_results` = echoed effective page size (post-clamp 1-500);
- `offset` = requested 0-based start index into the total ordering;
- `has_more = (offset + returned) < total`;
- `next_offset = offset + returned`, present iff `has_more`;
- `truncated = true` iff the ceiling omitted in-page items;
- `collection_complete = true` always (two-pass honest count) = total
  authoritative, NOT all items delivered (P004/P005).
`[EVIDENCE]`: one line per literal, exact shape
`<relative>:<line>:<col>: "<value>"` where `col` is the 1-based
column of the opening quote and `<value>` is raw content without
surrounding quotes (200-char `…` clip via existing rule).

### 7.3 Scope

Read-only investigation only. Root-confined
(`resolve_project_path`); ignore-policy enforced
(`IGNORED_DIRECTORIES`, `IGNORED_EXTENSIONS`, `is_ignored_path`);
`MAX_FILE_BYTES` (2,000,000) skip honored. No writes, execution,
network, or index persistence.

### 7.4 Supported file types

v1: **`.ts`, `.tsx`, `.js`, `.jsx` only** — identical set to
`find_imports`/`find_usages`/audit code path. Smallest scope for the
example class; no broad-language expansion (P006). Python/CSS/JSON/
Markdown modes are non-goals (§8).

### 7.5 Limits

Default page 50; hard cap 500; no context lines (items are
self-contained). Normal ≤4000 / ceiling ≤16000 / per-line ≤200;
atomic item emission (drop whole over-budget literal, never split) —
all via existing `search_block`/`OutputBudget`.

### 7.6 Pagination / truncation semantics

Two-pass count (pass 1 authoritative `total`/`files_affected`,
`collection_complete=true` always; pass 2 bounded page via
`heapq.nsmallest(offset+page_size)` + slice).
`has_more = (offset+returned) < total`;
`next_offset = offset+returned` iff `has_more`; `truncated=true` iff
ceiling omitted items. Page 2 NEVER automatic (D008). P004/P005 hold:
`collection_complete=true` + `has_more=true` = "total known, page
partial" — never claim complete while `has_more`/`next_offset` /
`returned<total`.

### 7.7 Deterministic ordering

Global `(relative_path ASC, line ASC, col ASC)`; byte-identical
repeats (D009). Never raw `os.walk` order.

### 7.8 Failure behavior

| Condition | Behavior |
|---|---|
| `path` missing/empty | `ValueError` |
| `path` nonexistent | `FileNotFoundError(path)` (matches `search`) |
| `path` escapes root | `ValueError` |
| ignored/unreadable/oversized | skipped (dir walk) or `validate_readable_file` error (single file) |
| `offset<0`, bad `min_length`/`max_results` | `ValueError` |
| binary/undecodable bytes | `errors="replace"` scan; no crash |
| multi-line template literals | only single-line segments in v1 (documented); no error |

## 8. Explicit non-goals (rejected)

1. Semantic/vector/embeddings/summarization/indexing (P006; no need).
2. Broad language support — v1 `.js`/`.jsx`/`.ts`/`.tsx` only;
   expansion needs its own measured proposal.
3. AST infrastructure, tree-sitter, language-server integration,
   AST string resolution (concatenations, constants, i18n keys).
4. Comment parser to exclude comments; docstring stripping;
   JSX-text-node extraction (reserved for Phase 3); CSS inventory.
5. `pattern_audit` string category (wrong home; enum stays layout).
6. Import/usage language expansion, diagnostics semantic expansion,
   execution tools, generated-artifact access, background indexing,
   repository indexing, `format=json`/`_meta`/file artifacts.
7. AI/LLM classification, semantic search, vector search, embeddings.
8. Weakening security/path boundaries in any form.
9. OBS-1 rewording beyond the new tool's own description — not a
   target.
10. Phase 3 UI-aware implementation of any kind (reserved §8A only).

## 8A. Phase 3 reservation — UI-aware Evidence (RESERVED ONLY)

Phase 3 is **reserved only** for a separate higher-level capability,
tentatively named `mcquest_find_ui_strings`. It is NOT authorized,
NOT implemented, NOT part of the Phase 2 release gate, and carries
NO implementation scope beyond this reservation note.

- Tentative purpose (if ever authorized): identify likely
  user-facing hardcoded string candidates using lightweight
  deterministic rules **over the Phase 2 literal evidence**.
- Architectural direction only (no implementation now):
  `source → literal inventory (Phase 2) → UI-aware candidate
  classification (Phase 3)`. A future Phase 3 MUST build
  conceptually on Phase 2 rather than introduce an independent large
  analysis subsystem.
- Phase 3 does not change Phase 2 semantics: Phase 2 results remain
  literal inventory, never UI classification.
