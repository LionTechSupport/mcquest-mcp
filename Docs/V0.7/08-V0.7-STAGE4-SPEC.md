## 1. Purpose and evidence basis

### 1.1 Purpose (proposed)

A narrow, read-only, **metadata-only** inventory of React component
**candidates** in `.js`, `.jsx`, `.ts`, `.tsx` source, returning for each
candidate its **file, line, name and kind** only. It exists to let an agent
answer "which components exist here, and where" in one bounded, paged call
instead of an ad-hoc regex over `mcquest_search` plus client-side filtering
(the workaround pattern documented in `07-V0.7-PHASE2-PROPOSAL.md` §1).

## 2. Scope

### 2.1 In scope (proposed)

- One new read-only MCP tool, provisionally `mcquest_component_inventory`
  (Q5; §11).
- Extension surface: **`.js`, `.jsx`, `.ts`, `.tsx`** (Q2) — identical to the
  established v1 source surface used by `mcquest_find_strings`,
  `mcquest_find_usages`, `mcquest_find_imports` and `mcquest_diagnostics`
  (`07-V0.7-PHASE2-PROPOSAL.md` §7 scope clarification; `diagnose.js:103-111`).
- Directory scope (bounded walk) **or** an explicit single file (§6).
- Emitting **lexical candidates** carrying `path:line` + `name` + `kind` (Q3).
- Deterministic ordering, bounded paging, honest completeness reporting
  (§5, §7, §8).

### 2.2 Out of scope — explicit non-goals (Q3, Q4; binding)

The tool MUST NOT emit, infer, resolve, or claim any of:

1. **props or parameters** — no prop list, param list, or signature detail;
2. **types** — no prop types, generics, interfaces, or TypeScript types;
3. **resolution** — no import resolution, aliasing, module graph, re-export
   following, or "where is this component used";
4. **defaults** — no default prop values or default parameters;
5. **runtime behavior** — not what renders, conditional rendering, or effects;
6. **JSX text** — bare text between JSX tags is never extracted;
7. **UI-string extraction or UI classification of any kind** — this is the
   **Phase 3 reservation** (`07-V0.7-PHASE2-PROPOSAL.md` §8A), which remains
   RESERVED / NOT AUTHORIZED;
8. **AST/parser-grade analysis** — no TypeScript compiler, no
   `src/mcquest_mcp/ts/diagnose.js` invocation, no tree-sitter, no language
   server (Q4; the `07-…PROPOSAL.md` §8.3 rejection class stays in force);
9. **semantic/vector search, embeddings, summarization, indexing**
   (`01-V0.7-CONTRACT.md` P006:44-46);
10. **execution tools, generated-artifact access, network access, writes**
    (P006; `00-V0.7-MASTER.md` §4:114-122);
11. **language expansion** beyond `.js/.jsx/.ts/.tsx` — no `.vue`, `.svelte`,
    `.mjs`/`.cjs`, etc. (`07-…PROPOSAL.md` §8.2);
12. **`format=json`, `_meta`, file-backed artifacts**
    (`00-V0.7-MASTER.md` §4:122);
13. **broadening the recognition rules to raise recall** — forbidden without a
    new user decision (see `O-6` in §13).

## 3. Operational definition of a component candidate and `kind`

### 3.1 Definition (Q2, Q4)

A **component candidate** is a *lexical* declaration of a **function-like or
class-like named value whose name begins with an uppercase ASCII letter**,
found at a declaration site in a `.js`/`.jsx`/`.ts`/`.tsx` file.

Q2 fixes the scope as **React function/class component declarations**
(Q2 selection). Q4 fixes the method as **lexical scanning only** — therefore:

> **A "component candidate" is a lexical candidate, not a verified React
> component.** It is a *name at a declaration site* whose shape is consistent
> with a component declaration. It may be a **false positive** (a
> non-component thing that looks like one) and the scan may produce **false
> negatives** (a real component it does not recognize). Both classes are
> mandatory documented output semantics (§3.4, §9, §13) — see `O-6`.

### 3.2 Proposed recognition rules (q.v. §4 for the exact rule text)

| Rule | Declaration form (single physical line) | Emitted `kind` |
|---|---|---|
| `R-1` | `function Name(` (incl. `export function Name(`) | `function` |
| `R-2` | `class Name` (incl. `export class Name`) | `class` |
| `R-3` | `const Name = (` … `=>` (arrow) | `arrow` |
| `R-4` | `const Name = function` (function expression) | `function` |
| `R-5` | `const Name = async (` … `=>` / `= async function` | `arrow` / `function` |
| `R-6` | `export default function Name(` / `export default class Name` | `function` / `class` |

In `R-1`…`R-6`, `Name` MUST match `[A-Z][A-Za-z0-9_]*` **case-sensitively**.

**`O-23` — Q2 scope-inclusion (APPROVED 2026-09-18 — DEC-013 updated, DEC-014).** Q2's selected
scope is "React function/class component declarations", but the rules above
include `R-3`–`R-5` — **variable declarations whose initializer is a function
value** (`const Name = () => …`, `= function`, `= async …`), which are not
literally function/class *declarations*. §3.1's operational definition
("function-like or class-like named value") also reads as including them.
Decide explicitly whether the inventory includes:

- (a) **function and class declarations only** (`R-1`, `R-2`, `R-6`); or
- (b) **those declarations plus function-valued variable declarations**
  (`R-3`–`R-5`).

Either way, lexical scanning **cannot prove a candidate is actually a React
component** — this decision concerns shape *coverage*, not verification. Phase
A does not silently reconcile this; it remains an explicit contract choice
(see `O-23` in §14).

**APPROVED RESOLUTION (2026-09-18).** The user approved the following for
`O-23` (recorded in DEC-013, updated, and DEC-014):

- **Include** function-valued variable declarations for **exactly** the forms
  covered by `R-3`–`R-5`.
- Do **not** add any initializer shapes beyond those rules.
- Treat matches as **lexical candidates**; do **not** claim React identity.

### 3.3 Mandatory false-positive exclusions (lexical guards)

These exclusions are **required** by the Q4 lexical-honesty requirement and by
the repository-native evidence in §1.2:

- **`E-1` Case guard.** The name must begin with **uppercase ASCII**; checked
  case-sensitively. Excludes `function main`, `function emit`, `const fs`,
  `let ts` (all observed in `diagnose.js`; see §1.2).
- **`E-2` Function-value guard (variable forms only).** For `R-3`…`R-5` the
  **initializer on the same line must be function-like** (`= (`, `= async`,
  `= function`). This is the guard that **excludes the repository's only
  capitalized declaration-site match**: `diagnose.js:144 const MAX_EMITTED =
  500;` — an uppercase constant holding a *number*, not a function.
- **`E-3` Non-function initializer guard.** `const Name = require("...")`,
  `= 42`, `= []`, `= {}`, `= Symbol(...)`, `= class extends X {}` (class
  expression — see `O-7`) MUST NOT qualify.
- **`E-4` No name ⇒ no candidate (default).** Under Q3 the emitted row
  requires a `name`. Anonymous declarations therefore cannot be reported as
  named candidates; whether they are reported at all is `O-3`.

### 3.4 What is NOT recognized (documented false negatives; no re-broadening)

Explicitly **not** recognized in this scope (each is a documented false
negative, **not** a bug to be silently fixed):

1. lowercase-named components (`function helper()` used as JSX in JSX-land);
2. higher-order component wrappers — `memo(...)`, `forwardRef(...)`,
   `connect(...)`, `withRouter(...)` — see `O-4`;
3. legacy `React.createClass({...})`;
4. re-exported/aliased components (`export { X as Y }`);
5. components declared **across multiple physical lines** — see `O-5`;
6. destructured or assigned-after-declaration components
   (`let X; X = () => ...`);
7. class components without a recognizable declaration-site form;
8. components in comments or strings are *emitted if they match* (the lexical
   limitation runs the other way — see §9).

**Prohibition (binding):** none of the above may be *added* to raise coverage
without a new explicit user decision (`O-6`; §2.2(13)).

### 3.5 `kind` vocabulary — APPROVED (2026-09-18)

The approved vocabulary is **`{function, arrow, class}`**. Q3 requires
name+kind but does not prescribe the vocabulary; the set was fixed by user
approval of `O-3` (DEC-013 updated, DEC-014). There is **no `default` kind** in
v1.

**`O-3` — `kind` vocabulary (APPROVED 2026-09-18).** (a) `arrow` is distinct
from `function`; (b) `class` is emitted for *any* `class Name` matching the
lexical rule, with no React-base-class gate; (c) anonymous `export default`
declarations are skipped — no placeholder name and no `default` kind are
introduced.

- **(a)** Use a distinct `arrow` kind for matched arrow-function variable
  declarations and `function` for matched ordinary function forms. Do **not**
  change the existing recognition patterns.
- **(b)** Emit `kind: "class"` for **any** class matching the existing lexical
  class recognition rule. Do **not** add a React-base-class gate. This does
  **not** mean every class is reported.
- **(c)** Skip anonymous default declarations. Do **not** introduce placeholder
  names.

## 4. Lexical recognition rules

### 4.1 Line model

- The scan is **line-oriented**: patterns are applied to **single physical
  lines**, one file at a time. A declaration split across physical lines is
  not matched (see `O-5`).
- Line numbers are **1-based** and refer to the physical line where the
  declaration-site keyword occurs.
- Matching is performed against the **full line text**. The 200-character
  per-line clip (`config.py:96`) is an **output/rendering** concern and MUST
  NOT be applied before matching (matching on clipped text would silently drop
  matches).
- The scan is **textual**: decoding failures are handled per §6.5, and no
  parse/parse-error concept exists (there is no parser).

### 4.2 Case sensitivity

All name recognition is **case-sensitive** with an **ASCII uppercase** first
character. This is load-bearing: the §1.2 measurement shows a case-insensitive
search yields 30 noise matches versus 1 real one on the same file.

### 4.3 Normative patterns (specification-level)

`NAME` denotes a capture matching `[A-Z][A-Za-z0-9_]*`, matched
case-sensitively, bounded by word boundaries.

| Rule | Normative condition (single line) |
|---|---|
| `R-1` | an optional `export` / `export default` prefix, then `function` `NAME` `(` |
| `R-2` | an optional `export` / `export default` prefix, then `class` `NAME` (optionally followed by `extends` …) |
| `R-3` | `const` `NAME` `=` (optional `async`) then a parenthesized or bare parameter list followed by `=>` on the same line |
| `R-4` | `const` `NAME` `=` (optional `async`) `function` (optionally named) |
| `R-5` | as `R-3`/`R-4` with the `async` keyword present |
| `R-6` | `export default function NAME(` / `export default class NAME` |

Guards `E-1`…`E-4` (§3.3) apply unconditionally: a match that fails any guard
is **not** a candidate.

Note: the **inclusion of `R-3`–`R-5` in scope** (function-valued variable
declarations) is **approved** (`O-23`, 2026-09-18 — DEC-013 updated, DEC-014;
§3.2).

### 4.4 Comments and strings — NOT stripped (v1 limitation)

Per `07-V0.7-PHASE2-PROPOSAL.md` §8.4, comment/string stripping is an
explicitly rejected work item (it requires a real parser). Therefore in v1:

- a declaration-shaped match **inside a line comment or block comment** is
  emitted as a candidate;
- a declaration-shaped match **inside a string/template literal** is emitted as
  a candidate;
- no `kind` refinement, no "probable" flag, and no suppression is applied.

This is a **documented false-positive source**, not a defect, and must be
stated in the tool description and in the zero-result wording (§8).

### 4.5 TypeScript declarations and type-only forms

`.ts` includes `.d.ts`, where application code does not exist but declarations
of components may be described. Forms such as `declare function Name(): void;`
or `export declare const Name: React.FC<Props>;` are **not** runtime component
declarations.

**APPROVED (`O-8`, 2026-09-18 — DEC-014):** `.d.ts` files are **excluded by
suffix** (option (b)); they are not candidate files. `declare`-form
declarations inside a non-`.d.ts` `.ts` file **remain matched** as documented
residual false positives in v1 — no `declare`-form exclusion guard is added.

## 5. Output schema and deterministic ordering

### 5.1 Row schema (Q3)

Exactly **four** identity components per row: **relative path, line, name,
kind** — nothing else. Q3 fixes the row as `path:line:name` plus `kind`, and
explicitly excludes props/types/resolution/defaults/runtime/JSX-text/UI-strings
(§2.2).

**Row rendering (approved `O-9`):**
`<relative_posix_path>:<line>: <Name> (<kind>)`
e.g. `src/ui/Widget.tsx:12: Widget (function)`

- Path rendering follows the established convention: relative POSIX path
  (see `tests/conftest.py:48` for the established `os.sep → "/"` normalization).
- Rendering is **display only**. Internal identity and ordering are
  `(relative_path, line, name, kind)` and MUST NOT depend on the rendered
  string; the 200-char atomic clip may clip the rendering (per
  `00-V0.7-MASTER.md` §4:112) without changing identity, ordering, `total`, or
  `collection_complete`.

**APPROVED (`O-9`, 2026-09-18 — DEC-014):** the row string is
`<relative_posix_path>:<line>: <Name> (<kind>)` (e.g.
`src/ui/Widget.tsx:12: Widget (function)`).

### 5.2 Summary fields (Q9 accounting model)

Following the established `search_block` summary convention, the response
carries at minimum:

| Field | Meaning |
|---|---|
| `tool`, `path` | identity of the call |
| `total` | exact count of candidate rows in scope, **iff** the scan is complete; otherwise the count found so far — see §7.3 |
| `files_affected` | number of files contributing ≥ 1 candidate row |
| `offset`, `has_more`, `next_offset` | explicit pagination (page 2 is never automatic; `00-V0.7-MASTER.md` §4:113) |
| `collection_complete` | `true` **only** under the exact conditions in §7.3; never implies every row was delivered (`01-V0.7-CONTRACT.md` P005:40-42) |
| `truncated` | renderer-only aggregate omission signal (does not affect `collection_complete`) |

**Disclosure fields — NOT APPROVED (`O-24`).** The "number of files scanned"
and "number of in-scope files skipped for a reason (unreadable / oversized /
decode)" fields are **proposed only** and MUST NOT appear as implicitly
approved public output. Whether they are adopted is an open decision (`O-24`)
**linked to the existing accounting decisions** `O-13` (decode handling),
`O-15` (files-analyzed cap) and `O-17` (row caps): these fields exist only to
make §7.3 checkable and are not independently justified output. No new public
field is added to this draft without explicit user approval.

### 5.3 Deterministic ordering

Global sort key, ascending, applied before capping and paging:

`(relative_path ASC, line ASC, name ASC, kind ASC)`

- `relative_path` compared as **byte order** on the relative POSIX path — the
  established determinism rule (`00-V0.7-MASTER.md` §4:114;
  `07-…PROPOSAL.md` §7.7:307-310). Raw filesystem walk order MUST NOT leak.
- `line` ascending, 1-based.
- `name`, `kind` are the final tie-breakers so that multiple candidates on one
  line and byte-identical repeats still have a total order.

**APPROVED (`O-10`, 2026-09-18 — DEC-014):** (a) a single line may yield
**multiple distinct** candidates and **all are emitted**; (b) rows that are
**byte-identical** in all four identity components are **deduplicated** — one
row per `(path, line, name, kind)` tuple.

## 6. Input, path, and error behavior

### 6.1 Parameters (proposed)

`mcquest_component_inventory(path=".", file_pattern="", max_results=50, offset=0)`

- **No `reference` parameter** — Q7 selects **single-scan only**; there is no
  comparison mode and therefore no eligibility/omission model of the Stage 3
  kind (§7.3).
- `max_results`: default 50, hard cap 500 — the established search convention
  (`config.py:74`, `config.py:85`), not invented here.

**APPROVED (`O-11`, 2026-09-18 — DEC-014):** the parameter set is
`(path=".", file_pattern="", max_results=50, offset=0)` (default `max_results`
50, hard cap 500). **No** `kind=` narrowing filter is added in v1.

### 6.2 Directory mode

- Bounded walk rooted at the resolved `path`, honoring
  `IGNORED_DIRECTORIES` (`config.py:29-45`) via `is_ignored_path`
  (`security.py:33-41`).
- Candidate files are limited to the **extension allowlist**
  `.js/.jsx/.ts/.tsx` (§2.1); all other files are out of scope by design.
  `.d.ts` files are excluded by suffix (`O-8`, approved).
- If `file_pattern` is supplied, it is applied to the **basename**
  (established convention: `tools/locales.py:404`, `fnmatch`-style globbing).
  Empty `file_pattern` = the extension allowlist only.
- Symlink safety and root confinement are preserved exactly as in existing
  tools (`security.py`; `00-V0.7-MASTER.md` §4:115-117).

### 6.3 Single-file mode

- An explicit `path` naming a file is scanned directly after validation.

**APPROVED (`O-12`, 2026-09-18 — DEC-014):** an explicit single-file `path`
whose extension is **outside the supported set** (`.js/.jsx/.ts/.tsx`;
`.d.ts` excluded per `O-8`) is **rejected** with `ValueError` (extension not
in scope). This deliberately diverges from Stage 3 audit concern **C1** (where
an explicit non-`.json` path was analyzed rather than rejected); strict-scope
behavior is chosen for Stage 4.

### 6.4 Path validation and errors (established conventions; cited)

These mirror the existing tools exactly and introduce no new security surface
(`00-V0.7-MASTER.md` §4:121):

| Condition | Required behavior | Source of convention |
|---|---|---|
| empty/missing `path` | `ValueError("Path cannot be empty.")` | `security.py:17-18` |
| `path` nonexistent | `FileNotFoundError(path)` | `07-…PROPOSAL.md` §7.8:317; matches `search` |
| `path` escapes the project root | `ValueError("Path escapes MCQuest project root: …")` | `security.py:23-28` |
| `path` inside an ignored directory | `ValueError("File is inside an ignored directory: …")` | `security.py:53-54` |
| `path` that is neither a usable file nor directory | `ValueError(f"Not a file: {path}")` | `security.py:50-51` |

### 6.5 Per-file failures inside directory mode (Q9 completeness requirement)

Q9 requires that **incomplete scans are never represented as complete**. A file
that is *in scope by extension* but cannot be fully scanned is therefore **not**
silently discarded:

| Condition | Required behavior |
|---|---|
| file larger than `MAX_FILE_BYTES` (`config.py:73`) | skipped as a candidate source; counted in the disclosed skipped count; `collection_complete` MUST be `false` |
| file unreadable (`OSError`, permissions, transient) | same as above |
| file not decodable as UTF-8 | **APPROVED (`O-13`, 2026-09-18 — DEC-014):** read with `errors="replace"` and continue scanning (the `find_strings` precedent, `07-…PROPOSAL.md` §7.8:321). A decoding replacement does **not** make the collection incomplete and does **not** affect `collection_complete`. |

**Rationale for the `MAX_FILE_BYTES`/unreadable rule:** a silent read-only skip
would make `total` an unmarked undercount; Q9 forbids that. No error row is
proposed (Q9's simpler model has no row-level error taxonomy — see §7.4), only
explicit disclosure + `collection_complete=false`.

### 6.6 Parameter validation

| Condition | Required behavior |
|---|---|
| `offset < 0` | `ValueError` (`07-…PROPOSAL.md` §7.8:320) |
| `max_results` ≤ 0 | clamped/validated per the existing search convention (`O-11`, approved) |
| `max_results` > 500 | capped at 500 (`config.py:74`) |
| `file_pattern` malformed | **OPEN — USER DECISION REQUIRED (`O-14`):** `fnmatch` accepts nearly any string and would simply match nothing; is silent no-match acceptable, or must an obviously malformed pattern raise `ValueError`? No Stage-4-equivalent convention exists. |

## 7. Resource limits and incompleteness semantics

### 7.1 Stage 3 limit → Stage 4 mapping (Q6; each limit judged individually)

Q6 requires each established Stage 3 limit to be **explicitly mapped**, and
requires a limit whose meaning does not transfer to be marked for user review
rather than assumed suitable. The Stage 3 values are recorded in
`src/mcquest_mcp/tools/locales.py:78-86`.

| Stage 3 limit | Value | Transfers to Stage 4? | Basis / required treatment |
|---|---|---|---|
| `MAX_ENUMERATE_FILES` | 2 000 | **YES** | Bounded walk enumeration cap; same meaning (a directory can hold arbitrarily many files). Stage 3 semantics at exactly-the-cap (⇒ incomplete) are preserved by §7.3. |
| `MAX_LOCALE_FILES` | 500 | **YES — approved as `MAX_FILES_ANALYZED` = 500 (`O-15`, 2026-09-18; DEC-014)** | The *meaning* (cap on files actually analyzed) transfers directly under the **new approved Stage 4 name** `MAX_FILES_ANALYZED` (value 500; recorded as a new approved limit per §7.2). Reaching it ⇒ `collection_complete=false` (§7.3). |
| `MAX_JSON_DEPTH` | 200 | **NOT APPLICABLE** | JSON-nesting depth has no Stage 4 analogue: scanning is line-oriented (`§4.1`), with no container nesting. It MUST NOT be carried over or described as a Stage 4 bound. |
| `MAX_EXACT_PATHS_PER_FILE` | 100 000 | **PARTIAL — OPEN (`O-16`)** | Stage 4 identity is `(path, line, name, kind)` with **no key-path concatenation**, so a "path count" budget has no direct analogue. An analogue would be a per-file candidate/identity-entry cap. |
| `MAX_EXACT_BYTES_PER_FILE` | 8 000 000 | **PARTIAL — OPEN (`O-16`)** | Stage 4 has no composed key-path bytes to charge. A per-file identity-byte analogue (name/path bytes) would have to be defined, or the limit dropped. |
| `IDENTITY_UNITS_MAX` | 64 000 000 | **PARTIAL — OPEN (`O-16`)** | Same reasoning: no key-path units exist. If kept, the unit definition must be specified for Stage 4 or the limit dropped. |
| `MAX_LOCALE_FILE_ROWS` | 3 000 | **NOT ADOPTED — dropped (`O-17`, 2026-09-18; DEC-014)** | Per-file and global row caps are **not adopted** for Stage 4; there is **no row-cap completeness condition** in §7.3. Delivery stays bounded by `max_results` and the 4000/16000 output budgets. |
| `MAX_LOCALE_ROWS` | 5 000 | **NOT ADOPTED — dropped (`O-17`, 2026-09-18; DEC-014)** | Same as above — no global row cap in Stage 4. |
| `MAX_FILE_BYTES` | 2 000 000 | **YES** (shared config) | Direct read cap: `config.py:73`; failure treatment per §6.5. |
| `MAX_PARSE_NODES_PER_FILE` | 1 000 000 | **NOT APPLICABLE** | There is **no parse tree** in a lexical line scan; the guard has no Stage 4 subject. It MUST NOT be claimed as a Stage 4 bound, and no RSS/parse-allocation ceiling may be claimed (Stage 3 D-2 discipline, `locales.py:47-51`). |

**Output-budget limits that do transfer (non-negotiable):** ≤ 4000 normal /
≤ 16000 ceiling / ≤ 200 per-line clip (`00-V0.7-MASTER.md` §4:110-112;
`config.py:94-96`).

### 7.2 Binding rule on non-transferring limits

A limit marked **NOT APPLICABLE** or **PARTIAL — OPEN** above:

- MUST NOT appear in the Stage 4 tool description or spec as though it were an
  established Stage 4 bound;
- MUST NOT be cited to justify a resource claim Stage 4 does not implement;
- if adopted for Stage 4, MUST be given an explicit Stage 4 definition and
  value by user decision, recorded as a new approved limit (not "borrowed").

### 7.3 Exact `collection_complete` semantics (Q9)

`collection_complete` is `true` **only when all** of the following hold:

1. the directory walk exhausted the tree **and** the enumerated file count did
   **not** reach the enumeration cap (`MAX_ENUMERATE_FILES` = 2000) **and** the
   number of files actually analyzed did **not** reach `MAX_FILES_ANALYZED` =
   500 (approved `O-15`);
2. every in-scope candidate file was read and scanned successfully (no §6.5
   skip of an oversized or unreadable file occurred; decoding with
   `errors="replace"` is **not** a failure — approved `O-13`);
3. the response is not a truncated page **due to its own pagination** — note
   that `has_more` / `returned < total` is a *page* signal, **not** a
   completeness failure (`01-V0.7-CONTRACT.md` P004/P005:34-42);
4. no in-scope file was excluded from analysis by a resource bound.

Otherwise it MUST be `false`.

The draft's "no row was dropped by any per-file or global cap" condition is
**removed**: per-file and global row caps are **not adopted** for Stage 4
(approved `O-17`), so there is **no row-cap completeness condition**.

Explicit Q9 prohibition, carried into every Stage 4 surface:

> `collection_complete=false` MUST never be softened to, or rendered as, a
> silent "complete" result, and a zero **omission count** (where such a count
> exists at all) MUST never be presented as evidence that the scan was
> exhaustive.

### 7.4 No row-level error taxonomy (consequence of Q9)

The Q9 model has **no** `ERROR` row kind, no per-type error counters, and no
`FINDINGS_UNKNOWN` / `FINDINGS_OMITTED` accounting. Incomplete-scan honesty is
therefore carried **only** by §6.5 disclosure fields plus
`collection_complete=false`. Stage 3's richer taxonomy MUST NOT be implied,
referenced, or reused by name in the Stage 4 tool description.

## 8. Zero-result and partial-result wording

### 8.1 Required semantics (Q8, binding)

A zero-result response means **only** that no *lexical candidate* matched under
the §3–§4 rules. It MUST NOT be expressed, or be interpretable, as "there are no
components in this repository".

Reasons a zero result may coexist with real components (each must be reachable
from the wording): lowercase-named components; HOC wrappers (`memo`,
`forwardRef`, `connect`) (§3.4.2); multi-line declarations (§3.4.5);
`React.createClass`; re-export/alias forms; any extension outside
`.js/.jsx/.ts/.tsx`; any file skipped per §6.5; and any file beyond an
enumeration/analysis cap.

### 8.2 Zero-result wording (approved `O-18`)

Proposed summary line when `total == 0`:

> `total: 0` — no component candidates matched (lexical scan of N file(s);
> candidates only — a zero result does not prove that no components exist).

Proposed summary line when `total == 0` **and** the scan was **not** exhaustive:

> `total: 0` found so far — scan incomplete (`collection_complete: false`);
> further files were not analyzed, so this is not a complete inventory.

### 8.3 Partial-result wording (approved `O-18`)

Proposed incompleteness disclosure line (present whenever
`collection_complete: false`):

> `collection_complete: false` — scan not exhaustive (reason: <reason>);
> results below are a partial inventory.

where `<reason>` is one of the §6.5/§7.3 causes (e.g. `file skipped:
oversized`, `file skipped: unreadable`, `file limit reached`,
`row limit reached`).

**APPROVED (`O-18`, 2026-09-18 — DEC-014):** the zero-result and partial-result
strings in §8.2 and §8.3 are approved as specified. (Q8 requires *precise*
wording; the project requires zero-result honesty,
`07-…PROPOSAL.md` §7:196-198.)

### 8.4 Cross-product requirement

The four combinations (zero/non-zero results × complete/incomplete scan) MUST
each be expressible simultaneously and unambiguously, and no wording may imply
completeness merely because an omission count is zero (Q9; §7.3).

## 13. Known limitations, risks, and unresolved questions

### 13.1 Known limitations (direct consequences of Q4 lexical-only)

1. **False positives are structural, not incidental.** Comment-borne and
   string-borne matches are emitted (§4.4); a non-component capitalized
   function-shaped declaration is indistinguishable from a component (§3.1).
2. **False negatives are structural.** All §3.4 forms are missed, including
   HOC wrappers, multi-line declarations, `React.createClass`, aliased
   re-exports, and lowercase-named components.
3. **No semantic content.** Props, types, resolution, defaults and runtime
   behavior are permanently out of scope (§2.2) — the tool cannot answer "what
   does this component take?" or "where is it used?".
4. **Single-line only.** A declaration split across physical lines is invisible
   (§4.1), which is the most common real-world miss.
5. **ASCII-only names.** `[A-Z]` excludes non-ASCII uppercase identifiers
   (§9 #20).
6. **No framework awareness.** The tool cannot verify React; "React component
   declarations" in Q2 is a *shape* target, not a verified claim (§3.1).
7. **Type-only files.** `.d.ts` files are **excluded by suffix** (`O-8`,
   approved 2026-09-18), so declarations inside them are never reported;
   `declare`-form matches inside non-`.d.ts` `.ts` files **are** reported
   (documented residual false positives — no `declare` guard in v1).
8. **Invalid UTF-8 lines can lose rows.** Input is decoded with
   `errors="replace"` (`O-13`, approved 2026-09-18). The resulting `U+FFFD`
   replacement character cannot satisfy the ASCII `NAME` grammar
   (`[A-Z][A-Za-z0-9_]*`), so a candidate on a line containing invalid
   UTF-8 is not matched. This can cause **row loss** while — exactly as
   `O-13` specifies — decoding does **not** affect `collection_complete`.
   Recorded as an implementation limitation; `O-13` is unchanged and no
   fix was authorized.
