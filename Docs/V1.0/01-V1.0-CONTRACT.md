## 1. Purpose

v1.0 exists to make local repository/document retrieval **route to structured evidence
rather than default to shell**, and to make that routing **verifiable**.

The contract therefore governs five things and nothing else:

1. which retrieval path a class of request must take;
2. what a local-evidence tool may know (path, range, encoding, completeness);
3. what a local-evidence tool may never do;
4. how local evidence is labelled and bounded;
5. how routing behaviour is verified rather than asserted.

### 3.1 The v0.9 preference ladder is normative for v1.0

`01-V0.9-CONTRACT.md` §13 already fixes the contractual preference order:

```text
existing evidence
  → existing MCQuest capability
    → structured tool operation
      → targeted shell operation
        → broader scan only if necessary
```

**v1.0 does not introduce a new ladder.** It **operationalizes** the existing one for local
file/JSON retrieval and adds a measurable acceptance model. This is the single most important
continuity statement in this contract: v1.0 is an **application** of v0.9 §13, not a
replacement of it.

### 3.2 The duplication constraint (decision A12) — binding

`Docs/V0.9/00-V0.9-MASTER.md:82-83` (decision A12) states:

> "v0.9 **must not duplicate** a v0.8 capability; when an existing capability answers the
> intent, v0.9 routes to it."

v1.0 inherits this constraint. Therefore:

1. A new v1.0 tool **may not** re-implement behaviour already provided by a registered tool.
2. A new v1.0 tool **may** fill a capability gap demonstrated by audit evidence.
3. Any proposal to add a duplicating tool requires an **explicit owner decision** that
   overrides A12 for that tool, recorded in `07-V1.0-DECISIONS.md`.

> **Direct consequence.** `mcquest_file_read` is **not** proposed, because `mcquest_read_file`
> already satisfies it in full (audit Finding A2).

### 4.1 Controlled literal search before regex — normative

The v1.0 instruction requires "controlled literal search first". This contract makes it
normative without adding a new tool:

1. A request naming **exact literal text** must be issued as a **literal** pattern, not a
   general regex, and must escape regex metacharacters.
2. A request requiring alternation, anchoring, or classes **may** use regex.
3. The chosen mode is **not** inferred heuristically; it is chosen by the caller and is
   visible in the tool parameter.

> This is satisfiable today: a literal string is a valid regular expression for both
> `mcquest_search` and `mcquest_search_docs`.

## 5. The routing contract

> **This is the normative core of v1.0.** It states which path a request **must** take.
> It is derived directly from the v0.9 §13 preference ladder and adds the host-agent branch
> established by audit Finding A8.

### 5.1 The routing hierarchy

```text
USER REQUEST
    │
    ├─ Q0. Is the target INSIDE the configured MCQuest project root?
    │       │
    │       ├─ NO ──► HOST-AGENT FILE TOOL  (Cline read_files / search_codebase)
    │       │          ── still NOT a shell pipeline ──
    │       │
    │       └─ YES ▼
    │
    ├─ Q1. Is existing recorded evidence already available and fresh?
    │       └─ YES ──► reuse it (v0.9 §20; no re-retrieval)
    │
    ├─ Q2. Local file / document CONTENT at a known path?
    │       └─► mcquest_read_file  /  mcquest_read_doc          [EXISTS]
    │
    ├─ Q3. SEARCH for text / headings / identifiers in local files?
    │       └─► mcquest_search_docs  (Markdown)
    │           mcquest_search      (source)                    [EXISTS]
    │
    ├─ Q4. STRUCTURED information from a local JSON file?
    │       └─► mcquest_json_read                                [PROPOSED]
    │           (locale semantics → mcquest_locale_inspect)      [EXISTS]
    │
    ├─ Q5. ENUMERATE or LOCATE files?
    │       └─► mcquest_list_files / mcquest_find_files /
    │           mcquest_list_docs                                [EXISTS]
    │
    ├─ Q6. Shell / environment / process / terminal STATE?
    │       └─► v0.9 shell intelligence (10 mcquest_shell_* tools) [EXISTS]
    │
    └─ Q7. Genuine command EXECUTION required?
            └─► Cline terminal — the client remains the execution authority
```

### 5.2 Normative routing rules

| ID | Rule |
| --- | --- |
| RT-1 | A request whose answer is **already present in a local file** must not be routed to the shell. |
| RT-2 | A request naming a **known path** and asking for content or a line range must use a structured read tool. |
| RT-3 | A request asking to **locate text** (literal, heading, identifier) must use a structured search tool. |
| RT-4 | A request asking for a **specific value inside a local JSON file** must use a JSON tool, not a shell pipeline. **No general JSON value tool exists (P1); this rule is currently UNSATISFIABLE for non-locale in-root JSON and is recorded as `UNKNOWN`, not as a pass.** |
| RT-5 | A request about **environment, process, terminal, or session state** must use v0.9 shell intelligence. |
| RT-6 | A request that genuinely requires **executing** something may use the Cline terminal, and only then. |
| RT-7 | When the target is **outside** the MCQuest project root, MCQuest tools are **inapplicable**; the host-agent file tool is the correct structured route. Shell remains incorrect. |
| RT-8 | A structured route must be attempted **before** any shell equivalent. If a structured tool fails, the failure must be reported as evidence — not silently replaced by a shell command. |
| RT-9 | A shell command is **never** a first-choice route for information already available in a local file. |

### 5.3 Tool availability is not tool selection

> **Explicit contractual statement.** A registered tool's existence proves **nothing** about
> whether a client will choose it. The MCP server cannot observe, require, or **enforce** which
> tool the client selects for a given request. Routing is therefore a property of **client
> behaviour**, not server state.
>
> **P1 CORRECTION (2026-09-29).** The Gate 0 text said the server "cannot observe, require, or
> **influence**". That was too strong. The server **does** influence: `server.py:48-116` supplies
> an `instructions` string to `MCPServer(...)` that already states *"When an MCP tool provides
> the required repository evidence, prefer it over an equivalent shell command (e.g. grep, rg,
> Select-String, Get-ChildItem)"*, pinned by
> `tests/test_discoverability.py::test_server_instructions_communicate_tool_selection_policy`.
>
> The correct distinction, now measured, is:

| Capability | Exists? | Evidence |
| --- | --- | --- |
| Server **influences / guides** (instructions, descriptions) | **YES** | `server.py:48-116`; `test_discoverability.py` |
| Server **observes** the client's choice | **NO** | `mcquest_shell_terminal` reports the client as entirely `unknown` |
| Server **enforces** | **NO** | no veto channel; no client identity; read-only design |

Consequences:

1. The server **must not** claim that routing is enforced. It may **guide** and **describe** the
   intended route (v0.9 §19.4: a routed name is a recommendation, never an invocation).
2. Routing compliance can only be established by an **external behavioural harness** that
   observes a live client (see `06-V1.0-TEST-PLAN.md` §6). **P1 additionally established that no
   client-side tool-call telemetry exists**, so even a harness records only the *selected tool*,
   never the *reason*.
3. v1.0 explicitly does **not** introduce shell interception or execution gates to force
   compliance — those are forbidden non-goals N-8 and N-9. The consequence is that v1.0
   improves routing through **specification, discoverability, and measurement**, not coercion.
4. **The only place enforcement could exist is client-side policy** — and P1 measured that the
   client rules file covers **writes** but has no **read-side** rule (`10` §2.2, D-V1-10).

### 5.4a Scope labelling requirement [V1.0-NEW — added at P1, **IMPLEMENTED at P2**]

> **Added because measurement showed two correct tools answering different questions with no way
> for the client to tell which it got.** P1 measured `mcquest_search` returning **9** matches and
> `search_codebase` returning **80** for the same literal `EXPECTED_TOOLS`.

Every local retrieval tool **must** state, in its client-visible description, all four of:

| # | Attribute | `mcquest_search` (measured) | `mcquest_read_file` (measured) |
| --- | --- | --- | --- |
| 1 | **Scope** | configured project root | configured project root |
| 2 | **Path model** | repository-relative | repository-relative |
| 3 | **Pruning** | `IGNORED_DIRECTORIES` applied | n/a |
| 4 | **Applicability** | in-root only; out-of-root is an error | in-root only; out-of-root is an error |

**Normative consequence:** a client asking "search the repository" must be able to determine,
from the tool description alone, which scope it will receive. A tool that silently answers a
narrower question than the request implies violates the evidence-orientation rule (§7.5).

> This is a **labelling** requirement on existing tools. It requires **no new tool**.

### 6.2 `mcquest_file_find` — **PROPOSED AS A THIN ROUTING ALIAS (no new retrieval logic)**

**Status: proposed, but only in the constrained form recorded as decision D-V1-02.**

**Purpose.** Provide a single, discoverable name that routes a *find-in-a-known-file-or-tree*
request to the correct existing engine, so the caller does not have to choose between
`mcquest_search` and `mcquest_search_docs` — and so the routing decision is expressed once,
visibly, in a tool description.

**Hard constraint.** This tool **must not** contain a search implementation. It **must** call
the existing search functions. Introducing an independent matcher would duplicate
`search_text` and violate decision A12.

**Inputs (proposed)**

| Input | Type | Meaning |
| --- | --- | --- |
| `query` | string, **required** | Text to find. Treated as a **literal** by default. |
| `path` | string, default `.` | Project-relative file or directory. |
| `case_sensitive` | bool, default `false` | Mirrors the existing search contract. |
| `mode` | enum, default `auto` | `literal` \| `regex` \| `auto` (see below). |
| `context_lines` | int, default 0, bounded 0-3 | Surrounding lines per match. |
| `max_results` | int, default 50, hard cap 500 | Page size. |
| `offset` | int, default 0 | 0-based page offset. |

**Deterministic mode selection (`auto`)** — no heuristics, no scoring:

```text
if mode == "literal"            → literal
if mode == "regex"              → regex
if mode == "auto":
    if the target resolves to a single FILE   → literal
    else                                     → literal unless the query
                                               contains a regex metacharacter
                                               ( ^ $ [ ] ( ) | * + ? \ )
                                    → then regex
```

This rule is total, deterministic, and independent of file content. It is a **declared
mapping**, not a heuristic, and therefore does not violate the "no uncontrolled heuristics"
constraint.

**Outputs (proposed)** — the existing `search_block` shape, so the output contract does not
diverge:

`[SUMMARY]` block (`total`, `files_affected`, `returned`, `offset`, `next_offset`,
`has_more`, `truncated`, `collection_complete`, `budget`, `MODE`, `QUERY`, `PATH`) followed by
`path:line` evidence rows ordered deterministically by `(path, line)`.

**Explicitly NOT included:** fuzzy matching, similarity, ranking, alias expansion, stemming,
or any uncontrolled heuristic. A rejected alternative is recorded in
`07-V1.0-DECISIONS.md`.

> **If the owner judges an alias to be duplication too (a defensible reading of A12), the
> fallback is zero new tools: the routing contract §5 plus tool-description changes alone
> would satisfy goals G-1..G-4.** This is recorded as decision **D-V1-03**.

### 6.3 `mcquest_json_read` — **PROPOSED (the one genuine gap)**

**Status: proposed, NOT authorized.** This is the only proposed tool backed by a real audit
gap (Finding A5): the repository has JSON *parsing* but no general *structured value reader*.

**Purpose.** Read a bounded, structured value from a local JSON file by deterministic path,
returning structured data rather than terminal text — replacing shell pipelines such as
`Get-Content x.json | ConvertFrom-Json` and `findstr`.

**Inputs (proposed)**

| Input | Type | Meaning |
| --- | --- | --- |
| `path` | string, **required** | Project-relative `.json` file. |
| `json_path` | string, optional | Deterministic selector (grammar below). Omitted ⇒ structure summary. |
| `max_results` | int, default 50, hard cap 500 | Bound on returned nodes/rows. |

**`json_path` grammar — deterministic and bounded [V1.0-NEW]**

```text
json_path  := segment ( "." segment )* [ "[" index "]" ]
segment    := key | "*" | "[]"
key        := bare-key
bare-key   := unquoted token of [A-Za-z0-9_-]+
index      := non-negative integer
```

Rules:

1. A **bare key** addresses an object member. Keys containing `.` or `[` must be written
   JSON-quoted inside the selector (`a."b.c"`) — mirroring the existing typed-path rendering
   in `tools/locales.py` so the two surfaces agree.
2. `[n]` addresses an **array index**; `[n]` is an index, while `["0"]` is the **string key**
   `"0"`. The two are never conflated (same discipline as `mcquest_locale_inspect`).
3. `*` matches every member of an object; `[]` matches every element of an array.
4. `[` and `]` are the **only** wildcards permitted. No `**`, no recursive descent, no
   fuzzy key matching.
5. An empty `json_path` returns a **structure summary** (types, counts, depth), not the whole
   document.
6. Depth is bounded by the existing `MAX_JSON_DEPTH`; size by `MAX_FILE_BYTES`.

**Outputs (proposed)**

`[SUMMARY]` block (`path`, `json_path`, `resolved`, `returned`, `next_offset`, `has_more`,
`truncated`, `collection_complete`, `budget`, `depth`) followed by bounded, deterministically
ordered rows. Missing key, type mismatch, decode failure, oversize, and depth overflow are
reported as **explicit, non-fatal rows or errors** — never as a fabricated empty value.

**Explicitly NOT included:** JSONPath wildcards beyond `[` `]` `*`, JSON Pointer (`/a/b`),
JMESPath, filters, projections, mutation, or schema inference.

## 7. Invariants

These are contractual. Every proposed and existing v1.0-relevant tool must satisfy them.

### 7.1 Read-only [V1.0-NEW restatement of a V0.9 invariant]

v1.0 evidence tools **must not**:

- write files;
- edit files;
- delete files;
- install packages;
- execute arbitrary commands;
- spawn arbitrary subprocesses.

Enforcement is already mechanical: `tests/test_security_readonly.py::test_source_has_no_write_primitives`
scans every `.py` under `src/` for `write_text`, `write_bytes`, `unlink`, `os.remove`,
`os.rename`, `shutil.rmtree`, `subprocess.Popen`, `os.system`, `os.popen`. **Any v1.0 tool that
introduces one of these tokens fails the suite.** This is inherited infrastructure, not a new
mechanism.

### 7.2 Local-only [V1.0-NEW]

v1.0 concerns repository/local files only. Explicitly out of scope: SSH, VPS, remote
filesystem, remote shell, remote command execution. The MCP server has no remote capability
today and v1.0 adds none.

### 7.3 Bounded [V1.0-NEW restatement]

Every retrieval/search operation must have explicit bounded behaviour.

1. No unbounded "read entire repository" operation may be introduced.
2. Bounds are inherited constants unless a new bound is explicitly approved:
   `MAX_FILE_BYTES` 2 MB; `MAX_SEARCH_RESULTS` 500; `DISCOVERY_MAX_RESULTS` 300;
   `MAX_READ_WINDOW_LINES` 1000; `DEFAULT_READ_WINDOW_LINES` 250;
   `MAX_OUTPUT_CHARS` 16 000; `NORMAL_OUTPUT_CHARS` 4 000; `LINE_CLIP_CHARS` 200.
3. Every response reports `truncated` and `collection_complete` truthfully.
4. Every response reports the exact inspected path.

### 7.4 Deterministic [V1.0-NEW restatement]

Same input + same file state ⇒ same result, byte-identical. This forbids wall-clock
timestamps, random ordering, set iteration order leaking into output, and filesystem-order
dependence. It is the v0.9 §16.6 invariant.

### 7.5 Evidence-oriented [V1.0-NEW restatement]

Every response must make clear **what was inspected**, **what was returned**, **whether the
result was complete**, **whether truncation occurred**, **what path was inspected**, and
**what provenance applies**. Inherited from the `[SUMMARY]` block convention and v0.9 §17.

### 7.6 No invented certainty [V1.0-NEW restatement]

1. **No numeric confidence.** v0.9 §7 rule 4.
2. `UNKNOWN` must remain `UNKNOWN`; an inferred value is never promoted to an observed one.
3. A zero-result search means "no match **within the inspected scope**" — never "the thing does
   not exist" (v0.9 §18.3).
4. No output may claim a command was executed or verified (v0.9 §14.1).

### 7.7 Registration integrity

1. `EXPECTED_TOOLS` in `tests/test_registration.py` remains the **single** authority
   (decisions A12/S5).
2. Any registration change must update **all three** in lockstep: `server.py`, `EXPECTED_TOOLS`,
   and the `capabilities.py` registry — or the three A12 drift tests fail.
3. Adding a tool requires an **explicit authorization**; documentation alone authorizes nothing.

## 10. Consolidated V1.0 routing model [P5 — NORMATIVE, AUTHORITATIVE]

> **This section is the single authoritative statement of v1.0 routing.**
> It consolidates §5 (P1) and §5.4a.1–.3 (P2–P4) and is the rule the V1.0 Final Gate tests
> against. Where an earlier section conflicts, **this section wins**.

### 10.1 The model

```text
LOCAL INFORMATION REQUEST
    │
    ├── target inside the MCQuest project root?
    │       └── YES → applicable MCQuest structured tool   (§10.2)
    │
    ├── target outside the MCQuest project root?
    │       └── YES → applicable NATIVE/CLIENT capability   (§10.3)
    │                    │
    │                    ├── capability supports the target?  → use it
    │                    │
    │                    └── no applicable capability?
    │                          └── is genuine shell / process / environment
    │                              execution genuinely required?
    │                                  ├── YES → shell / process tools (§10.5)
    │                                  └── NO  → report the boundary, do not
    │                                          substitute a shell pipeline (§10.4)
    │
    └── no local file target at all
            └── shell / environment / execution tools
```

### 10.2 In-root target — MCQuest is the applicable branch

> When the target is inside the MCQuest project root **and** an applicable MCQuest structured
> tool exists: **prefer the MCQuest structured tool.**

MCQuest tools are **conventionally confined** to `DEFAULT_PROJECT_ROOT`; an out-of-root path is
an **error by design**, never something to work around. Confinement must never be weakened,
bypassed, or re-requested as if the target were in-root.

### 10.3 Out-of-root target — native, evaluated per capability

> MCQuest structured tools must not bypass their project-root confinement. If the target is
> outside MCQuest's root, **use an applicable native/client capability if that capability
> supports the target.**

**Native reach must be evaluated per capability, not as one universal "native branch".**
Observed at P4:

| Capability | Observed reach | Class |
| --- | --- | --- |
| Native file **read** | arbitrary absolute local paths; no project-root check | **OBSERVED** |
| Native code **search** | workspace/index-dependent; reached repositories *outside* the MCQuest root; **silent zero** outside its reachable scope; no path parameter | **OBSERVED** |
| Native search size/binary handling, index freshness | not measured | **UNKNOWN** |

> **Retracted at P4 — do not restate.** The P3 claim *"native search cannot reach out-of-root
> targets"* is **false**. Native search **can** reach targets outside the MCQuest root. The true
> bound is the client workspace/index, which is a **different and larger** scope.

### 10.4 Out-of-root does NOT imply shell

**Shell must never be the generic fallback for file retrieval or search.** Formulating routing
as `out-of-root → shell` is a contract violation. Out-of-root means *"the applicable structured
capability is a different one"* — not *"no structured option exists"*.

**Silent-zero rule.** A native search returning **no results** for a target outside its reachable
scope is **not** evidence the string is absent — absence and unreachability are indistinguishable
at the tool boundary. Report it as a **boundary limitation**, or verify by reading.

### 10.5 Shell remains the execution / environment capability

Shell and process tooling remain appropriate for genuinely execution-oriented work:

- environment, process, and terminal state
- builds, tests, and installations
- command execution
- other work that genuinely requires a shell

It is **not** the default mechanism for retrieving information already available in local files.

### 10.6 Evidence discipline for every routing claim [P5 — NEW, from P4's method finding]

P4 found a recurring failure mode: **a correct observation generalised into a category-wide
rule without sufficient evidence.** Three occurrences: P1 (one cache-bearing result set → "a
search surface"), P3 (one out-of-root file → "native search cannot reach out-of-root"), P2 (read
reach → read *and* search* reach).

**Required form for any v1.0 claim:**

```text
Observation  →  capability-specific claim  →  evidence classification  →  bounded contract
```

**Prohibited form:**

```text
Single observation  →  universal rule
```

Consequences, binding on all v1.0 documents:

1. Claims name a **capability**, not a category.
2. Every claim carries an evidence class: **GUARANTEED** (implementation/test-pinned),
   **OBSERVED** (measured, environment-specific), **IMPLEMENTATION DETAIL** (true, not
   contractually stable), or **UNKNOWN**.
3. **`UNKNOWN` stays `UNKNOWN`.** Plausible-sounding host behaviour is never manufactured —
   the asymmetry P2 recorded as **L10** was correct behaviour, not a debt.
4. Environment-specific observations are labelled as such and are **not** promoted to
   guarantees.
