## 0. Method and its limits (read this first)

### 0.1 What this measurement actually is

The scenarios in §3 were executed **by the agent performing P1**, in the **live Cline session**,
against the **live MCQuest MCP server**. The "Actual tool selected" column records the tool
that was genuinely invoked. This is a real behavioural observation, not a simulation.

### 0.2 The three limits of this measurement

| # | Limit | Consequence |
| --- | --- | --- |
| **L1** | **Single session, single agent instance.** One agent's choices are not a population sample. | Results indicate *what can happen*, not *what usually happens*. No frequency claim is made. |
| **L2** | **Self-report of tool choice.** The invoking agent records its own selection. | Vulnerable to selection bias — an agent motivated to demonstrate good routing may route better than one that is not. |
| **L3** | **No client-side routing telemetry exists** (proven in §2.3). | The *reason* for a selection is **not independently observable**. Every "observed routing reason" below is `UNKNOWN`. |

> **Honesty rule applied throughout.** This report separates what was *seen* from what was
> *concluded*. No causal claim about "why Cline chose X" is made, because no evidence in this
> environment can establish it.

## 5. Q3 — server-side enforceability

### 5.1 The four mechanisms, separated

| # | Mechanism | Exists? | Evidence | Can it change what the client does? |
| --- | --- | --- | --- | --- |
| 1 | **Tool-description guidance** | **YES** | `server.py:50-116` instructions; per-tool docstrings; pinned by `test_discoverability.py` | Influences the client's choice. **Not binding.** |
| 2 | **MCP server `instructions`** | **YES** | `MCPServer(..., instructions=...)` at `server.py:48` | Same as above — a prompt-level statement. **Not binding.** |
| 3 | **Actual enforcement** | **NO** | No gate, interceptor, or hook in `src/`; `test_security_readonly.py` forbids subprocess primitives | Nothing can refuse a client action. |
| 4 | **Client-side tool selection** | **EXTERNAL** | Implemented by Cline; `project-rules.md` read-side gap (§2.2) | Determined outside this repository. |

### 5.2 OBSERVED FACT — the server cannot observe or refuse

```text
mcquest_shell_terminal  → CLIENT TERMINAL: session_id/process_id/shell/cwd all
                          "unknown | UNKNOWN/untrusted" — no client declaration
```

The server has **no declared client identity**, so it cannot even correlate a client action
with a server-side record, let alone constrain it. The MCP protocol surface used here is
`tools/list` + `tools/call`; the server answers calls it receives and has no channel to veto
one.

> **ANSWER to Q3: MCQuest can provide routing GUIDANCE only. It cannot enforce routing.**
> Enforcement would require either (a) client-side policy, or (b) an interception mechanism
> that V1.0 explicitly forbids (N-8/N-9) and that the read-only invariant would block.

### 5.3 What V1.0 can realistically control

| Controllable by V1.0 | Not controllable by V1.0 |
| --- | --- |
| The `instructions` text the client receives | Whether the client obeys it |
| Per-tool descriptions and discoverability | Which tool the client selects |
| The operation-class vocabulary used by `shell_plan` | Whether `shell_plan` is called at all |
| Correctness/scope labelling of each tool's output | The client's choice of branch |
| Whether a capability exists for a class | Client-side rules content |

## 9. Required P1 conclusions

### 1. Missing-tool problem or routing problem?

**Primarily a ROUTING problem — but a different routing problem than Gate 0 assumed.**

The evidence does **not** show a missing-tool problem. `mcquest_read_file`,
`mcquest_search_docs`, `mcquest_search`, `mcquest_git_context`, and `mcquest_shell_environment`
all existed, were registered, and answered their scenarios correctly.

The measured problems are:

| Problem | Class | Evidence |
| --- | --- | --- |
| The client rules cover **writes but not reads** | **client-side policy gap** | §2.2 |
| The V0.9 router **cannot classify** a git-state intent it can actually answer | **router vocabulary gap** | §3.5 |
| "In the repository" is **scope-ambiguous** between two search tools (9 vs 80 hits) | **scope-labelling gap** | §3.3 |
| No **telemetry** exists to detect any of the above in future | **observability gap** | §2.3 |

### 2. Can the motivating request already be completed without shell?

**YES — demonstrated live, not argued.** Scenario B completed in one structured call
(`read_files:1417-1431`) with zero shell commands. The in-root equivalent completed via
`mcquest_read_file:307-321`, also with zero shell.

### 3. Which existing structured tools can already handle it?

| Tool | Role | Measured |
| --- | --- | --- |
| `mcquest_read_file` | bounded line-range read, in-root | used in §3.2 control |
| `mcquest_read_doc` | Markdown read, in-root | not exercised (same implementation) |
| `mcquest_search_docs` | heading/pattern location in Markdown | used in §3.1 |
| `read_files` (Cline native) | bounded read, **any** path | used in §3.1, §3.2, §3.4 |
| `search_codebase` (Cline native) | workspace-wide search | used in §3.3 |

### 4. When is Cline-native file/search the correct branch?

**Measured conditions — all four observed:**

1. The target is **outside** the configured MCQuest root (2/2 attempts: MCQuest rejected, native succeeded).
2. The request is **workspace-wide** rather than repo-scoped (search spanned 205 files vs 5).
3. The file is a **non-source config** (`package.json`, `tsconfig.json`) rather than a code/doc artefact.
4. Absolute paths are already the natural form of the request.

### 5. When is MCQuest structured the correct branch?

**Measured conditions — all observed in-root:**

1. Target is **inside** the configured root.
2. Deterministic, paged, bounded evidence is wanted (`total_lines`, `has_more`, `truncated`).
3. Generated directories must be **pruned** (`.pytest_cache` excluded).
4. Scope is explicitly repository-relative and root-confined.

### 6. When is MCQuest shell tooling appropriate?

**Measured (Scenarios F, G):** when the question is about **machine/process/environment
state** (executable presence, version, repository identity) or when a **command must actually
run**. It contributed labelled provenance and pre-execution validation in both cases, and it
**did not** need to be eliminated — it was never misused in these scenarios.


### 7. Can MCQuest enforce routing, or only guide?

**Guide only.** §5. Guidance exists (server `instructions` + tool descriptions); enforcement
does not and cannot exist within the read-only, recommend-only architecture. The only place
enforcement could live is **client-side policy** — which is outside this repository and, for
reads, currently empty (§2.2).

### 8. Is `mcquest_json_read` still justified after measurement?

**DEFER — the evidence weakened, but did not eliminate, the case.**

| For | Against (measured) |
| --- | --- |
| Gap G1 is real; no structured JSON value reader exists | **The MCQuest repository contains zero `.json` files** — the gap is latent, not blocking |
| `mcquest_locale_inspect` is locale-scoped, not a value reader | The measured D target was **out of root**, so MCQuest was never the applicable branch |
| Frozen `READ_JSON` class is declared but unserved | The request was satisfiable by reading text |

> **Honest position.** The gap is real but **undemonstrated in this repository**. Building a
> tool for it now would be building ahead of evidence — the exact failure mode P1 was called
> to prevent. Defer until a real in-root JSON requirement appears.

### 9. Should `mcquest_file_read` and `mcquest_file_find` remain rejected?

**`mcquest_file_read`: REJECT — confirmed.** `mcquest_read_file` was used successfully in §3.2.
Adding a second name for a working capability would be pure duplication (A12).

**`mcquest_file_find`: REJECT — confirmed, and now more strongly.** Measurement showed the
*real* problem between the two search tools is **scope ambiguity** (§3.3), not the absence of
a finder. A thin alias would **not** fix a scope-labelling problem; it would add a third
search surface and make the ambiguity worse.

### 10. What should P2 implement, if anything?

**Not a new tool.** The measured defects are all addressable without adding a tool:

| Defect | Smallest fix | New tool needed? |
| --- | --- | --- |
| Client rules have no read-side routing rule | Client-side rules (outside repo) | **NO** |
| `shell_plan` cannot classify git-state intent | Operation-vocabulary entry (frozen — needs owner) | **NO** |
| "In the repository" is scope-ambiguous | Clarify scope in existing tool descriptions | **NO** |
| No routing telemetry | Opt-in observation via existing `mcquest_shell_observe` | **NO** |

> **Measured conclusion: the highest-value P2 adds no MCP tool at all.** Every reproducible
> defect found in P1 is a **vocabulary, labelling, or policy** problem.
