## 2. The v1.0 goal

V0.9 answered *"how should I interact with the environment?"*. V1.0 has a different primary goal:

> **Local repository/document information should be retrieved through structured MCQuest
> evidence tools instead of defaulting to shell commands.**

The core behavioural principle:

> **Structured local evidence first; shell only when genuinely required.**

### 2.1 The separation of concerns

```text
MCQuest V0.8   Repository Intelligence                  "What is true?"
MCQuest V0.9   Environment + Terminal + Command Intel.   "How should I interact with it?"
MCQuest V1.0   Local Evidence Routing                   "Which retrieval path is correct?"
Cline          Task Intelligence                         "What should I accomplish?"
```

V1.0 is **not** a repository auditor, **not** a shell executor, and **not** a search engine.
It is a **routing and evidence-discipline layer over local retrieval**.

## 3. The problem, restated against audit evidence

The V1.0 problem statement proposes three tools. The Gate 0 audit (§2 and §4 of
`02-V1.0-IMPLEMENTATION-AUDIT.md`) established that:

| Proposed tool | Audit verdict |
| --- | --- |
| `mcquest_file_read` | **Already satisfied** by the registered `mcquest_read_file` |
| `mcquest_file_find` | **Already satisfied** by `mcquest_search_docs` / `mcquest_search` |
| `mcquest_json_read` | **Genuine gap** — only locale-audit JSON exists today |

> **This reframes V1.0.** The dominant problem is **not** missing tools. It is that a capable,
> registered, read-only evidence surface already exists and is nevertheless **not the default
> route**. V1.0's primary deliverable is therefore **routing discipline**, with at most **one**
> genuinely new tool.

## 11. Authoritative routing contract (consolidated at P5)

The normative, single-source statement of v1.0 routing is **`01-V1.0-CONTRACT.md` §10**. In brief:

```text
in-root target      → prefer the applicable MCQuest structured tool
out-of-root target  → use an applicable NATIVE capability, evaluated PER CAPABILITY
                      (native read: unconfined · native search: workspace/index-dependent)
no applicable cap.  → is genuine shell/process/environment execution required?
                        yes → shell tools
                        no  → report the boundary; never substitute a shell pipeline
```

**Shell is never the generic fallback for file retrieval or search.** Two rules the Final Gate
must test: out-of-root **does not** imply shell, and a zero-result native search is a **boundary
limitation, not a negative finding**.

> **Nothing in this package is committed. No commit and no push were performed.**
