## 1. Decision record

### D-V1-01 — Do **not** add `mcquest_file_read`; use the existing `mcquest_read_file`

| Field | Value |
| --- | --- |
| Status | **PROPOSED** (audit-evidenced) |
| Evidence | `02-V1.0-IMPLEMENTATION-AUDIT.md` §4.2, Finding A2 |
| Alternatives considered | (a) add it as specified; (b) add it as a thin wrapper; (c) reject it |
| Chosen | **(c) reject** |

**Rationale.** `mcquest_read_file` already satisfies every element of the proposed contract
(repository-relative path, start/end line, 2 MB byte bound, 250/1000-line windows,
`total_lines`/`next_start_line`/`has_more`, `truncated`, `collection_complete`, exact line
numbers, root confinement). Adding `mcquest_file_read` would be pure duplication and would
breach decision A12 and contract §19.5.

**Consequence.** The v1.0 tool surface does **not** include a file-read tool. The routing
contract points at the existing one. The only real delta (encoding information, Gap G6) is
raised as open question **OQ-1** rather than used to justify a duplicate tool.

**Reversal cost.** Low. If the owner later wants a distinct name, it is a rename/alias, not a
new retrieval implementation.

### D-V1-02 — `mcquest_file_find`, if built, is a **thin alias** with no search implementation

| Field | Value |
| --- | --- |
| Status | **PROPOSED** |
| Evidence | `02` §4.3, Finding A3 |
| Alternatives considered | (a) full new search tool; (b) thin alias; (c) drop |
| Chosen | **(b) as the default reading of the proposal; (c) remains live via D-V1-03** |

**Rationale.** Two registered tools already provide deterministic, line-numbered,
bounded content search. The only defensible value of a third name is **discoverability**: a
single entry point that routes to the right engine, with a deterministic literal-first mode
satisfying contract §4.1. Any independent matcher would duplicate `search_text`.

**Hard constraint.** The tool must call the existing search functions. It must not contain a
matcher.

**Consequence.** Tool count 34 → 35 **only if** D-V1-02 and D-V1-04 are both accepted.

### D-V1-05 — The routing hierarchy includes the host-agent branch

| Field | Value |
| --- | --- |
| Status | **PROPOSED** |
| Evidence | `02` §7, Finding A8 |
| Alternatives considered | (a) two-branch tree (MCQuest vs shell) as originally proposed; (b) three-branch tree including host-agent file tools |
| Chosen | **(b)** |

**Rationale.** The host agent already owns structured, read-only file tools
(`read_files`, `search_codebase`) that take **absolute** paths. The v1.0 worked example targets
a path **outside** the MCQuest project root, where MCQuest tools are inapplicable by design.
Omitting this branch would make the routing contract prescribe a route that cannot work for the
very example that motivated v1.0.

**Consequence.** The governing principle is restated as *"prefer structured retrieval over
shell"*, with MCQuest preferred **when the target is inside its root**.

A native search returning **no results** for an out-of-workspace target is the expected

| Layer | Content |

### 10.3 Reach is not selectable: **RECORDED**

`search_codebase` exposes only `queries` — no root, path, glob, or file-type parameter. The
client therefore **cannot** direct native search beyond the workspace root.

**Consequence for V1.0 scope:** a target outside the workspace root is unreachable by **every**
structured surface available here. MCQuest can document that dead end; it cannot remove it, and
adding an in-root tool would not help. This is the strongest argument yet for the existing
**"out-of-root does NOT imply shell"** rule — it is exactly where an unguided client is most
likely to reach for a shell pipeline.
