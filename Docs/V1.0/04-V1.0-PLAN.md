Every phase was **re-scoped by measurement** rather than following this plan. The plan's
assumption — that `mcquest_json_read` was the work — did not survive contact with evidence.

| Phase | Planned as | Actually authorized as | New tools | Source changes |
| --- | --- | --- | ---: | ---: |
| **P1** | routing contract + discoverability | routing baseline / **measurement** | 0 | 0 |
| **P2** | `mcquest_json_read` | routing contract + **scope semantics** + discoverability tests | 0 | 2 files |
| **P3** | behavioural routing harness | **live client routing re-measurement** | 0 | 0 |
| **P4** | evidence-based revision | **native search boundary investigation** | 0 | 0 |
| **P5** | — | **documentation consolidation** | 0 | 0 |

**Cumulative v1.0 result: 0 new tools.** `mcquest_json_read` was **deferred**, not deferred-then-
built, because P1–P4 never demonstrated a capability gap that justified it. The P2 `+1`
registration planned in §4 was **never performed**.

> **Why the plan was wrong:** it was written before measurement. Each phase was re-scoped by
> what the previous phase actually found, which is the intended working mode — but it means the
> planned tool never entered implementation.

### 1.1 Sequencing rationale

The order is deliberate and is the main architectural recommendation of this plan:

> **Specify routing → measure routing → then add capability only where measurement shows a
> gap.**

Because the audit established that 2 of 3 proposed tools already exist (`02` §4), building
`mcquest_json_read` before measuring routing would risk solving a problem that does not exist.
P1 and P3 are therefore ordered **before** and **around** P2, and **P2 is explicitly
optional** — P4 may conclude that no new tool is needed.

## 4. P3 — Behavioural routing verification harness

**Goal.** Establish, with evidence, whether a live client actually prefers structured tools
over shell (contract §5.3: tool availability is not tool selection).

| Item | Detail |
| --- | --- |
| New files | `Docs/V1.0/prompts/` scenario fixtures + a recorded results file |
| New source files | none |
| Dependency | **P2 complete (or explicitly deferred) + explicit authorization** |

**Scope**

1. Define the canonical request suite: tests **A**–**E** from `06-V1.0-TEST-PLAN.md` §6,
   including the documented "must not route to shell" cases.
2. Run each request against a live client and **record the actually-selected tool**.
3. Record pass/fail per scenario with the observed tool name, verbatim.
4. Report `UNKNOWN` for any scenario that cannot be observed rather than inferring a result.

**Explicit boundaries**

- The harness **observes**; it never intercepts, blocks, or rewrites a tool call.
- No shell interception, no execution gate (forbidden non-goals N-8/N-9).
- Results are recorded as observations, not asserted as guarantees.

**Gate to P4:** a complete, verbatim evidence table for tests A–E.
