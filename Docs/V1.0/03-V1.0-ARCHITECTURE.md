# MCQuest MCP v1.0 — Architecture

> STATUS: **GATE 0 — PROPOSED ARCHITECTURE (NOT IMPLEMENTATION-AUTHORIZED)**
>
> This document designs how local evidence is retrieved, how it relates to the v0.9 shell
> intelligence layer, and how provenance and boundedness are preserved. Nothing here is built.

---

## 1. Design principles

1. **Reuse before creation.** Every bound, guard, renderer, and traversal already exists in
   `config.py`, `security.py`, and `formatting.py`. v1.0 adds adapters, not infrastructure.
2. **The server proposes; the client decides.** v1.0 states the correct route. It cannot
   enforce it, and does not pretend to (contract §5.3).
3. **One retrieval surface per information class.** Text content, doc content, JSON content,
   and enumeration each have a designated tool. No overlapping third surface.
4. **Bounded by construction.** A tool cannot be written without a bound; the summary block
   makes truncation and incompleteness visible.
5. **Additive only.** v1.0 extends v0.9; it never redefines it.

---

## 2. Layer model

```text
┌───────────────────────────────────────────────────────────────┐
│ L4  CLIENT / TASK INTELLIGENCE — Cline                        │
│     Chooses a tool. This is where routing actually happens.   │
├───────────────────────────────────────────────────────────────┤
│ L3  HOST-AGENT FILE TOOLS — read_files, search_codebase       │
│     Structured, read-only, ABSOLUTE paths, any location.      │
│     Correct route for targets OUTSIDE the MCQuest root.       │
├───────────────────────────────────────────────────────────────┤
│ L2  MCQUEST EVIDENCE LAYER — 24 repository-intelligence tools │
│     Read-only, bounded, project-root confined, repo-relative. │
│     + v1.0 PROPOSED: mcquest_json_read, (mcquest_file_find)   │
├───────────────────────────────────────────────────────────────┤
│ L1  MCQUEST SHELL INTELLIGENCE (V0.9) — 10 mcquest_shell_*    │
│     Environment/terminal/plan/validate. Recommend-only.       │
├───────────────────────────────────────────────────────────────┤
│ L0  CLIENT TERMINAL — genuine execution authority              │
└───────────────────────────────────────────────────────────────┘
```

### 2.1 Why L3 exists at all

This layer is **not** in the v1.0 problem statement's routing tree, and its omission is a real
defect in that tree (audit Finding A8). The host agent already owns first-class, read-only,
structured file tools. The architectural consequences are:

| Consequence | Detail |
| --- | --- |
| Path model differs | L2 takes **repo-relative** paths under one root; L3 takes **absolute** paths anywhere. |
| Applicability differs | An L2 call for an out-of-root path is **rejected by design** (`security.resolve_project_path`), not merely unavailable. |
| Correctness differs | For an out-of-root target, L3 is the **correct structured route** and shell is still **wrong**. |

> **Therefore the v1.0 principle is not "prefer MCQuest over shell". It is
> "prefer structured retrieval over shell", with MCQuest as the preferred structured route
> *when the target is inside its root*.**

## 3. Relationship to v0.9 shell intelligence

v1.0 does not modify the v0.9 layer. The relationship is **complementary and one-directional**.

| Concern | v0.9 | v1.0 |
| --- | --- | --- |
| Domain | environment, terminal, command | local file/document retrieval |
| Question | "How should I interact with the environment?" | "Which retrieval path is correct?" |
| Operation classes | frozen 15-class vocabulary | **unchanged**; v1.0 adds no class |
| Stance | recommend-only, no execution | read-only, no execution, no enforcement |
| Output | v0.9 summary-first validation | existing `[SUMMARY]` block family |
| Tool count | 10 | +1 recommended, +3 maximum (proposed) |

### 3.1 The declared-but-unserved operation class

`shell/capabilities.py:65` already declares `READ_FILE` and `READ_JSON` as operation classes,
and v0.9 contract §13 already rules that *"Repeated `findstr` searches are a contract
violation of the preference ladder."*

So v0.9 **already declares the behaviour v1.0 wants**. What is missing is a capability for
general `READ_JSON` to route to. v1.0's most defensible single addition is therefore the tool
that makes an **already-frozen contract rule enforceable**.

## 4. Routing hierarchy (normative form)

The authoritative form is contract §5. Architecturally it is a decision cascade:

```text
Q0  in-root?            ── no ──► L3 host-agent file tool
        │ yes
Q1  fresh evidence?     ── yes ─► reuse (no retrieval)
        │ no
Q2  content @ path?     ── yes ─► L2 read_file / read_doc
Q3  search content?     ── yes ─► L2 search_docs / search
Q4  JSON value?         ── yes ─► L2 json_read [PROPOSED] / locale_inspect
Q5  enumerate?          ── yes ─► L2 list_files / find_files / list_docs
Q6  env/process state?  ── yes ─► L1 v0.9 shell intelligence
Q7  execution needed?   ── yes ─► L0 client terminal
```

## 5. Evidence flow

```text
  request
     │
     ▼
  ┌──────────────────┐   in-root?  ──────────────► out-of-root ⇒ ERROR row
  │ path resolution  │   (security.resolve_project_path)
  └────────┬─────────┘
           ▼
  ┌──────────────────┐   missing / not-a-file / ignored ⇒ explicit ERROR
  │ validation       │   (security.validate_readable_file)
  └────────┬─────────┘
           ▼
  ┌──────────────────┐   MAX_FILE_BYTES, MAX_JSON_DEPTH, MAX_SEARCH_RESULTS
  │ bounded read     │   (config.py constants)
  └────────┬─────────┘
           ▼
  ┌──────────────────┐   line numbers, counts, determinism
  │ parsing          │
  └────────┬─────────┘
           ▼
  ┌──────────────────┐   NORMAL 4 000 / CEILING 16 000 / LINE_CLIP 200
  │ rendering        │   (formatting.OutputBudget)
  └────────┬─────────┘
           ▼
     [SUMMARY] + evidence rows
     (total, returned, has_more, truncated, collection_complete, path)
```

**Every stage is inherited.** A v1.0 tool is a thin adapter that plugs into this flow; it does
not re-implement any stage.

## 6. Provenance

Provenance requirements are inherited from v0.9 §17 and are not re-specified.

| Requirement | How a v1.0 tool satisfies it |
| --- | --- |
| What was inspected | `path` in the summary block |
| What was requested | `json_path` / `PATTERN` / range echo |
| What was returned | `returned`, `total`, `next_offset` |
| Completeness | `collection_complete` |
| Truncation | `truncated` + `[OUTPUT TRUNCATED: N characters omitted]` |
| Scope/freshness | **Only** when the result is recorded as an observation via `mcquest_shell_observe` (v0.9 A14). A plain read is **not** automatically an observation. |

> **Important discipline (avoids invented certainty).** v1.0 must not retro-label ordinary
> reads with `trusted` / `fresh` / `stale` labels. Freshness is a property of the
> **observation store**, not of a file read. Conflating them would violate v0.9 A5 and S6.

## 7. Bounded retrieval — module reuse map

| v1.0 need | Existing module | Change required |
| --- | --- | --- |
| Root confinement | `security.resolve_project_path` | none |
| File validation | `security.validate_readable_file` | none |
| Size bound | `config.MAX_FILE_BYTES` | none |
| Ignored paths | `config.IGNORED_DIRECTORIES` / `IGNORED_EXTENSIONS` | none |
| Read windowing | `formatting.read_window_block` | none |
| Search rendering | `formatting.search_block` | none |
| JSON depth | existing `MAX_JSON_DEPTH` logic in `tools/locales.py` | reuse, do not fork |
| JSON typed paths | `tools/locales._typed_key` | reuse so path rendering agrees |
| Summary block | `formatting.summary_block` | none |
| Budget | `formatting.OutputBudget` | none |

> **Architectural constraint.** A new JSON reader that *forks* the depth/typed-path logic out
> of `locales.py` would create the duplication A12 forbids. It must **import and reuse** it.
> This is a concrete, checkable design rule for P2.

## 8. The architecture question (instruction §9)

> *Should v1.0 create new MCP file tools, wrap/reuse an existing capability, or expose a thin
> MCQuest-specific evidence layer over existing safe infrastructure?*

**The audit answered this with evidence rather than assumption.** The resolution is a
**three-tier answer**, because the three proposed tools do not have the same answer.

| Proposed tool | Resolution | Reason |
| --- | --- | --- |
| `mcquest_file_read` | **REJECT — use existing** | `mcquest_read_file` is a complete implementation. New tool = pure duplication (A12 violation). |
| `mcquest_file_find` | **WRAP existing (thin alias), or drop** | Search logic must not be re-implemented. Value is discoverability/routing clarity only. |
| `mcquest_json_read` | **NEW, thin, over existing safe infrastructure** | Real gap (G1). Reuses `security`, `config`, `formatting`, and the depth/typed-path logic from `locales.py`. |

### 8.1 The general principle

```text
v1.0 = a THIN EVIDENCE LAYER over existing safe infrastructure
     + a NORMATIVE ROUTING CONTRACT
     + a BEHAVIOURAL VERIFICATION HARNESS
```

It is **not** a new file-access subsystem. There is no second path resolver, no second size
guard, no second output budget, and no second search engine. This is the architecture that
"minimizes duplication" as the instruction requires.

### 8.2 What the architecture deliberately does NOT include

Rejected as non-goals (N-1..N-14): embeddings, vector search, fuzzy/similarity matching,
autonomous crawling, background indexing, file watchers, automatic edits, shell interception,
execution gates, and all remote/VPS/SSH capability. The audit confirmed **none** of these
exist in the codebase today, so this design preserves the existing posture rather than
loosening it.

## 10. P1 architectural validation (2026-09-29)

> Evidence: `10-V1.0-P1-MEASUREMENT-REPORT.md`. This section records what measurement
> **confirmed** and what it **corrected** in the architecture above.

### 10.1 Confirmed by measurement

| Architecture claim | Gate 0 basis | P1 measurement |
| --- | --- | --- |
| L3 host-agent layer is real and needed (§2.1) | inference from tool inventory | **2/2 out-of-root paths** rejected by MCQuest, succeeded natively |
| Root confinement is a permanent property (§2.1) | design reading of `config.py` | verbatim `Path escapes MCQuest project root` rejection |
| Evidence flow stages are all inherited (§5) | source reading | every stage observed in live calls |
| Single-root per process (§2.1 Q5) | design reading | 2 processes, 2 distinct roots, confirmed |
| Shell legitimacy is preserved, not eliminated (§3) | contract reading | Scenarios F and G both routed to shell intelligence correctly |

### 10.2 Corrected by measurement

| Item | Gate 0 architecture said | P1 measured |
| --- | --- | --- |
| **Routing hook** | "The server **cannot** influence routing" (implied no mechanism) | **Correction:** `server.py:48-116` instructions **already** state the preference and are regression-pinned. The server *does* guide; it cannot *enforce*. |
| **L2 JSON row** | `mcquest_json_read` as an L2 capability | **No such capability exists.** The Q4 row is now `[GAP, DEFERRED]`, not a designed layer member. |
| **Scope semantics** | not modelled | **New requirement:** L2 and L3 search have *different* scopes (9 vs 80 hits measured). The architecture must label this, not hide it. |

### 10.3 Architectural addition from P1 — scope labelling

P1 measured a divergence the Gate 0 architecture did not model:

```text
mcquest_search    (path="src", root-confined, IGNORED_DIRECTORIES pruned)  →   9 hits
search_codebase   (workspace-wide, no pruning)                             →  80 hits
same literal: EXPECTED_TOOLS
```

Neither is incorrect. The architecture defect is that **the client is not told which question
each tool answers.** Proposed addition (design only, not implemented):

| Layer | Scope | Path model | Pruning | Paging vocabulary |
| --- | --- | --- | --- | --- |
| L2 `mcquest_search` / `mcquest_search_docs` | configured project root | **repo-relative** | `IGNORED_DIRECTORIES` applied | `offset`/`next_offset`/`has_more` |
| L3 `search_codebase` | workspace | caller-supplied | none observed | not offered in the same vocabulary |

> **P2 implication.** The fix is **labelling**, not a new tool. Both surfaces are correct; the
> contract must state which is which.

### 10.4 Architectural correction — the router, not the toolbox

P1's only reproducible routing failure was **not** a missing capability:

```text
mcquest_shell_plan("check uncommitted changes and report branch")
  → operation: UNKNOWN   status: BLOCKED
mcquest_git_context()
  → BRANCH: main   UNCOMMITTED: 1
```

The toolbox answered; the **router could not classify the question**. The Gate 0 architecture
treated the routing contract as a documentation layer above the tools. P1 shows the
classification step itself has a defect — and `OPERATION_CLASSES` is frozen by V0.9, so the
correction is an **owner decision**, not a V1.0 edit.

### 10.5 Architecture status after P1

```text
Architecture validated ............ YES (with two corrections, §10.2)
New tools required ................ 0
New architecture surfaces required . 1 (scope labelling, §10.3)
Owner decisions blocking P2 ........ 4 (OD-1…OD-4) + 2 proposals (D-V1-09, D-V1-10)
```



Each question is **total** and **ordered**, so the cascade always terminates in exactly one
route. No question requires a heuristic judgement about intent.

## 12. P2 — implemented guidance layer

P2 added a **guidance layer only**. No new component, no new tool, no new execution path.

### 12.1 What was added, and where it lives

```text
MCP client
    │
    ├─ reads server `instructions`  ──► ROUTING BY TARGET LOCATION block (P2)
    │                                  • IN-ROOT  → MCQuest branch
    │                                  • OUT-OF-ROOT → native host tools, never shell
    │                                  • never bypass project-root confinement
    │                                  • search scope is per-tool and narrower
    │                                  • shell reserved for env/process/execution
    │
    ├─ reads tool descriptions ──────► `SCOPE:` sentences (P2)
    │                                  root, corpus, pruning, case, ordering, paging
    │
    └─ selects a tool ──────────────► unchanged; MCQuest cannot observe or veto this
```

The two P2 text surfaces are **the only levers MCQuest owns** for routing. Everything else in
this architecture is unchanged: confinement still raises, tools still return the same bytes,
registration is untouched.

### 12.2 Why guidance and not a mechanism

Three independent constraints, all recorded from measurement:

| Constraint | Evidence | Consequence |
| --- | --- | --- |
| No client identity | `mcquest_shell_terminal` reports the terminal as `unknown` | The server cannot know who is calling |
| No veto channel | No MCP mechanism lets a server refuse a client tool call | Enforcement is technically impossible |
| No telemetry | No client tool-call log is readable | Adoption is unobservable from here |

A new architecture component would not change any of these. Adding one would create the
illusion of control without the substance — precisely what non-goals N-8 and N-9 forbid.

### 12.3 Discoverability as architecture

P2 treats **discoverability text as a tested interface**:

| Layer | Artifact | Test |
| --- | --- | --- |
| Routing decision | `instructions` block | T1–T4 |
| Scope semantics | tool `SCOPE:` sentences | T5 |
| Truthfulness of that text | implementation | T6 (behavioural) |

T6 is the load-bearing one. Without it, T1–T5 would only prove that a *claim* exists. T6
proves the claim matches behaviour, so the guidance cannot silently become a lie.

### 12.4 Scope asymmetry is deliberate

| Surface | Labelling at P2 | Labelling at P4 |
| --- | --- | --- |
| `mcquest_search` / `mcquest_search_docs` | **GUARANTEED**, cited to source lines | **GUARANTEED** (unchanged) |
| host `search_codebase` | **`UNKNOWN`** — not observable from this repository | **OBSERVED** — workspace-rooted; see §4a |
| host file read | implicit | **OBSERVED** — unconfined, path-addressable |

P2 declined to describe native search semantics it could not verify, recording the asymmetry as
limitation **L10**. P4 closed that gap by measurement.

## 4a. Measured host/native boundary (added at P4)

The two native capabilities have **different reach**, so v1.0 states reach per capability
rather than treating "native" as one branch.

```text
MCQuest tools        [ DEFAULT_PROJECT_ROOT ]        out-of-root → ERROR (by design)
Host file READ       [ any local absolute path ]     no root check observed
Host file SEARCH     [ client workspace root   ]     no path parameter; outside → SILENT ZERO

Measured workspace root:  D:\DeveloperTools
  ├── mcquest-mcp                 (MCQuest project root — inside both)
  ├── mcquest-vps-inspector-mcp   (outside MCQuest, INSIDE native search)  ← 27 results
  ├── LTE-Monitoring_Tool         (outside MCQuest, INSIDE native search)  ←  1 result
  └── .cline
  D:\App Development\…            (outside BOTH)                            ←  0, silent
```

### 4a.1 Consequences for evidence handling

1. **A zero-result native search is not a negative finding.** For a target outside the
   workspace, absence is indistinguishable from unreachability. The result must be reported as
   a boundary limitation, not as "the string does not exist".
2. **Native read and native search are not interchangeable.** A file outside the workspace can
   still be *read* by absolute path even though it cannot be *searched*.
3. **The dead end is real and is a shell-pressure point.** Beyond the workspace root, no
   structured surface available here can serve the request. This is precisely why the
   **"out-of-root does not imply shell"** rule must remain explicit — and it cannot be
   enforced from the server, only stated.
4. **MCQuest cannot widen the native bound.** No root or path parameter is exposed, and the
   workspace root is a client/IDE property outside this repository.

> **Reach is not symmetric, and v1.0 no longer implies that it is.**
> Full semantics table: `12-V1.0-P4-NATIVE-SEARCH-BOUNDARY.md` §4.
