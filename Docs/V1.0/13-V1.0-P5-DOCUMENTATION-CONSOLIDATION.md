## 5. P4 consolidation

### 5.1 Native `read_files` boundary

**GUARANTEED:** nothing about the host tool. **OBSERVED** (9 probes): arbitrary absolute local
paths; out-of-root files; **no project-root boundary** (read `C:\Windows\System32\drivers\etc\hosts`);
exact line ranges; arbitrary file types; no workspace requirement; `ENOENT` for a missing file.
**UNKNOWN:** binary/encoding policy; size/range ceilings.

### 5.2 Native `search_codebase` boundary

**GUARANTEED:** nothing. **OBSERVED** (8 probes): workspace/index-dependent root
(`D:\DeveloperTools` during measurement); reached repositories **outside** the MCQuest root;
**no path parameter**; **silent zero** outside reachable scope; case-insensitive; 100-result cap;
**no paging**; **no cache pruning** (`.pytest_cache/v/cache/nodeids` returned); regex supported.
**IMPLEMENTATION DETAIL:** path-grouped ordering. **UNKNOWN:** size/binary handling; index
freshness; behaviour beyond the observed workspace/index.

### 5.3 Capability-specific routing — the consolidated rule

```text
in-root      → prefer the applicable MCQuest structured tool
out-of-root  → use an applicable NATIVE capability, evaluated PER CAPABILITY
no cap.      → genuine shell/process/environment execution required?
                 yes → shell tools
                 no  → report the boundary; never substitute a shell pipeline
```

Native reach is **not** one category. Read reach and search reach differ measurably, and treating
them as one branch is what produced P3-F1.

### 5.4 P3-F1 correction — recorded, not rewritten

| Step | Content |
| --- | --- |
| 1. **What P3 observed** | Native `search_codebase` returned 6 in-root results for an out-of-root pattern; native `read_files` reached the target. |
| 2. **What P3 incorrectly generalised** | That native search **cannot** reach out-of-root targets, and therefore that reads and searches share one narrower boundary. |
| 3. **What P4 measured** | Native search **does** reach out-of-root repositories: 27 results in `mcquest-vps-inspector-mcp`, 1 in `LTE-Monitoring_Tool`. The true bound is the **client workspace root**, which is *larger* than the MCQuest root. |
| 4. **Corrected conclusion** | Native reach is **per capability**: read is unconfined; search is workspace/index-dependent with a silent-zero failure mode. |
| 5. **Authoritative statement** | `01-V1.0-CONTRACT.md` **§10** (and §5.4a.3). §5.4a.2 is marked SUPERSEDED. |

P3's report is **unedited**; the correction lives as a forward-pointing addendum, so the original
evidence remains recognisable as history.

### 5.5 `.pytest_cache` distinction

Two different surfaces, two different policies — and P1 conflated them:

| Surface | `.pytest_cache` | Basis |
| --- | --- | --- |
| `mcquest_search` / `mcquest_search_docs` | **Pruned** — structurally cannot return it | `IGNORED_DIRECTORIES` (`config.py:37`), pinned by a P2 behavioural test |
| Native `search_codebase` | **Not pruned** — returned it | **OBSERVED** at P4: `.pytest_cache/v/cache/nodeids:490` |

P2 *inferred* the attribution; P4 *observed* it. P1's original phrasing ("a search surface")
was imprecise; the substance was right.

### 5.6 Silent-zero search behaviour

A native search returning **no results** for a target outside its reachable scope is **not**
evidence the string is absent. At the tool boundary, absence and unreachability are
indistinguishable. P4 verified this directly: `collections/quizzes/records` exists at
`Phase-66-…md:1427` — read with `read_files` — while native search returned **0** for it, with no
error or warning.

This is now normative (contract §10.4) and a Final Gate requirement (**FG-4**). It is the mirror
image of the P3 error: P3 read a boundary result as a capability fact; a client that does not know
about silent zeros will read a boundary result as a negative finding.
