### 4.4 `mcquest_json_read` — JSON parsing exists, but not as a general reader

`mcquest_locale_inspect` is registered and performs real JSON work:
`json.loads(text, object_pairs_hook=_Pairs)` (`locales.py:368,475`), depth pre-check via
`_max_nesting` / `MAX_JSON_DEPTH` (`locales.py:154`), `MAX_FILE_BYTES` guard
(`locales.py:356,441`), `json.JSONDecodeError` handling (`locales.py:476`), and typed
key-path rendering (`locales.py:136 _typed_key`).

**However**, `mcquest_locale_inspect` is scoped to **locale inspection semantics**:
structure/collision/duplicate analysis and MISSING/EXTRA key-path comparison against a
reference locale. A call without a reference performs "structure/collision/duplicate inspection
only". It is **not** a general-purpose structured JSON value reader.

> **Finding A5 (`mcquest_json_read` has a genuine, bounded gap).** This is the **only** one of
> the three proposed tools with a real capability gap. The existing JSON capability is
> locale-audit-specific, not a general "read this key from this JSON file" primitive. This gap
> is the strongest candidate for a genuine V1.0 addition, and it maps directly to the frozen
> V0.9 operation class **`READ_JSON`**, which already exists in `OPERATION_CLASSES`.

## 7. Capability in the surrounding MCP / Cline environment (audit §8.8)

The audit instruction required identifying whether a file/document tool already exists in the
surrounding environment, not only inside MCQuest.

| Environment | Observed capability | Relevance |
| --- | --- | --- |
| **MCQuest MCP server** | `mcquest_read_file`, `mcquest_read_doc`, `mcquest_search`, `mcquest_search_docs`, `mcquest_list_files`, `mcquest_list_docs`, `mcquest_find_files`, `mcquest_locale_inspect` | Primary structured local evidence surface. |
| **Cline (host agent) native tools** | The host agent has its **own** first-class file tools: `read_files` (batched, line-ranged, absolute paths), `search_codebase` (regex, multi-query, parallel), `list_files`, plus `run_commands` for the shell. | **Material finding — see Finding A8.** |
| **Serena (`.serena/`)** | Project-scoped code intelligence directory present in both repositories | Possible additional capability; not audited in depth — `UNKNOWN`. |

> **Finding A8 (the routing hierarchy in the V1.0 problem statement is incomplete).** The
> routing diagram places only MCQuest tools and the Cline terminal in the decision tree. In the
> real environment the host agent **already owns `read_files` and `search_codebase`**, which are
> structured, bounded, read-only file tools.
>
> This has two consequences V1.0 must address explicitly:
>
> 1. **The real competition is not only shell — it is also the host's own file tools.** A routing
>    contract that only demotes shell would be incomplete.
> 2. **MCQuest and the host tools have different path models.** MCQuest is confined to a single
>    configured project root and takes **repository-relative** paths; Cline's `read_files` takes
>    **absolute** paths. The V1.0 example reads a file at
>    `D:\App Development\Education_app\MCQuest\...`, which is **outside** the MCQuest project
>    root. For that file an MCQuest tool is **not applicable** — by design, because
>    `resolve_project_path` rejects it. The correct route for that specific example is the host
>    file tool, not an MCQuest tool and not a shell command.
>
> This is a first-class architectural finding, not a footnote. See `03-V1.0-ARCHITECTURE.md` §4.

## 9. Risks

| # | Risk | Why it matters |
| --- | --- | --- |
| R1 | **Duplicating existing tools** breaks V0.9 §19.5 and decision A12 | The V1.0 proposal as literally written would add 3 tools, 2 of which duplicate registered capabilities |

| R7 | **Scope creep toward the forbidden list** | Embeddings, fuzzy search, watchers, background indexing are excluded; the audit found no such code exists today, which is the baseline to preserve |
