## 0. Headline

P4 was asked to determine the native out-of-root search boundary left open as **P3-OQ-1**.

**It is resolved, and the answer corrects P3.**

| | P3 concluded | P4 measured |
| --- | --- | --- |
| Native search is bounded | ✅ inferred | ✅ **confirmed** |
| …therefore it cannot reach out-of-root targets | ✅ implied | ❌ **wrong** — it reached **two** out-of-root repositories |

**strictly larger** than the MCQuest project root (`D:\DeveloperTools\mcquest-mcp`). P3 tested
one out-of-root file in a *third* location and generalised from a single sample.

> **This is a correction of my own P3 reasoning, made explicitly rather than quietly.**

> retraction.

## 5. Investigation 3 — the native/MCQuest boundary

### Question A — out-of-root **read**: is native `read_files` the observable branch?

**YES — OBSERVED.** Unconfined, path-addressable, exact ranges (§2). This is a clean handoff:
MCQuest declines, native serves.

### Question B — out-of-root **search**: is there an observable native branch?

**YES, but conditionally — OBSERVED.** Native search covers everything inside
`D:\DeveloperTools`. For a target **outside** that root, **no native search branch was
observable**, and the failure mode is a **silent zero-result** rather than an error.

### Question C — should the contract name `search_codebase` as universally applicable?

**NO.** Evidence supports a capability-conditional rule, because the two native tools differ
in reach:

| Native tool | Reach | Confidence |
| --- | --- | --- |
| `read_files` | Any local path, absolute | **OBSERVED**, 9 probes |
| `search_codebase` | Workspace root only, silently | **OBSERVED**, 8 probes |

Naming both as one "native branch" is what produced P3's error. **The contract must name
reachability per capability, not per category.**

## 10. Corrected routing rule (normative, supersedes contract §5.4a.2)

P4 evidence supports replacing the P3 wording. The following is the corrected rule:

```text
ROUTING BY TARGET LOCATION (corrected at P4)

IN-ROOT  (inside the selected project root)
    → MCQuest structured tools are the applicable branch when scope matches.

OUT-OF-ROOT  (outside the selected project root)
    → MCQuest repository tools are NOT the applicable branch; they reject such
      paths by design ('Path escapes MCQuest project root').
    → Never bypass, weaken, or re-request that confinement.
    → Use host/client-native capabilities ONLY where they support the target:
         * file READ   — host read tools are path-addressable and were observed
                        to reach arbitrary local files, in-root or not;
         * file SEARCH — host search tools are bounded by the CLIENT WORKSPACE
                        root, not the filesystem, and expose no path parameter.
    → Do NOT assume a native capability reaches every out-of-root target.
    → A native search that returns NO results for an out-of-workspace target is
      a SILENT ZERO, not proof the string is absent. Verify by reading, or state
      the limitation.
    → Being out-of-root does NOT imply shell.
```

**Why this replaces the P3 text.** P3 wrote "use the host's native file tools, naming
`read_files` **and** `search_codebase`". Grouping them as one branch asserted a reach the
second tool does not have. P4 measured them separately and states reach per capability.

**Two properties deliberately preserved:**

1. **No tool is added.** Both native tools are host capabilities; MCQuest documents them.
2. **The out-of-root ⇒ shell prohibition is strengthened**, because a target beyond the
   workspace root is now a known dead end for *both* structured surfaces — which is precisely
   where an unguided client is most likely to reach for a shell pipeline.
