# V1.1 SQLite Contract — `mcquest_sqlite_read`

STATUS: **IMPLEMENTED (Gate 1)** — owner-approved `READ_SQLITE` operation class.
BASELINE: V1.0 release `8a778a198d7625f7c14928a2eb231ffdcd0dbc73` (34 tools) ->
V1.1 Gate 1 (35 tools). Scope: exactly one new tool; no other tool, alias, or
V1.0 behavior was changed.

## 1. Purpose

> Read structured, read-only evidence from one project-local SQLite database
> with a single `SELECT`, without temporary Python/shell inspection commands.

Evidence acquisition only. NOT: arbitrary SQL execution, database
administration, mutation, migration, backup, shell replacement, Python
replacement, or generic database tooling.

## 2. Inputs

```text
database   (required, string)  repository-relative path; no file: URIs
query      (required, string)  one read-only SELECT (read-only WITH...SELECT)
parameters (optional, list)    bound values for ? placeholders; never interpolated
max_rows   (optional, int)     default 50, hard cap 500 (SEARCH_DEFAULT_RESULTS /
                               MAX_SEARCH_RESULTS reused, not re-invented)
```

Validation order (deterministic): query -> parameters -> database path ->
max_rows type -> execute.

## 3. SQL policy (layer 3, not regex-only)

Accepted: a single `SELECT`, or a single read-only `WITH ... SELECT` (recursive
CTEs supported).

Mechanism (all four are mandatory):

1. string/comment-aware scanner (`_scan`) — collects bare words outside
   strings/comments/quotes, counts `;` and `?`, rejects unterminated
   literals/comments and unbalanced parentheses;
2. first bare word must be `SELECT` or `WITH`;
3. deny-list at any nesting depth: `INSERT UPDATE DELETE REPLACE CREATE ALTER
   DROP ATTACH DETACH VACUUM PRAGMA EXPLAIN BEGIN COMMIT ROLLBACK SAVEPOINT
   RELEASE REINDEX ANALYZE TRANSACTION VALUES TABLE`;
4. single statement: `;` count <= 1 and, when 1, the query must end with it;
   plus `sqlite3.complete_statement` cross-check.

SCANNER ORDER FACT (tested): deny-verbs are evaluated before the semicolon
count, so `SELECT ...; DELETE ...` reports the statement-type error first.
Both messages are deterministic policy errors.

`complete_statement` normalization (Gate 1 bug fix): SQLite returns False for
any string lacking a trailing `;`, which rejected ordinary queries. The check
now appends `;` when missing before calling it. Its real value is catching
unterminated string literals / block comments; the probe suite confirmed all
8 normalization cases.

Named parameters (`:name`, `@name`, `$name`) are rejected; only `?` with a
bound `parameters` list is accepted. No string interpolation of values exists
anywhere in the implementation.

## 4. Path policy (layer 1, reused)

`resolve_project_path` + `validate_readable_file` are reused unchanged
(`src/mcquest_mcp/security.py`). Consequences:

- relative and absolute paths both resolve against `DEFAULT_PROJECT_ROOT`;
- `..`, symlink, and junction escapes -> `Path escapes MCQuest project root`;
- missing -> `FileNotFoundError`; directory -> `Not a file: ...`;
- caller input beginning `file:` -> rejected ("SQLite URIs are not accepted");
- input containing `mode=` / `cache=` -> rejected ("Connection parameters are
  not accepted") — the caller can never control connection semantics;
- magic-header gate: first 16 bytes must equal `SQLite format 3\0`
  (`Not a SQLite database file: ...`) — extension is never trusted;
- size gate: > `MAX_FILE_BYTES` (2,000,000) rejected.

The server alone builds the URI: `<resolved-path>.as_uri() + "?mode=ro"`.

## 5. Result contract

Summary-first text report (`summary_block` conventions):

```text
[SUMMARY]
tool: mcquest_sqlite_read
DATABASE: <input path as given>
QUERY: <executed SQL, not rewritten>
columns: <column count>
row_count: <rows kept after the max_rows cap>
returned: <rows included in the response>
truncated: true|false
collection_complete: true|false
read_only: true
max_rows: <effective page size>
budget: 4000/16000

## 6. Resource limits

| Limit | Value | Source |
|---|---|---|
| query length | 16,384 chars | `SQLITE_QUERY_MAX_CHARS` (local; matches shared `MAX_INPUT_CHARS` convention — no `config.py` constant exists, so it is defined in `tools/sqlite_read.py`) |
| default rows | 50 | `SEARCH_DEFAULT_RESULTS` reused |
| hard row cap | 500 | `MAX_SEARCH_RESULTS` reused |
| output ceiling | 16,000 chars (normal 4,000) | `MAX_OUTPUT_CHARS` / `NORMAL_OUTPUT_CHARS` / `LINE_CLIP_CHARS` reused |
| query execution | 500,000 VM steps via `set_progress_handler` | deterministic; NO wall-clock timeout (V0.9 decision A5 preserved) |
| database file | 2,000,000 bytes | `MAX_FILE_BYTES` reused |
| connection busy-wait | `timeout=0` | SQLITE_BUSY -> deterministic error, never retried |

No arbitrary limits were introduced; every bound maps to an existing project
constant except the two SQLite-specific ones (step budget, busy timeout=0),
which are documented in `02-V1.1-SQLITE-SECURITY.md`.

## 7. Error semantics

Deterministic `ValueError` (or `FileNotFoundError` for a missing file,
matching `validate_readable_file` behavior used by all file tools), grouped:

- **Validation/policy**: non-empty query; query length; first-verb not
  SELECT/WITH; deny-listed statement type; multiple statements; incomplete
  statement; unterminated literal/comment; unbalanced parens; named
  parameters; parameter count/type/non-finite; `max_rows` type; `file:` URI;
  connection parameters; non-SQLite magic header; oversized database;
  path escapes root / not a file.
- **Execution**: `SQLite error: <msg>` (generic); `Statement denied by the
  read-only authorizer` (authorizer deny); `Query exceeded the deterministic
  step budget` (interrupt); `Database is locked/busy; no retry was attempted`.
- `Database unavailable: <msg>` when the read-only connection cannot open.

No error retries, no silent fallbacks, no UNKNOWN-to-error guessing.

## 8. Evidence / freshness / trust semantics

Existing vocabulary only — nothing invented:

- **Operation class**: `READ_SQLITE` (owner-approved for V1.1; one class, not
  overloaded onto `READ_FILE`/`READ_JSON`, not duplicated).
- **Fact source**: `SERVER_OBSERVED` — the MCP server process itself executed
  the read; not client-declared, not inferred.
- **Scope**: `repository` (same scope as `mcquest_read_file`); confined to the
  configured project root.
- **Freshness**: no TTL (V0.9 rule); rows are as-of the read timestamp, with
  normal staleness semantics of local file evidence.
- **Trust**: same tier as other server-read repository content; whether the
  database content is stale or wrong is a data question, not a
  trust-vocabulary question.
- **Read-only**: `read_only: true` on the capability row; registry metadata in
  `shell/capabilities.py` (phase `V1.1`, family repository, intent tags
  `SQLITE_READ` + `READ_SQLITE`).

## 9. Routing rule

Prefer `mcquest_sqlite_read` when: the evidence needed is structured SQLite
records AND the database resolves inside the permitted project boundary AND
one read-only SELECT can answer the request.

Keep using native/shell for: starting/stopping services, migrations, backups,
writes, repair/admin operations, live HTTP diagnostics, arbitrary process
execution, and out-of-root files (native client tools remain the V1.0
out-of-root branch).

The rule is pinned in `server` instructions ("...instead of temporary
Python/shell inspection commands") and in the tool description ("READ ONLY...
read-only SELECT"). It is guidance, not enforcement — same client-routing
limitation documented as D-V1-10 in V1.0.

## 10. Invariants preserved

`EXPECTED_TOOLS` remains the single registration authority (now 35); A12
(no duplicate capability) holds — Gate 0 documented that no existing tool
answers record-level SQLite questions; path confinement untouched; no shell/
Python execution added; no numeric confidence; no wall-clock TTL; no writes.

[EVIDENCE]
columns: ["col", ...]
[...one JSON array per row...]
[END]                  # present only when not truncated
```

Definitions:

- `row_count` == `returned` == rows kept by the tool after the cap. It is
  NEVER claimed to be the total matching-row count; with `truncated: true` or
  a query-side `LIMIT`, completeness is unknown to the tool.
- `truncated: true` only when bounded output occurred: the row cap fired OR
  the output ceiling cut emission. Distinguished from failures, which raise.
- `collection_complete: true` only when `truncated: false` — i.e. every row
  SQLite produced for the statement was returned and emitted. Successful
  execution alone never implies completeness.
- `read_only: true` is emitted only on a successful read-only run (any
  policy/security violation raises instead).

Serialization: NULL -> `null` (distinct from `""`); INTEGER/REAL/TEXT preserved
(Unicode emitted with `ensure_ascii=False`); BLOB -> base64 envelope
`{"$blob": "...", "bytes": N}` — never lossy text decoding.
