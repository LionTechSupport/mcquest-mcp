# V1.1 SQLite Security — `mcquest_sqlite_read`

STATUS: **IMPLEMENTED (Gate 1)**. Companion to `01-V1.1-SQLITE-CONTRACT.md`.
Audit source: `00-V1.1-GATE-0-SQLITE-AUDIT.md` sections 9-17.

## 1. Mandatory defense layers (all present in code)

```text
L1  filesystem path confinement   resolve_project_path + validate_readable_file
                                  (reused verbatim, never forked)
L2  read-only connection          server-built URI: <path>.as_uri() + "?mode=ro",
                                  isolation_level=None, timeout=0; caller URIs and
                                  mode=/cache= inputs rejected before resolution
L3  SQL grammar policy            string/comment-aware scanner + first-verb gate
                                  + depth-aware deny list + single-statement rule
                                  + complete_statement cross-check
L4  SQLite authorizer             allow only SQLITE_SELECT / SQLITE_READ /
                                  SQLITE_FUNCTION / SQLITE_RECURSIVE; deny all else
L5  resource bounds               row cap 500, output ceiling 16,000 chars,
                                  500,000-step VM budget, 2 MB file gate, timeout=0
```

L3 is explicitly NOT a `startswith("SELECT")` check: comments, CTE wrapping,
and nesting are handled by `_scan`, and L4 independently denies anything
non-read even if L3 were bypassed.

## 2. Threat analysis

| Threat | Control | Residual risk |
|---|---|---|
| Path traversal (`../`) | L1 resolve + `relative_to` | none observed |
| Absolute outside-root path | L1 (absolute path wins in join, then `relative_to` fails) | none observed |
| Symlink/junction escape | L1 `resolve()` follows links before containment check | Windows may deny link creation (test skips); confinement still holds when links exist |
| URI escape (`file:`, `mode=rwc`, `cache=`) | L2 pre-resolution string gates | a file literally named with `mode=` is rejected — over-restrictive, accepted |
| SQL mutation | L3 deny list + L4 authorizer + read-only connection (writes fail at SQLite level anyway) | none observed; byte-identity proven per test |
| Multiple statements | L3 `;` count + endswith rule + complete_statement | none observed |
| `ATTACH`/`DETACH` | L3 first-verb deny + L4 (`SQLITE_ATTACH`/`DETACH` not in allow list) | none observed |
| Extension loading | L4 denies `SQLITE_LOAD_EXTENSION`; Python also disables extensions by default | empirically verified: `load_extension('x')` -> "not authorized" -> policy error |
| PRAGMA | L3 first-verb deny + L4 (`SQLITE_PRAGMA` not allowed) | empirically verified: authorizer returns "not authorized" |
| `EXPLAIN` | L3 first-verb/deny-list reject | **authorizer alone does NOT block `EXPLAIN`** (probe: allowed) — L3 is load-bearing for this case; documented honestly |
| Resource exhaustion (runaway query) | L5 deterministic 500k-step budget via progress handler; no wall-clock | step budget is a chosen bound, not infinite-proof; a query under budget can still be slow |
| Huge result sets | L5 row cap + output ceiling + `truncated`/`collection_complete` honesty | caller may not know total match count when truncated — by contract |
| Locked/busy database | L2 `timeout=0` -> immediate `SQLITE_BUSY` -> deterministic error; no retry | none; behavior surfaced, never hidden |
| Malformed database | magic-header gate (L2 pre-check) + SQLite's own error at execute | header-valid garbage reaches SQLite and raises -> classified `SQLite error` |
| WAL/SHM behavior | read-only URI; the tool never sets WAL and never writes | opening a WAL database read-only without `-shm` write access may fail -> deterministic `SQLite error`/`Database unavailable` |
| Secrets/private rows exposed | confinement to project root + `SERVER_OBSERVED` provenance; no logging of row content by the tool | in-root database content IS readable by design — same exposure class as `mcquest_read_file` |
| DoS via expensive scans | L5 step budget | same as runaway query |
| Files outside project scope | L1 + root policy | none observed |

## 3. Empirical probes performed during Gate 1 (read-only, temp files)

1. `complete_statement` behavior on 8 query shapes -> drove the documented
   normalization fix (contract section 3).
2. Authorizer denial messages: `load_extension` -> "not authorized";
   `PRAGMA` -> "not authorized"; `EXPLAIN` -> **allowed** (L3 covers it).
3. Locking: `BEGIN EXCLUSIVE` + write in a second connection -> reader gets
   `database is locked` -> mapped to the deterministic no-retry error.
4. Interrupt: progress handler abort -> `interrupted` -> step-budget error.

Probe files were created under the system temp directory, outside both
repositories, and deleted immediately. No probe touched the MCQuest
application, its database, or this repository's working tree.

## 4. Read-only guarantee wording

The tool may claim: "reads rows under a layered read-only policy (confined
path + read-only connection + statement policy + authorizer + bounds)."
The tool may NOT claim: "no SQL can ever write" as a single-layer proof —
read-only comes from L1-L5 together, which is why every mutation-attempt test
asserts byte-identical SHA-256 before/after.

## 5. Security test coverage (see `03-V1.1-SQLITE-TEST-PLAN.md`)

Traversal, absolute-outside, symlink (skip-guarded), `file:` URI, `mode=`/
`cache=`, missing, directory, non-SQLite, malformed, 17 statement classes,
comment/block-comment/CTE-wrapped mutations, multi-statement, extension
loading, parameter policy, row/output/length/step bounds, locked database,
and byte-identity integrity on every rejection path.
