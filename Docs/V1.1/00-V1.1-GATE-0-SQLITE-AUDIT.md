## B. Gap assessment

**What existing tools can do.** Locate the file (`mcquest_find_files` by
name). Read its bytes as replacement-character-mojibake
(`mcquest_read_file` → `files.py:207-210`, UTF-8 `errors="replace"` — §19
shows the header *is* legible). State confinement/test bounds.

**What they cannot do.** No tool parses the SQLite page format, so no tool
can answer "what are the `quizzes` rules?" or "which `quizzes` rows belong
to user X?" — the exact motivating questions. Text search cannot match
values inside database pages, and reading bytes ≠ inspecting records.

**Why the workflow fell back to shell/Python.** Two distinct causes:

1. **Capability gap (primary).** With no structured SQLite reader,
   inline Python was the only route from question to evidence. This is
   V1.0-class-2 shell use: *shell used only because no structured SQLite
   evidence capability exists*.
2. **Execution need (secondary, stays shell).** The PocketBase process was
   *running*; an HTTP 400 arrived from a *live superuser route*. Diagnosing
   a live server via its HTTP API is process interaction — that half of the
   workflow belongs to shell/process tooling regardless of this proposal.

## D. Proposed contract — `mcquest_sqlite_read` (Gate-1 design target, not live)

**Name / purpose.** `mcquest_sqlite_read` — return structured evidence
from one `SELECT` query against one project-local SQLite database file.
Evidence acquisition only; no administration, no writes.

**Inputs (minimal).**

| Input | Required | Contract |
|---|---|---|
| `database` | yes | Repository-relative path to the `.db`/`.sqlite` file. Resolved by `resolve_project_path`; everything after resolution (§9) applies. A bare `file:` URI form is **not** accepted — see §9. |
| `query` | yes | One `SELECT` statement, bounded by `MAX_INPUT_CHARS` (16_384). §8 defines acceptance. |
| `parameters` | no | Optional positional parameter values bound via DB-API substitution (`?`), never interpolated. Justified: the motivating workflow filters by a specific user id; binding removes an injection class entirely. |
| `max_rows` | no | Optional caller cap, clamped to the server maximum (§11). |

No `timeout`, `offset`, `json_path`, or pragma input — unjustified surface.

**Outputs (deterministic shape).**

```text
database             # normalized repository-relative path as requested
query                # echoed query text
columns              # ordered column names of the result set
rows                 # list of row value-lists, in query order
row_count            # == len(rows) returned on THIS page; see below
returned             # == row_count (kept as a separate field for V1.0-shape parity)
truncated            # true iff rows were cut by max_rows, the output ceiling, or the timeout
collection_complete  # true iff the query ran to completion AND nothing was cut
read_only            # true literal — connection was opened mode=ro with authorizer deny-all
```

`row_count` semantics (honest): it counts rows **returned**, which equals
rows **matched** only when `truncated` is false and the query has no
`LIMIT`. A bounded read cannot know the full match count without consuming
the result; the contract must not claim otherwise. `collection_complete`
is therefore the conjunction above, never "the query succeeded".
Error metadata (§13) replaces the shape on failure; rows and errors are
never mixed.

**Value encoding.** JSON-serializable only: NULL→null, INTEGER/REAL→number,
TEXT→string, BLOB→`{"$blob": "<base64>", "bytes": n}` (never raw bytes,
never lossy text decode — the `errors="replace"` precedent of `read_file`
must **not** be reused for database values).

(`Docs/V1.0/07-V1.0-DECISIONS.md:85-93`): a declared-but-unserved
structured-read need.
## 8. SQL safety model (layered; no single check is sufficient)

A leading-`SELECT` regex is **explicitly rejected** as a safety model:
comments (`/* … */`), CTEs (`WITH … DELETE …`), stacked statements, and
trailing `; ATTACH` all defeat it.

Gate-1 mandatory layers, in enforcement order:

1. **Single statement.** Reject if `sqlite3.complete_statement` disagrees,
   if a second statement follows, or if a `;` terminates anything but the
   final statement. Comments are stripped before this check, never trusted
   by it.
2. **Read-only parse gate.** Tokenize the first keyword after comment/CTE
   stripping: it must be `SELECT` or `WITH` (and a `WITH…` body must itself
   resolve to `SELECT`). Explicitly rejected: `INSERT UPDATE DELETE DROP
   ALTER CREATE REPLACE VACUUM ATTACH DETACH PRAGMA BEGIN COMMIT ROLLBACK
   SAVEPOINT RELEASE EXPLAIN ANALYZE REINDEX`.
3. **Authorizer deny-all.** `connection.set_authorizer()` returning
   `SQLITE_DENY` for every action except `SQLITE_SELECT`, `SQLITE_READ`,
   `SQLITE_FUNCTION` (pure functions only). This is the layer that survives
   a parser mistake.
4. **Read-only connection.** Open `mode=ro` (the probe's own pattern:
   `file:…?mode=ro`), so the OS/page layer refuses writes even if layers
   1–3 all failed.

Allowed: subqueries, JOINs, aggregates, `WITH`…`SELECT` CTEs (recursive
included — bounded by §11, not by grammar fear), bound parameters.
`PRAGMA` is **denied** (it can change behavior: `journal_mode`,
`foreign_keys`, `writable_schema`). `EXPLAIN` is denied (not evidence).

## 9. Database path security

Resolution order, each step mandatory:

1. Input must be a repository-relative path. Absolute paths, `..` above
   the root, and any `file:` URI in the input are rejected **before**
   resolution — `resolve_project_path` joins onto the root, so a URI
   string must never reach it (a `file:…?mode=ro&…` input could otherwise
   smuggle query parameters past a naive join).
2. `resolve_project_path` (§A2): traversal rejection on the
   `.resolve()`d candidate (symlink escape collapses here).
3. `validate_readable_file`: exists / is-file / not in an ignored
   directory.
4. SQLite magic-header check (`SQLite format 3\0`): a non-database file
   must fail as `invalid database`, never be parsed as anything else.
5. The server constructs the `mode=ro` URI itself from the validated path
   — caller-supplied URI parameters are never honored.
6. Directories, missing files, and zero-byte files fail deterministically
   (§13); WAL/SHM sidecars are read through the normal SQLite open (no
   special handling, no copying of a live database — §17 notes the live-DB
   caveat).

Residual: TOCTOU between validation and open (accepted, same as every
existing read tool); symlink *inside* the root pointing at a sensitive
in-root file (accepted — in-root is in-scope by design).

## 10. Read-only guarantee (defense layers)

| # | Layer | Status | What it stops |
|---|---|---|---|
| 1 | Path confinement (§9) | **mandatory** | out-of-root databases, URI smuggling |
| 2 | `mode=ro` connection (§8.4) | **mandatory** | all writes at the pager layer |
| 3 | Authorizer deny-all (§8.3) | **mandatory** | any non-read action reaching the engine |
| 4 | Parse gate + single statement (§8.1–2) | **mandatory** | mutation/admin SQL before execution |
| 5 | Row/output/timeout bounds (§11) | **mandatory** | exhaustion, runaway queries |
| 6 | No extension loading (`load_extension` never enabled) | **mandatory** | native-code escape |
| 7 | Magic-header gate (§9.4) | defense-in-depth | mis-typed inputs |

"SELECT-only" alone proves nothing — that is why layers 2 and 3 exist
independently of layer 4.

## 11. Resource limits (bounded, with reasons)

| Bound | Proposed value | Why |
|---|---|---|
| `max_rows` default | 50 | parity with `SEARCH_DEFAULT_RESULTS`; the probe used `LIMIT 10` — same order of magnitude |
| `max_rows` hard cap | 500 | parity with `MAX_SEARCH_RESULTS` |
| Serialized output | 16,000-char ceiling | parity with `formatting.py` output budget |
| Query text | 16,384 chars | parity with `MAX_INPUT_CHARS` |
| Execution timeout | fixed server constant (Gate 1 to set, ≈5–10 s; cf. `environment.py:28` ≤10 s probe rule) | runaway-query protection; no caller input |
| Database file size | `MAX_FILE_BYTES` gate applies at validation | parity with `read_file`; large-but-valid DBs fail closed at Gate 1 unless evidence requires otherwise |

`truncated=true` iff rows were cut by `max_rows`, the output ceiling, or
the timeout. It is distinct from `query failed` (error shape, §13) and
from `database unavailable` (error shape, §13).

## 12. Result contract

Defined in §D. Open items resolved: `columns` **required** (rows are
meaningless without them); `returned` kept for V1.0-shape parity;
execution duration recorded as provenance metadata (not a freshness TTL —
V0.9 A5 stands). No row content in metadata beyond the rows themselves.

## 13. Error semantics

| Category | Cases |
|---|---|
| Policy/security (validation) | outside-root path, absolute path, `file:` URI input, non-SELECT SQL, multiple statements, denied statement type |
| Validation | missing database, not-a-file, ignored-dir, invalid database (magic-header fail), invalid SQL, parameter-count mismatch |
| Execution | locked/busy (`SQLITE_BUSY` → deterministic busy error, no retry loop), SQLite runtime error, timeout, result-too-large |

All errors preserve existing vocabulary: `ValueError`/`FileNotFoundError`
shapes per `security.py`, explicit ERROR rows per the `locale_inspect`
precedent — no new terminology.

## 14. Evidence / freshness / trust semantics (no new vocabulary)

| Field | Value | Reasoning |
|---|---|---|
| `source` | `SERVER_OBSERVED` | bytes parsed by the server process itself, same basis as `environment.py:252` |
| `trust` | `TRUSTED` | locally-read project data, same basis as `environment.py:253` — with the §17 caveat that *trust in accuracy* of app data is the app's business, not the tool's claim |
| `scope` | `FILE` | anchors to the database path (A14: "FILE anchors path evidence", `facts.py:46`) |
| `freshness` | `WORKTREE` | live project content, re-read per call; explicitly **not** `STATIC` (a database mutates) and not time-based (A5) |

## 15. Operation class

No frozen class fits (§A5). Reusing `READ_FILE` would mislabel a query as
a line-window read; reusing `READ_JSON` would mislabel rows as JSON keys;
classifying as `RUN_PYTHON` would route evidence to the execution branch —
exactly the routing error this proposal exists to fix.

**Recommendation: new `READ_SQLITE` class as an explicit owner decision**
(D-V1-09 precedent: propose, do not apply). The alternative — leaving the
capability under `UNKNOWN` — reproduces the D-V1-09 defect
(`shell_plan` BLOCKED on a servable request). `OPERATION_CLASSES` stays
frozen until the owner decides; Gate 1 must not add the class unilaterally.

## 16. Routing / discoverability

**Prefer `mcquest_sqlite_read` when:** the request needs structured rows
or schema evidence from a local SQLite file inside the selected project
root. Route: `IN-ROOT + needs records → mcquest_sqlite_read`, alongside
the existing `IN-ROOT → MCQuest tool` branch (V1.0 §10). Discoverability:
one `server.py` instructions sentence + description pin in
`tests/test_discoverability.py` (V1.0 P2 pattern), **not** enforcement.

**Stays shell/process:** starting/stopping the app server, migrations,
backups, repair, any write, live HTTP diagnosis (§B cause 2), arbitrary
scripting, anything needing a real process environment.


## 17. Security threats

| Threat | Control | Residual |
|---|---|---|
| Path traversal / absolute path | §9 steps 1–2 | none |
| Symlink escape | `.resolve()` before check (§A2) | in-root symlink accepted by design |
| URI escape (`file:` + parameters) | URIs rejected as input; server builds `mode=ro` URI (§9.1, §9.5) | none |
| SQL mutation / stacked statements | parse gate + authorizer + `mode=ro` (§8) | none known; three independent layers |
| `ATTACH` / `DETACH` | denied keyword + authorizer deny (§8) | none |
| Extension loading | never enabled (§10.6) | none |
| PRAGMA side effects | denied (§8) | none |
| Resource exhaustion / huge results | §11 bounds | slow-but-bounded queries still consume the timeout window |
| Malformed / non-DB file | magic-header gate (§9.4) | none |
| Locked DB (live PocketBase!) | deterministic busy error, no retry (§13) | caller retries explicitly; no hidden loop |
| WAL consistency on a live DB | normal SQLite open; rows are a point-in-time read | **accepted caveat**: evidence from a running app's DB can shift between calls — freshness `WORKTREE`, never presented as a snapshot |
| Secret exposure | tool returns only queried rows; no broader dump mode | row content is the requester's own project data; access control is the root boundary, not the tool |
| DoS queries (recursive CTE, cartesian JOIN) | timeout + row/output caps (§11) | bounded compute per call |

## 18. Test plan (Gate-1 matrix; design only, no tests written)

**Positive (mandatory):** simple SELECT; WHERE with bound `?` parameter;
ORDER BY; LIMIT; JOIN; aggregate (`COUNT`/`GROUP BY`); recursive CTE;
`sqlite_master` schema read; PocketBase-shape query (`_collections` +

**Negative (mandatory):** each of INSERT UPDATE DELETE DROP ALTER CREATE
REPLACE VACUUM ATTACH DETACH; PRAGMA; `BEGIN`; stacked statements
(`SELECT 1; SELECT 2`); trailing `;`; comment-prefixed mutation
(`/* x */ DELETE …`); CTE-wrapped mutation (`WITH … DELETE …`);
traversal path (`../`); absolute path; `file:…?mode=ro` URI input;
non-database file; missing database; directory as database;
parameter-count mismatch.

**Bounds (mandatory):** `max_rows` default/cap; output-ceiling truncation
(`truncated` true, `collection_complete` false); timeout (stubbed slow
query); `row_count == len(rows)` invariant whenever not truncated.

**Integrity (mandatory):** database file byte-identical after every test
(including all negative tests); WAL/SHM unmodified-or-absent assertion;
byte-identical output for repeated calls (D009 determinism); registration

**C. Implementation-time finding (documented, not silently patched):**
`sqlite3.complete_statement()` returns False for any statement without a
trailing `;`, which made the §8-layered validator reject ordinary queries.

(`rstrip` + append `;`) before the check, preserving its real value —
catching unterminated strings/comments (8 probe cases, all documented in
`01-V1.1-SQLITE-CONTRACT.md` §3). Also empirically measured: the authorizer
does **not** block `EXPLAIN` (it compiles to read actions) — L3's deny list is
load-bearing there, now stated explicitly in `02-V1.1-SQLITE-SECURITY.md`.
