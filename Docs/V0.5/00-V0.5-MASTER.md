## 2. Authority Order

This is the DOCUMENT PRIORITY whenever a future session resumes. When
documents appear to conflict, use this order (higher wins):

0. **Repository reality + executable test evidence** (always highest —
   repository contents and actual test results outrank every document).
1. User's explicit instruction in the current task.
2. `03-V0.5-STATE.md` (living checkpoint — current implementation state).
3. `01-V0.5-CONTRACT.md` (normative specification).
4. `04-V0.5-TEST-PLAN.md` (test contract).
5. `05-V0.5-DECISIONS.md` (approved decisions).
6. `02-V0.5-IMPLEMENTATION-PLAN.md` (plan).
7. `06-V0.5-CHANGELOG.md` (historical log).
8. phase prompts.

Rules:

- Never use a lower-priority document to silently override a higher one.
- Never trust the CHANGELOG for current state — it is historical only.
- Never infer "implemented" from a plan, a prompt, a changelog entry, a
  previous Cline statement, or the mere existence of a file.
- "Implemented" requires repository evidence AND relevant passing tests.
- If two documents disagree with repository reality: repository reality
  wins; report the discrepancy; do NOT silently reconcile the documents.

## 6. Working Rules

Cline MUST:

1. inspect before editing;
2. implement one phase at a time;
3. run focused tests after each phase;
4. update STATE after each completed phase;
5. update CHANGELOG after meaningful implementation changes;
6. record newly discovered decisions;
7. never claim a phase is complete without test evidence;
8. never mark an item implemented merely because code was written;
9. distinguish:
   - planned
   - in progress
   - implemented
   - tested
   - verified
10. stop and ask if an implementation decision conflicts with the contract.

## 7. Completion Definition

A phase is COMPLETE only when ALL of the following hold:

- implementation exists in the repository (evidence, not claims);
- required focused tests exist AND pass with executable evidence;
- relevant existing tests pass;
- contract invariants are verified (per `04-V0.5-TEST-PLAN.md`);
- acceptance criteria for the phase are satisfied;
- STATE has been updated with that evidence;
- no unexpected working-tree changes remain.

A phase is NOT COMPLETE merely because:

- code was written;
- a test was added;
- Cline believes it works;
- a previous Cline response said it works;
- a changelog entry says so.

"Do not mark a phase complete before the evidence gate."

## 9. Implementation Protocol

When implementing a phase, Cline MUST:

1. Work one phase at a time — never implement future phases early unless
   explicitly authorized.
2. Read the phase prompt before editing.
3. State the planned files before editing.
4. Make the smallest changes necessary.
5. Preserve security and read-only behavior (see §5 Non-Negotiable
   Invariants).
6. Run focused tests first.
7. Run the relevant regression suite.
8. Only AFTER tests pass, update STATE.
9. Update CHANGELOG only with verified facts.
10. Record material decisions in DECISIONS.
11. Report unexpected repository changes immediately.

## 10. Interruption / Resume Rule

If a session ends midway through a phase:

- STATE MUST remain truthful;
- incomplete work MUST remain marked IN PROGRESS (never IMPLEMENTED /
  COMPLETED);
- the next action MUST identify the exact remaining task;
- never mark a phase complete before the evidence gate (§7) has evidence.

The correct last state on interruption is:

- status = IN PROGRESS (with what remains undone)
- next action = exactly what binary step comes next
