# MCQuest MCP v0.5 — Test Plan

> Purpose: Define, BEFORE implementation, the tests that prove the v0.5
> Token-Sparse Contract. A phase is only complete per `00-V0.5-MASTER.md`
> §7 when its required tests exist AND pass with executable evidence.
>
> Listing a test here is NOT evidence that it passes. Only the repository
> consuming it, an actual run, and the recorded result count as evidence.
> Nothing here claims any test currently passes.

---

## A. Purpose

Prove, with executable evidence, that MCQuest MCP v0.5:

- never lets a single MCP response exceed 16,000 characters;
- keeps normal calls at or below 4,000 characters, including when context
  is amplified (`context_lines`, multi-file, multi-category);
- clips every output line to 200 characters;
- truncates atomically at item boundaries (never mid-line) with explicit
  `truncated` state;
- preserves summary-first output (header survives truncation);
- pages only via explicit continuation (`offset` / `next_offset` /
  `next_start_line`), never automatically;
- orders results deterministically (`relative_path ASC, line ASC`);
- reports honest `total` / `returned` / `has_more` / `collection_complete` /
  `total_known`, and for `find_evidence` an authoritative merged-stream
  `total` that is never `min(code_count, docs_count)`;
- bounds read windows (`read_file` / `read_doc` default window + explicit
  ranges);
- does not regress registration, security, read-only, or existing behavior.

## D. Hard 16,000-Character Invariant

- Proves: no tool response (raw string) exceeds the ceiling.
- Expected: `len(output) <= 16_000` for every worst-case scenario.
- Owner: Phase A (formatter), Phase F (every tool, acceptance).
- Also required: `json.dumps({"content":[{"type":"text","text":out}]}).len()`
  stays within a serialized budget (≈16,500) — the Phase 1 audit's
  serialized-response-size assertion.
- Kind: unit (Phase A) / acceptance (Phase F).

## E. Normal 4,000-Character Invariant

- Proves: default calls (including max `context_lines`) stay ≤4,000.
- Expected: `len(default_output) <= 4_000` for all non-read,
  non-diagnostics tools; read defaults and diagnostics defaults per D004/prompt.
- Owner: Phase A (budget), Phases C–E (per tool), Phase F (all).
- Kind: unit + integration.

## F. 200-Character Line Clipping

- Proves: any single source/doc line in any output is ≤200 chars.
- Expected: a 20,000-char line appears as `line[:199] + "…"`.
- Owner: Phase A (`_clip_line`), Phase F (through every tool).
- Kind: unit + regression.

## G. Atomic Output Cutoff

- Proves: the formatter never splits an item mid-line; the next item is
  dropped whole, `truncated` becomes true, and the trailer states the
  omitted-character count.
- Expected: no partial line; trailer present; retained items unchanged.
- Owner: Phase A. Kind: unit.

## H. Summary-First Preservation

- Proves: the leading `[SUMMARY]` (or budget header) is always fully
  emitted even when the body is truncated; truncation trailer follows.
- Expected: header first, body second, trailer last; summary present even
  at the ceiling.
- Owner: Phase A. Kind: unit + acceptance (Phase F).

## I. Explicit Pagination Tests

- Proves: the server only returns page 1 unless `offset`/`start_line` is
  explicitly supplied; pagination metadata is never auto-fetched.
- Expected: default call shows `has_more: true` (if more) with no page-2
  content; page 2 only via explicit continuation.
- Owner: Phases B–E. Kind: integration.

## J. Deterministic Ordering Tests

- Proves: `(relative_path ASC, line ASC)` ordering where applicable.
- Expected: two identical calls return byte-identical bodies; page
  boundaries align (no gaps/dupes) across a multi-page walk.
- Owner: Phases B–E. Kind: integration.

## K. next_offset Correctness

- Proves: `next_offset = offset + returned`, exactly covering the fixture
  once across pages.
- Expected: pages 0→…→k cover all results with `has_more: false` at the
  end.
- Owner: Phases C–E. Kind: integration.

## L. next_start_line Correctness

- Proves: read windows chain via `next_start_line = end_line + 1`.
- Expected: walking `read_file(path, start_line=N)` from `next_start_line`
  reads a whole file exactly once; no overlap, no gap.
- Owner: Phase B. Kind: integration.

## M. total / returned / has_more Correctness

- Proves: `total` is honest (matches fixture or is labeled count-so-far),
  `returned` ≤ page limit, `has_more` consistent with `offset+returned < total`
  and with `collection_complete`.
- Owner: Phases C–E. Kind: integration.

## N. collection_complete / total_known Behavior

- Proves: when a collector stops early the response says so; `total` is
  then count-so-far; the fields are never silently omitted.
- Owner: Phase D, E. Kind: integration.

## O. Read-File / Read-Doc Window Tests

- Proves: unranged read = default window (primary budget 4,000), explicit
  range honored up to 16,000, `next_start_line` + `has_more` correct,
  2MB guard intact, >1,000-line explicit window clamped.
- Owner: Phase B. Kind: integration.

## P. Diagnostics Tests

- Proves: default `max_diagnostics`/`context_lines` fit the normal budget;
  worst settings stay ≤16,000 with `truncated` explicit; 200-char per-line
  clip; "shown (of N)" retained.
- Owner: Phase E. Kind: integration + acceptance.

## Q. pattern_audit Tests

- Proves: default = category summary (counts + samples, no evidence dump);
  expansion via explicit single-category request; per-category paging;
  total ≤16,000; 2MB guard (data added by Phase E).
- Owner: Phase E. Kind: integration + acceptance.

## R. find_evidence Shared-Budget Tests

- Proves: `scope="all"` uses ONE shared `max_results` page budget across
  the merged stream; per-scope counts are reported separately; `total` is
  the authoritative merged/count-so-far value and is **never**
  `min(code_count, docs_count)`; paging by merged position.
- Owner: Phase D. Kind: integration + acceptance.

## S. Security / Read-Only Regression Tests

- Proves: traversal, ignored directories, symlink safety, read-only
  primitives, no shell execution, no new path surface from
  `offset`/patterns/ranges/`category`. Existing security tests unmodified
  and green.
- Owner: every phase (gate at Phase F). Kind: regression.

## T. Registration Tests

- Proves: exactly the 17 approved tool names remain, with preserved
  schemas and defaults.
- Owner: gate at Phase F (guarded continuously by `test_registration.py`).
- Kind: regression.

## U. Full-Suite Regression

- Proves: existing suite (`53 passed, 1 skipped`) plus all v0.5 tests pass
  together.
- Owner: Phase F (and every phase runs the relevant subset).
- Kind: regression/acceptance.

## V. Worst-Case Fixture Tests

Fixtures designed for the failure modes the Phase 1 audit measured:

| Fixture | Used by | Proves |
|---|---|---|
| 2MB file | O | read large-file protection (window + char cap + `next_start_line`) |
| 20,000-char single line | F | per-line clip in every tool path |
| 5,000-line file | O, L | window chaining, explicit range clamp |
| 601-file / 304-doc tree | M, I, J | list/search totals, paging, ordering |
| 1,000-match search corpus | K, J | merged-stream paging, deterministic ordering |
| scope="all" corpus with code+doc matches | R | shared budget, per-scope counts, honest total |
| invalid inputs (`offset=-1`, bad `category`, traversal) | S | parameter validation, security |
| serialized-response worst case | D | `json.dumps` size invariant |

- Proves: no normal investigation tool can inject ~18k–40k tokens into one
  MCP response (the Phase 1 observed failure) — the 16,000-char ceiling is
  enforced on realistic large inputs, not just synthetic strings.
- Owner: Phase F. Kind: acceptance.
