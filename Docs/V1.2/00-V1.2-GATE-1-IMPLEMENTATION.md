## 2. SQLite size-boundary decision

| | |
|---|---|
| Old gate | shared generic `MAX_FILE_BYTES` = 2,000,000 (a text/source-file reading constant; V1.1 Gate 0 §11 itself called it provisional — *"fail closed unless evidence requires otherwise"*) |
| New gate | `SQLITE_MAX_FILE_BYTES` = **32,000,000** decimal bytes, defined in `sqlite_read.py` |
| Semantics | **inclusive**: a file of exactly 32,000,000 bytes is accepted; 32,000,001 is rejected (`st_size > limit`) |
| Position | unchanged — after readable-file validation, **before** the magic-header read and before any SQLite open (oversized non-SQLite files fail at the size stage, never reach SQLite) |
| Configuration | server-side constant only; not a tool argument; not caller-influenced |

Calibration (honest, not a universal claim):

```text
largest observed in-root DB (Gate 0):  auxiliary.db = 21,745,664 bytes
selected limit:                        32,000,000 bytes
headroom:                              ~1.47x
motivating target (Gate 0):            data.db = 2,359,296 bytes
```

This is a single-observation calibration for this version. It is not
statistically proven and not claimed optimal for all PocketBase databases.

## 3. Value-materialization safety model

Gate 0 established four DISTINCT dimensions, each now with its own control:

```text
database file size   !=  query execution cost  !=  returned result size  !=  value-materialization cost
SQLITE_MAX_FILE_BYTES     500,000 VM steps          500 rows / 16,000 chars    three bounds below
```

Three bounds (all server-side constants):

1. **`SQLITE_MAX_VALUE_BYTES = 1,000,000`** — enforced INSIDE SQLite via
   `connection.setlimit(sqlite3.SQLITE_LIMIT_LENGTH, ...)` at connect time.
   Runtime-verified (Python 3.13.9 / SQLite 3.50.4): an over-limit value
   raises `sqlite3.DataError("string or blob too big")` inside SQLite
   **before the value crosses into Python**; the limit also applies to
   values SQLite evaluates (e.g. function arguments). Verified NOT to be an
   aggregate budget: a result row of 3×900 KB passed a 1 MB limit — which
   is exactly why bounds 2 and 3 exist. `getlimit` round-trips; the limit is
   per connection, so no state persists between calls (test-proven).
2. **`SQLITE_MAX_RESULT_COLUMNS = 64`** — Python-side width guard checked
   from `cursor.description` after `execute()` and **before any row is
   fetched**, bounding single-row transient materialization to
   64 × 1,000,000 = 64,000,000 bytes.
3. **`SQLITE_MAX_FETCH_BYTES = 16,000,000`** — Python-side cumulative byte
   budget counted **row by row** (UTF-8 bytes for TEXT, raw length for
   BLOBs) while rows are pulled one at a time — never `fetchmany` — so page
   materialization cannot accumulate past the bound.

Compatibility: `Connection.setlimit` requires Python ≥ 3.12. On older
interpreters the tool **fails closed** with a deterministic error rather
than serving without the per-value bound. The repository runtime is
Python 3.13.9 (probe-verified); packaging metadata (`requires-python
>= 3.10`) is intentionally untouched — recorded here as a known tool-level
floor for V1.2.

## 4. Answers required by Gate 1 §4.1

1. **Resource bounded:** per-result-page Python memory (plus a per-value
   ceiling inside SQLite). Not a whole-process memory budget — described
   exactly as SQLite length limits plus a Python accumulation budget.
2. **Where enforced:** `setlimit` at connect (SQLite C level); width guard
   immediately after `cursor.description`; byte budget inside the row
   collection loop.
3. **When exceeded:** execution aborts immediately; the connection closes;
   no output is built.
4. **Error the caller receives:** deterministic `ValueError` (surfaced as a
   tool error) with one of exactly three messages:
   `SQLite value exceeds the 1,000,000-byte materialization safety limit.`,
   `Query results exceed the 16,000,000-byte materialization safety budget.`,
   `Query returns N columns; the materialization guard allows at most 64.`
5. **Partial results escape:** none — the exception is raised before any
   row encoding, summary, or `[END]` construction; the returned payload
   contains no rows.
6. **`truncated`/`collection_complete` honesty:** these fields exist only
   on success paths and keep V1.1 meaning (row cap / output cut). A
   materialization abort is an ERROR and never carries `truncated=true`,
   `collection_complete=true`, or `row_count` (asserted by test).

## 5. Validation order (documented, fail-closed preserved)

```text
query policy -> bound parameters -> path -> readable-file -> file-size gate -> magic header ->
max_rows clamp -> read-only URI connect -> setlimit -> authorizer -> progress handler ->
execute -> result-column guard -> row-by-row fetch under byte budget -> encode -> output budget
```

The V1.1 order is preserved up to the connection; guards are additive and
post-connect. Oversized non-SQLite files still fail at the size stage
(test 9.F) and never reach SQLite parsing.
